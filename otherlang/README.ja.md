## 「Too Many Tools」 — CLI コーディングエージェント。サンドボックス化されたワークスペース内のファイルを編集し、十数種類の言語でコードを実行し、任意のリポジトリで自動的にコミットとプッシュを行います。

>**Python 3.8 以上が必要です。**

## コマンドは `tmtcode` です

インストールすると、PATH にコマンドが 1 つ追加されます。

```bash
tmtcode
```

システム上のどのディレクトリからでも実行できます。**実行したディレクトリが、TMT の作業対象となるプロジェクトになります。**

```bash
cd ~/Projects/MyWebsite && tmtcode      # TMT は ~/Projects/MyWebsite を対象に作業します
cd ~/Documents/MyProject && tmtcode     # TMT は ~/Documents/MyProject を対象に作業します
```

TMT のインストールは、どこであれ一度きりです。プロジェクトの中にコピーすることは一切ありませんし、プロジェクト側に TMT のファイルが必要になることもありません。

## インストール

```bash
git clone https://github.com/lllons/TMT.git
cd TMT
pip install -e .                 # `tmtcode` を PATH に配置します
pip install -e ".[live]"         # 任意: ストリーミングと色のために requests と rich を追加します
```

エージェント本体は標準ライブラリ以外に何も必要としません。`requests` と `rich` はライブストリーミングと色を追加するだけのもので、なくても TMT は代替動作にフォールバックします。

インストール後は、クローンをその場に置いたまま、作業したい場所から `tmtcode` を実行してください。クローンは TMT の住まいであり、あなたのプロジェクトではありません。

インストールしなくても、クローンはそのまま、どこからでも実行できます。

```bash
python /path/to/TMT/TMT.py                    # カレントディレクトリがプロジェクトになります
python /path/to/TMT/TMT.py ~/Projects/MyWebsite
```

Windows なら `py`、macOS / Linux なら `python3` です。

## 2 つのディレクトリ

TMT は、自身のインストール先とあなたのプロジェクトを厳密に分けています。これらは別々のものであり、別々のままであるべきものです。

| | そこにあるもの | 場所 |
|---|---|---|
| **インストールディレクトリ** | TMT 自身のソース、保存した API キー、TMT の git 共著者 ID、そのログ | クローンした場所 — `~/tools/TMT`、`C:\Coding\TMT` など。一度決めたら動きません |
| **プロジェクトディレクトリ**（ワークスペース） | TMT が読み、編集し、実行し、コミットするファイル | `tmtcode` を実行した場所 |

変更されるのはプロジェクトディレクトリだけです。どのプロジェクトの中に立っていても TMT 自身のファイルはインストールディレクトリに留まるため、どこでも同じエージェント — 同じキー、同じ共著者アドレス — になります。

もう一度はっきり言っておきます。**あるプロジェクトで TMT を使うために、TMT をそのプロジェクトへコピーする必要はありません。** クローンは 1 つ、インストールも 1 回。あとは任意のプロジェクトへ `cd` して `tmtcode` と打つだけです。

## プロジェクトディレクトリの選び方

| コマンド | プロジェクトディレクトリ |
|---|---|
| `tmtcode` | カレントディレクトリ |
| `tmtcode ../other-repo` | カレントディレクトリを基準に解決され、その後絶対パス化されます |
| `tmtcode /abs/path/to/project` | そのパス |
| `tmtcode --dir PATH` | 位置引数の `PATH` と同じもの。既存の利用のために残されています |

相対パスは、コマンドを実行したディレクトリを基準に解決されたうえで絶対パス化されます。位置引数の `PATH` と `--dir` に別々のディレクトリを指定するのはエラーで、TMT は起動せずに終了します。

TMT は与えられたディレクトリを、そのまま使います。プロジェクトルートを探して上へ遡ることはしません。`MyWebsite/src` で実行すれば、ワークスペースは `MyWebsite/src` です。

解決されたパスは起動時に表示されるので、間違った場所からの実行はすぐに分かります。

```
Workspace: C:\Projects\my-repo
```

そのディレクトリの外側はすべて対象外です。ワークスペースの外へ出るパスは、たどられるのではなく拒否されます。

## 権限と制限

- TMT はプロジェクトディレクトリ内のどこにでもファイルを作成、上書き、削除でき、そのディレクトリが git リポジトリでない限り、そこで行われたことは復元できません。通常の読み書き権限が必要です。
- インストールディレクトリは書き込み可能である必要があります。`.tmt_key` と `logs/` がそこに書かれます。`.tmt_git` と `.tmt_git.local` はそこから読まれるだけです。
- ディレクトリは選択されるものであり、作成されることはありません。TMT は、存在しないパス、ファイル、ファイルシステムのルート、そしてホームディレクトリを拒否します。
- ディレクトリにすでにファイルがあり、かつ git のワーキングツリー内でない場合、TMT は何に向けられようとしているのかを説明し、開始前に確認を求めます。git リポジトリはそれ自体が取り消し手段なので、確認なしで開始します。
- TMT がシェルコマンドを実行することはありません。コードの実行は `run_file` を通じてのみ行い、起動するアプリケーションは以下に挙げる 2 つだけです。
- プッシュにはすでにお使いの git 認証情報が使われます。TMT は認証情報を一切保存せず、ログイン機構も実装していません。

## 起動画面

`tmtcode` を起動するたびに、同じ画面が開きます。ターミナルいっぱいに広がる TMT のワードマークと、その下の一行です。

```
                              Press Enter to Continue
```

この行は待っている間、脈打ちます。カラー対応のターミナルではグラデーションが行を流れ、色のないターミナルではゆっくりとした太さの脈動になり、エスケープが使えない環境では何も起きません。ここでも色がメッセージそのものになることはないからです。先へ進むキーは Enter だけで、Ctrl-C は TMT を閉じます。それ以外はすべて無視されるので、画面が落ち着く前に最初のタスクを打ち込んでも、何かが動き出すことはありません。

**起動画面は必ず表示されます。** これは設定項目ではなく、オフにする手段もありません。*設定できる*のは、Enter を押したあとに何が起きるかです。

### Enter のあと: 更新チェック

`Auto Update on Launch` が **オン**（既定）の場合、TMT は自身の git チェックアウトを見て新しいバージョンが存在するかを確認し、同じ画面上で結果を伝えます。

```
                              Searching for updates...
```

続いて、次のいずれかが表示されます。

```
                                    Up to date.            nothing was pulled, nothing restarted
                          Update complete. Restarting...   a fast-forward was applied
                            Continuing without updating.   an update could not be taken safely
                Update check failed. Continuing without update.
```

設定が **オフ** の場合、これらは一切行われず、TMT が行ったふりをすることもありません。実行されなかった検索について「searching」の行が出ることはありません。そのまま先へ進みます。

そのあとは、TMT はこれまでどおりに続きます。このインストールがまだ設定されていなければ API キーのセットアップへ、そうでなければ通常のスタート画面へ進みます。

### TMT が自身を更新する場合としない場合

更新は、明白に安全なときにだけ行われ、あなたの作業には決して手を触れません。

| 見つかった状態 | 行われること |
|---|---|
| すでに最新 | 何もしません。プルもリスタートもありません |
| リモートが先行、ツリーがクリーン、fast-forward 可能 | fast-forward してからリスタートします |
| **未コミットのローカル変更がある** | 拒否し、その旨を伝えます。あなたの変更はそのままです |
| **ブランチが分岐している** — ローカルとリモートの両方が進んでいる | 拒否します。ローカルのコミットが破棄されることはありません |
| upstream が未設定、または detached HEAD | 判断できない旨を伝えて先へ進みます |
| そもそも git チェックアウトではない | 先へ進みます |
| ネットワークなし、git なし、リモート不正、マージ失敗 | 失敗を報告して先へ進みます |

すでにチェックアウトされているブランチ上で動作し、ブランチを作成したり切り替えたり強制したりすることはありません。使うのは `git fetch` と `git merge --ff-only` だけです。**`git reset --hard`、`git clean`、強制チェックアウト、素の `git pull` は決して実行しません。** プルはマージを起こしうるものであり、起動時のマージこそ絶対に起きてはならないことだからです。テストが更新機構自身のソースを読み、それらのコマンドが含まれていないことを表明しています。

TMT はインターネットがなくても使えます。更新チェックの失敗は、スプラッシュ上の一行以上のものにはなりません。

### リスタート

更新が成功すると、プロセスは新しいものに置き換えられます。古いモジュールが読み込まれたままになるのではなく、新しいコードが実際に動くようにするためです。コマンドラインは保持されます。`tmtcode --dir ~/project` は `tmtcode --dir ~/project` として戻ってきます。

その後もう一度起動画面が表示されますが、これは想定どおりです。起動画面はあらゆる起動の一部だからです。再起動されたプロセスは自身が最新であることを確認し、そのまま続きます。**ループすることはありません。** 自動リスタートは 1 回の起動につき最大 1 回で、2 つめのプロセスは自分が 2 つめであることを知っています。

### オフにする

Settings → `Auto Update on Launch` を選び、Enter で切り替えます。

```
  AI Provider            Which service answers a request
  API Key                The credential that service is given
  Model                  Which model TMT runs on
> Auto Update on Launch  Check for a newer TMT after the launch screen  ON
  Back                   Return to the menu
```

この値はインストールディレクトリの `.tmt_autoupdate` に、モデルやエフォートの設定と並べて保存されます。したがって 1 つのプロジェクトではなくインストールに属し、再起動しても残ります。ファイルがなければオン、誰にも読めないファイルや意味をなさない内容に書き換えられたファイルも、起動時のエラーではなくオンとして扱われます。

**これをオフにしても起動画面はオフになりません。** スプラッシュはどちらの場合でも表示されます。

## 初回起動

初回起動では [OpenRouter のキー](https://openrouter.ai/keys) を尋ね、インストールディレクトリの `.tmt_key`（git 管理外）に保存します。`OPENROUTER_API_KEY` を設定すればこの手順は省けます。キーはプロジェクトごとではなく、インストールごとに一度だけ尋ねられます。

`Task>` プロンプトでタスクを入力してください。`quit` または `exit` で終了します。Ctrl-C は TMT を閉じずに現在のタスクをキャンセルします。

8 KB 未満のファイルは、一定の個数と合計サイズを上限として自動的にモデルへ提示されます。途中で打ち切られた場合はその旨がリストに記されます。それより大きいファイルは必要に応じて読まれます。

## 頼めること

普通の言葉で構いません。アクションは TMT 自身が選びます。

```
Task> write a python script that fetches a URL and prints the status code
Task> what does report.py do?
Task> find every TODO in src and list them
Task> change the timeout in net.py from 5 to 30 seconds
Task> run hello.py
Task> open notes.txt in notepad
Task> commit the changes and push to main
```

## あなたに話しかける手段: `send_message` と `end_conversation`

TMT があなたの画面に言葉を出す方法はちょうど 2 つあり、その違いのすべては、そのあとタスクが続くかどうかにあります。

| アクション | テキストを表示する | タスクを終了する |
|---|---|---|
| `send_message` | する | **しない** — 制御は毎回エージェントに戻ります |
| `end_conversation` | する | **する** — そしてタスクを終了できる唯一のアクションです |

**`send_message` は途中で何かを伝えるためのものです。** 「まずパーサーを読みます」「テストが通ったので、次はドキュメントです」「このファイルは思ったより大きいです」といった具合です。セッションに印字されるのであとからスクロールして読み返せますし、そのあと TMT はいた場所からそのまま作業を続けます。1 つのタスクの中で、価値がある限り何度でも使えます。上限はなく、最終的な意味合いも一切ありません。

**`end_conversation` が終わりです。** そのメッセージが、あなたの手元に残る要約になります。だからこそエージェントには、そこに書かれていない作業はやらなかったも同然だと伝えてあります。停止する方法はこれ以外にありません。別途 `done` があるわけでもなく、メッセージをこっそり最後のものに変えるフラグもありません。TMT はこのアクションでタスクを終えるか、終えないかのどちらかです。

**終わらせたいことと、終わらせてよいことは別です。** 完了ゲートが押し止めるのは `end_conversation` であり、そのプロンプトで有効にしたケイパビリティはこれを拒否できます。未完了のステップが残っているプラン、まだ通っていないレビュー、実行されていない、あるいは失敗したチェックを見つけた検証などです。拒否はエラーではなく、ターンを終わらせもしません。TMT は理由を渡されて作業に戻り、答えはまだ語られないままになります。[ケイパビリティ](#ケイパビリティ-planreviewverify) を参照してください。

バックグラウンドエージェントには、意味のある形ではどちらのチャンネルもありません。読んでいる人がいないのでメッセージは 1 ステップを費やして誰にも届かず、終了はメインエージェントへの報告になります。[バックグラウンドエージェント](#バックグラウンドエージェント) を参照してください。

## ケイパビリティ: `/plan`、`/review`、`/verify`

TMT にできることのうち 3 つは、通常のツール作業ではありません。プランを書いてそれに縛られること、2 つめのエージェントに差分を監査させること、そしてリポジトリ自身のチェックを走らせること。いずれもモデルの実行を丸ごと 1 回分余計に消費し、画面に列を 1 つ増やし、TMT 自身の最終回答を拒否しうるものです。これらはあなたが費やすものなので、頼まない限りオフであり、頼み方はプロンプトにコマンドを書くことです。

| コマンド | 有効になるもの |
|---|---|
| `/plan` | プランニングのワークフロー — TMT がステップを書き、それを終えるまで完了できません |
| `/review` | 独立したコードレビュー — 別の読み取り専用エージェントが作業を監査します |
| `/verify` | スマート検証 — このリポジトリが実際に備えているチェックを、本当に実行します |

```
Task> build me an authentication system
        nothing gated. Ordinary tools, ordinary answer.

Task> build me an authentication system /plan
        plans the work and is held to the plan. No review, no verification.

Task> fix this implementation /review
        an independent reviewer audits it before the answer goes out.

Task> add the endpoint /plan /verify /review
        the whole pipeline: plan, implement, verify, review, fix, answer.
```

**スラッシュこそがすべての違いであり、`verify` という語だけでは足りません。** 「verify this code」「please verify this」「verified」「verification」はいずれも、通常の作業を依頼するときに人が口にする言葉であり、どれもエンジンをオンにしません。オンにするのは `/verify` だけです。`plan` と `review` も同様で、「review my code please」は意見を求める依頼、`/review` はゲート付きでサイクル数に上限のある、独立したレビュアーへの依頼です。

コマンドで始まるより長い単語も同じくオンにしません。`/planning`、`/planner`、`/plan123`、`/reviewing`、`/verification` はいずれもただのテキストであり、パスの中に現れたコマンドも同様です。`src/review` や `abc/verify` はパスであってコマンドではありません。

残りの規則は、想像どおりのものです。

- **プロンプトのどこでも構いません。** 先頭でも、途中でも、末尾でも、貼り付けたブロックの中で単独の行になっていても構いません。`/plan Build it`、`Build it /plan`、`Build the /plan feature` はいずれも同じ依頼です。
- **何度書いても構いません。** `/plan ... /plan` はプランニングを 1 回だけ有効にします。プランが 2 つ存在することはありません。
- **大文字小文字は問いません。** `/PLAN` も有効で、画面上では `/PLAN` のまま残ります。TMT はあなたのテキストに装飾を施すだけで、書き換えることはありません。
- **互いに独立しています。** `/plan` はレビューや検証をオンにしませんし、それらも互いをオンにしません。ワークフローを選ぶのはあなたです。
- **1 プロンプトごとに有効です。** ケイパビリティは、それを求めたリクエストに対して認可されます。次の質問では、そこでも求めない限りゼロから始まります。

**これらをオンにできるのはあなただけです。** TMT でもなく、バックグラウンドエージェントでもなく、レビュアーでもなく、読み込んだファイルでもありません。タスクが大きそうだと判断したモデルが自分の推論の中に `/plan` と書いてアクションを呼んでも、ランタイムがそれを拒否します。認可はあなたが入力した行からのみ読み取られ、それ以外からは読み取られません。これは二重に強制されています。認可されていない動詞はそもそもプロンプトに含められず、それでも呼び出されたときにはディスパッチャがもう一度拒否します。

**入力中にハイライトされます。** 入力ボックス内の有効なコマンドには赤 → オレンジ → 緑のグラデーションがかかるので、Enter を押す前に何をオンにしたのかが分かり、打ち間違えたときにはそれが消えるのも見えます。塗られるのは正確なコマンドだけで、`verify` はそのまま、`/verification` もそのままです。色のないターミナルでは代わりに太字と下線でコマンドが示され、パイプ経由の実行では装飾は一切ありません。その場合でも行には `/plan` と読める形で残ります。それがコマンドそのものの綴りだからです。

ターンの実行中は、認可したものが右側の列の上部に一覧表示されます。

```
                                                        CAPABILITIES 2
                                                        ● /plan
                                                        ● /verify

                                                        PLAN 2/5
```

**`/plan`、`/review`、`/verify` を単独で書けば、従来どおりのレポートのままです。** [スラッシュコマンド](#スラッシュコマンド) を参照してください。コマンドだけの行は TMT が何をしているかを見せ、そのあとにタスクが続く行は、そのタスクに対してケイパビリティを認可します。

### ファイル

| アクション | 用途 |
|---|---|
| `write_file` / `write_files` | ファイルを 1 つ、あるいは一度に複数作成します |
| `patch_file` | 検索と置換 — 編集の既定手段です |
| `replace_lines` | 正確な行範囲を置き換えます |
| `append_file` | ファイルの末尾に追記します |
| `read_file` / `read_lines` | ファイル全体、または行範囲を読みます |
| `glob` | パスのパターンでファイルとディレクトリを見つけます |
| `grep` | ファイルの内容を検索し、パス、行番号、その行を報告します |
| `copy_file` / `rename_file` / `delete_file` | 移動、リネーム、削除 |
| `create_folder` / `delete_folder` | フォルダ（再帰的な削除はオプトイン） |
| `list_files` | ワークスペースの一覧 |

パスはプロジェクトディレクトリからの相対として解釈され、その外側に解決されるものはすべて拒否されます。一覧表示、読み取り、書き込みの対象は、そのディレクトリだけです。

既存ファイルの編集には書き直しではなく `patch_file` が使われるので、触れていない行は触れられないままです。Python ファイルは書き込み前に構文チェックされ、壊れた編集は保存されずに拒否されます。

### プラン

**プロンプトに `/plan` と書いて依頼してください。** このコマンドがなければ TMT はプランを書かず、ここに書かれていることが回答をゲートすることもありません。[ケイパビリティ](#ケイパビリティ-planreviewverify) を参照してください。

`/plan` を付けた場合、まとまった作業 — 機能の追加、リポジトリ全体にまたがるバグ修正、サブシステムのリファクタリング、プロジェクト全体のドキュメント更新 — に対して、TMT は着手前にプランを書き、あなたの目の前でそれを一つずつ片付けていきます。プランは作業中、ライブ領域の右側に列として現れ、そのまま完了した状態で次のプロンプトの横に残ります。

```
                                                        PLAN 2/5
                                                        ─────────────────────────
                                                        S1 ✓ Inspect repository
 09:14 · OpenRouter · MiniMax M3                        S2 ✓ Find and…erminology
 ───────────────────────────────────────────────────    S3 ● Update documentation
 > Describe your next task                              S4 ○ Run tests and verify
 ───────────────────────────────────────────────────    S5 ○ Explain changes
```

| 記号 | ステータス | 色 | 意味 |
|---|---|---|---|
| `✓` | completed | 緑 | そのステップの作業が実際に完了しています |
| `●` | in progress | オレンジ | いま取り組んでいる唯一のステップです |
| `○` | pending | 赤 | これから行うものです |
| `!` | blocked | 琥珀 | 進められない状態で、未完了として数えられます |

進行中のステップは常にちょうど 1 つです。1 つ完了すると、次のステップが自動的に繰り上がります。色は確認のためのものであって、メッセージそのものではありません。どのステータスにも記号が付いており、列全体は、それ以外を描けないターミナルでは `+ > - !` と ASCII の罫線に劣化します。

**プランは進捗バーではなく、契約です。** ステップが残っている間、TMT はタスクを終えることを許されません。作業を残したまま送られた最終回答は、そもそもあなたには表示されません。ランタイムがそれを拒否し、まだ果たしていないステップの一覧をモデルに返し、ターンが続きます。これはプロンプトでのお願いではなくプログラムによって強制されるので、モデルが終わったと判断しても終わったことにはなりません。

```
Task> add the feature
 · Planning the work in two steps.
 ◆ Plan created with 2 steps.
 ▲ Plan not finished - 2 steps outstanding, next is S1 Implement the feature. Continuing.
 · The feature is in; running the tests next.
 ◆ S1 (Implement the feature) in_progress -> completed.
 · Suite is green.
 ◆ S2 (Run the tests) in_progress -> completed.
 ┌──────────────────────────────────────────────────────────────┐
 │ Added the feature and the suite is green: 12 tests, 0 failures.│
 └──────────────────────────────────────────────────────────────┘
```

作業が想定と違うと分かったときには、いつでもプランを改訂できます。ステップのリネーム、追加、削除、あるいはプラン全体の差し替えです。できないことが 2 つあります。完了したステップが再び開かれることはありません。終わったステップは終わったままであり、形が間違っていたプランは巻き戻すのではなく丸ごと差し替えられます。そして、作業が積まれたプランを取り下げることはできません。それがゲートを回避する唯一の抜け道だったので、いずれかのステップが完了した時点でクリアは拒否されます。プランを完遂することも作り直すことも、どちらも画面上で見えます。こっそり取り下げることは、見えません。

**何にでもプランが付くわけではありません。** 「この関数は何をしていますか」は 1 回の回答で済むもので、そこにプランを立てても画面上のノイズであり、TMT 自身の返答へのゲートにしかなりません。プランは段階のある作業のためのものです。

**プランはセッションではなく、タスクに属します。** あなたが次の質問をした瞬間に破棄されるので、未完了のプランが無関係な質問への回答を止めてしまうことはありません。ディスクには何も書かれません。バックグラウンドエージェントはプランを見ることも変更することもできません。プランはメインエージェントとあなたの契約であり、ワーカーがステップを完了扱いにできてしまえば、主張されただけの作業で TMT が完了できてしまうからです。

**45 桁未満のターミナルでは** この列は描画されません。プロンプトボックスのほうが場所を必要とするからです。`/plan` はどの幅でも通常のテキストとして同じ内容を表示します。

### リポジトリを理解する

コードベース全体を読まずに中を把握するための 9 つのアクションです。それぞれが 1 つの問いに答えるもので、TMT は目的に合う最も狭いものを選ぶよう指示されています。

| アクション | 用途 | 使いどころ |
|---|---|---|
| `tree` | ディレクトリ、ファイル、サイズ、階層。内容は読みません | プロジェクトの形を知りたいとき |
| `glob` | パスのパターンに一致するファイルとディレクトリ。`*` は `/` の手前で止まり、`**/` は任意の深さを意味し、`/` を含まないパターンはどこにあるその名前にも一致します | どのファイルが存在するのか、あるいはあるファイルがどこにあるのかを知りたいとき |
| `grep` | ファイルの中を検索し、パス、行番号、その行を報告します。既定では完全一致で大文字小文字を区別し、クエリは複数行にまたがっても構いません | 探しているテキストが分かっているとき |
| `find_symbol` | 関数、クラス、メソッド、定数、型が *定義されている* 場所 | 言及ではなく定義を知りたいとき |
| `code_map` | 何がこれを定義し、何がこれを import し、これが何を import し、どこから参照されているか | 変更が何に影響するかを知る必要があるとき |
| `replace_across` | 多数のファイルにわたる同一の編集 | プロジェクト全体で使われているものをリネームするとき |
| `related_tests` | git の差分を読み、実行する価値のあるテストを挙げます | 1 か所だけ変更したので全部は走らせたくないとき |
| `remember` / `recall` | このプロジェクトについての、セッションをまたいで残るメモ | 突き止めるのに時間がかかったことがあるとき |

```
Task> show me the project structure
Task> find every place that calls self.workspace_root
Task> where is calculate_total defined?
Task> what imports agent_file_ops?
Task> rename old_function_name to new_function_name across src
Task> which tests should I run for what I just changed?
```

**`glob` はパスや名前でファイルを見つけ、`grep` はファイルの中のテキストを見つけます。** 違いはそれだけであり、そしてそこは取り違えないでおく価値があります。うまくいく順序は、`glob` で候補となるファイルを見つけ、`grep` でその中の行を見つけ、`read_lines` でその範囲を読み、それから編集し、最後にテストする — 1 行を探すためにリポジトリを読み通すのではなく、という順序です。

```json
{"action": "glob", "pattern": "agent_*.py"}
{"action": "glob", "pattern": "testing/**/*.py"}
{"action": "grep", "query": "end_conversation"}
{"action": "grep", "query": "def run_file", "glob": "agent_*.py"}
{"action": "grep", "query": "timeout", "path": "src", "ignore_case": true}
```

`grep` は、その名前の由来となったツールと同じく、既定では完全一致で大文字小文字を区別します。`"ignore_case": true` を付けると緩くなり、`"regex": true` はクエリを正規表現として読み、`"context"` は各マッチの前後に行を加え、`"path"` や `"glob"` はそもそもどのファイルを読むかを絞り込みます。ファイル全体が返ってくることは決してありません。得られるのはパスと行番号とその行で、残りは `read_lines` が取ってきます。

**`replace_across` は既定でプレビューします。** 何ファイル、何か所を変更する *はずか* を報告するだけで、何も書きません。同じアクションを `"apply": true` を付けて再送すると実行されます。改行コードとエンコーディングは保たれ、バイナリファイルはスキップされ、Python ファイルをパース不能にしてしまう置換は書き込まれずに拒否されます。

**事実と推測は、区別して示されます。** Python のシンボルはファイルをパースして見つけるので、その答えは正確です。他の言語は字句的にマッチさせるもので、その旨が明示されます。`related_tests` は、差分が証明していることと単なる推測とを分けて示します。ヒューリスティックを測定値として提示するものは 1 つもありません。

**プロジェクトメモリ** は TMT 自身の設定の横に、プロジェクトをキーとして保存されます。あなたのリポジトリの中に置かれることは決してありません。TMT の他のあらゆる状態と同じ規則です。ノートは書き込まれる前に走査され、キーやトークンやパスワードらしき形のものは拒否されます。

### コードの実行

`run_file` はコードを実行して出力を返します。Python、JavaScript、TypeScript、Ruby、PHP、Lua、Perl、R、Go、C、C++、Java に対応します。タイムアウトは 10 秒です。ツールチェインは PATH 上にある必要があります。コードはプロジェクトディレクトリを作業ディレクトリとして実行されます。

### アプリ

`open_app` は Notepad か、ファイルを選択した状態の Explorer を起動します。それ以外はありません。TMT がシェルコマンドを実行することは決してありません。

## Git

TMT がコミットするのは、プロジェクトディレクトリを含むリポジトリであって、TMT 自身のリポジトリではありません。TMT が作るすべてのコミットで、author も committer もあなたのままです。TMT は `Co-authored-by` トレーラーによって、あなたと並んでクレジットされます。

```
Task> commit this                        commits, does not push
Task> commit these changes and push       commits and pushes
Task> push this to main                   targets main
Task> fix the bug                         edits only, no commit, no push
```

コミットとプッシュは別々です。TMT がプッシュするのは、あなた自身の言葉がそれを求めたときだけです。「fix the bug」でプッシュが起きることはありませんし、編集を終えたことでも起きません。

アクション: `git_status`、`git_diff`、`git_identity`、`git_commit`、`git_push`。

ステージするのは自分が変更したファイルだけなので、あなたの無関係な作業は未コミットのまま残ります。ブランチを作ることも、リモートをでっち上げることも、強制プッシュすることもありません。プッシュが失敗した場合、コミットはローカルに残り、実際のエラーがそのまま返されます。

### TMT の共著者クレジット

TMT はあなたとしてコミットしませんし、あなたの代わりにコミットもしません。リポジトリ自身の git ID が author であり committer です。TMT はメッセージにトレーラーを 1 行加えるだけで、それ以外は何もしません。コミットは 1 つ、そこに 2 人がクレジットされます。

TMT が作ったコミットを、git が報告するとおりに示します。

```
$ git log -1 --format=fuller
commit f1977e70a471011bf9b5ab643aecdf5e18a8e8fa
Author:     Liam <liam@example.com>
AuthorDate: Sat Aug 29 13:10:01 2026 +1200
Commit:     Liam <liam@example.com>
CommitDate: Sat Aug 29 13:10:01 2026 +1200

    Add a greeting file

    Co-authored-by: TMT code <TMT.tmt.code@gmail.com>
```

これはたまたまコロンを含む散文の行ではなく、git のトレーラーです。したがって git 自身がそれを返してくれます。

```
$ git log -1 --format=%(trailers:key=Co-authored-by)
Co-authored-by: TMT code <TMT.tmt.code@gmail.com>
```

実際上の意味は次のとおりです。

- author と committer は、リポジトリの git 設定が示す人物です。TMT がそのどちらかに自分を書き込むことはなく、あなたの git 設定にグローバルにもリポジトリ単位にも書き込むことはありません。
- git の ID が設定されていなければ、git はコミットを拒否します。TMT はそれを報告し、`user.name` と `user.email` を自分で設定するよう伝え、author の代役を務めることはしません。何もコミットされません。
- TMT がトレーラーを付けるのは、自分が作成したコミットだけです。あなたが自分で実行した `git commit` には手を触れません。
- すでに TMT のアドレスをクレジットしているメッセージには、トレーラーは 2 つではなく 1 つだけ付きます。判定はアドレスで行われるので、表示名が違っていても同じアドレスであればクレジット済みとみなされます。
- 既存のトレーラーは残ります。他の誰かの `Co-authored-by:` は保持され、TMT はその横に追加されます。`Signed-off-by:` のブロックには、新しい段落を作るのではなく合流します。
- 履歴が書き換えられることはありません。完成したコミットに何らかの理由でトレーラーがなかった場合、TMT はそれを報告し、amend せずにコミットをそのままにします。
- TMT のアドレスが設定されていない場合、あるいは同梱のプレースホルダーがそのままになっている場合、TMT はコミットを拒否し、何もステージしません。

GitHub 上でのクレジットは別の問題であり、その答えを TMT が左右することはありません。

- TMT が決めるのはコミットのメタデータ、すなわちトレーラー、それだけです。
- 共著者をクレジットするかどうかを決めるのは GitHub です。GitHub はトレーラー内のアドレスを、アカウントで検証済みのアドレスと突き合わせます。どのアカウントでも検証されていないアドレスは誰にもクレジットされず、表示名だけでは何も起こりません。
- アドレスが一致している場合でも、GitHub のコントリビューターやプロフィールのデータは遅れることがあります。プッシュしたからといって、コントリビューショングラフがすぐ変わるとは限りません。
- クレジットを得ることと、プッシュを許されることは別です。認証は別個の話であり、あなたの手に残ります。

### 共著者の ID

```
TMT_GIT_NAME=TMT code
TMT_GIT_EMAIL=someone@example.com
```

TMT がクレジットされるアドレスです。コミットの author として書き込まれることは決してありません。読み取り順は、`TMT_GIT_*` 環境変数、次に `.tmt_git.local`（git 管理外、マシンごと）、次に `.tmt_git`（追跡対象で、プロジェクトに同梱）です。名前の既定値は `TMT code` です。メールアドレスに既定値はなく、あなたの git 設定から取られることも決してありません。あなたの git 設定が供給するのは author であって、共著者ではありません。

どちらのファイルもインストールディレクトリにあるので、どのプロジェクトに向けても TMT は同じアドレスでクレジットされます。

`.tmt_git` が追跡対象なのは意図的です。コミット用のメールアドレスは公開メタデータであって認証情報ではないので、どのクローンも設定なしで同じ TMT 共著者を得られます。このファイルが保持するのは名前とアドレスだけです。トークン、パスワード、キーの類は、このファイルにも `.tmt_git.local` にも書かないでください。

どの供給元が採用されたか、どのファイルが参照されたか、そのアドレスが使用可能かを見るには `git_identity` を実行してください。

### GitHub の帰属設定

追跡対象の `.tmt_git` には、TMT を表す GitHub アカウントで検証済みのアドレスが記されているので、新しいクローンでも設定なしで正しくクレジットされます。そのメールアドレスがプレースホルダーのままである場合、TMT は誰も特定しない共著者をクレジットするくらいならと、コミットを拒否します。代わりにあなた自身のアカウントをクレジットするには、次のようにします。

1. TMT 用の GitHub アカウントを作成します。
2. そこにアドレスを追加し、検証します。
3. そのアドレスを `.tmt_git.local` に書くか、`.tmt_git` に書いて一度コミットします。

これらは 4 つの別々のことであり、TMT が決めるのはそのうち 1 つだけです。

- **オーサーシップ** — コミットに書き込まれる author と committer。あなたのものです。TMT はそれを報告するために読み返すだけで、設定も変更もせず、あなたの `user.name` と `user.email` はグローバルにもリポジトリ単位にも変更されません。
- **共著者クレジット** — `Co-authored-by` トレーラー。コミットのうち TMT が決める唯一の部分です。
- **GitHub の帰属** — GitHub がそのトレーラーのアドレスを検証済みアカウントと突き合わせること。TMT の手を離れており、表示名だけでは何も起こりません。
- **認証** — 誰がプッシュしてよいか。あなたのものであり続けます。SSH キー、認証情報マネージャー、`gh` のログインなどです。TMT は認証情報を保存せず、ログイン機構も実装していません。

## 検証

**プロンプトに `/verify` と書いて依頼してください。** このコマンドがなければ以下のことは何も起こらず、ここに書かれていることが回答をゲートすることもありません。`verify` という素の単語では足りません。[ケイパビリティ](#ケイパビリティ-planreviewverify) を参照してください。

`/verify` を付けた場合、TMT はある作業が完了したと言うことを許される前に、このリポジトリが実際に備えているチェックを実行し、それが通るまでランタイムは回答を許しません。

要点は、証拠と意見の違いです。

> 「これで動くはずです」は検証ではありません。`43 passed, 0 failed` が検証です。

TMT はコードが動くかどうかをモデルに尋ねません。リポジトリを読み、このプロジェクトが自分自身を何でテストし、リントし、ビルドしているのかを突き止め、差分を読んで何が変わったかを把握し、*その*変更にとって実行する価値のあるチェックを選び、それらを実行し、終了コードを報告します。モデルが書くものがその結果を動かすことはありません。ステータスを設定できるキーはどのアクションにも存在せず、チェックが通るのはプロセスが 0 で終了したときだけで、それ以外の瞬間には通りません。

### 何を実行するかの決め方

**あなたのコマンドを、自分の推測より優先します。** 順序は次のとおりです。

1. このリポジトリが名前で定義しているコマンド — `package.json` のスクリプト、`Makefile` のターゲット、ルートの `run_tests.py`
2. このリポジトリが設定しているツール — `[tool.ruff]`、`[tool.mypy]`、`tsconfig.json`
3. プロジェクトのパッケージマネージャー — `npm`、`pnpm`、`yarn`、`bun`、`uv`、`poetry`
4. そのエコシステムの標準コマンド — `cargo test`、`go vet`、`pytest`
5. 推測。ただし推測であると明示されます

`package.json` に `"test": "vitest run"` とあれば、TMT は `npm run test` を実行します。node のプロジェクトは jest を使うものだ、などと決めつけません。リポジトリに `run_tests.py` があれば、それがテストコマンドです。`pytest` でも動く場合であってもそうします。あなたが実行しているものと違うものを実行して、それをあなたの検証だと称するのは、たとえ通ったとしても間違いだからです。

CI の設定は、あなたが実際に使っているツールの *証拠* として読まれるのであって、コマンドの供給源として読まれることは決してありません。TMT が実行するものに、プロジェクトのファイルから取り出した文字列は 1 つもありません。取り出されるのは名前であり、コマンドはそれを中心に固定のテーブルから組み立てられます。その経路のどこにもシェルはありません。

**安いチェックを高いものより先に実行し**、最初に失敗したところで止まります。

| レベル | 内容 |
|---|---|
| 1 | 変更箇所の構文とフォーマット |
| 2 | リント、型チェック、コンパイラのチェック |
| 3 | 変更したものを名指ししているテスト |
| 4 | その周辺のテスト |
| 5 | プロジェクトのビルド |
| 6 | スイート全体 |

型チェッカーがすでに失敗しているなら、結合テストスイートに費やす 10 分は、間違っていると分かっているツリーを測るための 10 分です。失敗より後のものはすべてスキップとして、その理由付きで報告されます。したがって、*チェックされなかった* ものは暗黙にされるのではなく、目に見えます。

**変更のリスクが高いほど、深くまで進みます。** 認証、マイグレーション、データベーススキーマ、API 契約、並行処理、ファイルシステムの境界、シェル実行、依存関係やビルドの設定 — あるいは単に一度に多くのファイルが変わった場合 — にはスイート全体が実行されます。ドキュメントのみの変更には静的チェックだけが行われ、テストは実行されません。

### 4 つの結果を、混同しないこと

| | 意味 |
|---|---|
| **PASSED** | コマンドが実行され、0 で終了した。これが唯一の証拠です |
| **FAILED** | コマンドが実行され、0 以外で終了した。何かが間違っており、出力がそれを語っています |
| **SKIPPED** | 実行されなかった — ツールが未インストールか、先行するチェックがすでに失敗していた |
| **ERROR** | 実行できなかった、あるいは完了しなかった。何も分かっておらず、これはあなたのコードの失敗では *ありません* |

これらが真偽値にまとめられることはありません。タイムアウトは失敗ではありませんし、リンターがないことはリントが通ったことではありません。TMT がそうした穴を埋めるために何かをインストールすることはありません。依存関係の不足は報告されるだけで、こっそり解決されることはありません。

### 見た目

```
VERIFY 1/3
✓ Syntax          passed
✓ Lint            passed
✗ Targeted tests  2 failed, 41 passed
– Full suite      not run: Targeted tests did not pass
```

`/verify` は実行の全体を表示します。失敗したものの出力も含みます。

### どのテストを選ぶか

テストコマンドがパスを受け取れるプロジェクトでは、TMT は変更が到達するテストを割り出し、それらを先に実行します。テストファイルが **targeted** として数えられるのは、それを裏づける証拠があるとき — 変更されたモジュールを名指ししている、変更されたシンボルを import している、あるいはプロジェクト自身の命名規約が示す場所にある — であり、到達可能性の推測にとどまる場合は **related** として数えられます。両者は分けて扱われ、レベルも分けられます。推測を測定値として提示することは、選別しないことより悪いからです。

プロジェクトのテストコマンドをパスで絞り込め *ない* 場合 — `npm test` や、すべてを実行する `run_tests.py` など — TMT はその旨を述べ、テストの証拠としてスイート全体を実行します。すべてを実行しておいて、それを targeted と称することはありません。

### いつ行われるか

検証が必須になるのは、ランタイムがまとまった作業の **両方** の側面を観測したときです。3 ステップ以上のプランと、実際に書き込まれたファイルが少なくとも 1 つ。レビューの要否を決める材料と同じ 2 つの事実で、主張ではなく観測されたものです。質問、読み取り、あるいはプランのない小さなパッチは、まったくゲートされません。

あなた自身の言葉で、どちらの方向にも上書きできます。「…そしてテストを実行して」でオンになり、「no verification needed」でオフになります。何も言わなければ、証拠に委ねられます。

プランの中にも居場所があります。検証を名前に含むプランのステップは、検証が未了のうちは完了としてマークできません。この拒否はプロンプトではなくコードの中にあります。そして最終回答には 3 つすべてが必要です。**プランの完了、検証の合格、そしてレビューの合格。** どれか 1 つが他を免除することはありません。

### サイクルと、その上限

失敗したチェックはフィードバックであって、タスクの終わりではありません。TMT は出力を読み、報告された内容を修正し、もう一度検証します。最大 3 巡です。それを超えると、回答は永久に保留されるのではなく解放され、検証は結局通らなかったという一行を伴って出ていきます。沈黙のほうが悪い失敗だからです。

**合格は、その下でコードが動いた瞬間に古くなります。** 検証が通ったあとに何かを編集したなら、通ったものは出荷されるものではありません。次の回答は、あらためて検証されるまで保留されます。これこそが、修正と検証のループを提案ではなく閉じたループにしているものです。

リポジトリに実行できるものが何もない場合 — テストコマンドもリンターもなく、何もインストールされていない場合 — 検証はその旨を述べ、回答は解放されます。そして TMT は、この作業は未検証だとはっきり伝えなければなりません。「検証できませんでした」は有用ですが、何も実行していないのに「検証済み」と言うのは有用ではありません。

## 独立したレビュー

**プロンプトに `/review` と書いて依頼してください。** このコマンドがなければレビュアーは起動されず、ここに書かれていることが回答をゲートすることもありません。[ケイパビリティ](#ケイパビリティ-planreviewverify) を参照してください。

検証とレビューは別の問いに答えるものであり、まとまった変更には両方が必要です。検証が問うのは *実行可能なチェックを通るか* であり、レビューが問うのは *これは正しい変更か、そして安全か* です。スイートが緑であることは、コードがそのテストの言うとおりに動くことを示すだけです。そのテストが正しいテストであることも、あなたが間違った機能を作ってしまったことに気づくことも示しません。

TMT は、完了したと言うことを許される前に自分の作業をレビューします。しかも自問によってではありません。**別のエージェント** が、そのどこも自分では書いていない状態でリポジトリと差分とあなたの元の依頼を読み、見つけたことを報告します。メインエージェントは、完了を妨げる指摘に対処しなければならず、レビューが実際に通るまでランタイムは回答を許しません。

要点は、緑のテストスイートが捕まえられない類の失敗です。

> あなたはリフレッシュトークン対応の認証を依頼しました。テストは通ります。レビュアーが差分を読むと、リフレッシュトークンの有効期限が一度も確認されていないこと、そして `/health` がいつのまにか認証の後ろへ移動していることが分かります。どちらもテストされていません。同じエージェントがコードもテストも書いたからです。

### サイクル

```
      your request
           |
      plan --> implement --> tests
           |
      independent review
           |
   +-------+--------+
   |                |
 PASS            FINDINGS
   |                |
   |          main agent fixes
   |                |
   |            tests again
   |                |
   +-------<---- review again
           |
     plan complete
           |
      final answer
```

### レビュアーが見るもの、見ないもの

レビュアーに与えられるのは、真実の源として扱われる **ユーザーの元の依頼**、実装したエージェントが書いたプラン、そのプランの完了状況、`git status`、`git diff`、`git diff --stat`、現在のコミット、実際に書き込まれたパス、そしてセッション内で実際に実行されたものの記録です。それ以外はすべて自分で取りに行きます。変更されたファイル、それを呼び出しているコード、テスト、プロジェクト自身の慣習などです。まず差分を見て、差分では答えられないところにだけ広げていきます。

レビュアーは **読み取り専用** で、これはプロンプトでのお願いではなくコードで強制されています。書き込み系の動詞はすべて、ディスパッチされる前に拒否されます。レビュアーは報告し、変更はすべてメインエージェントが行います。また何も実行できないので、自分の実行結果をレビューすることもできません。セッションが何を実行したかは観測された事実として伝えられ、それが何を証明するのかを判断するのがレビュアーの仕事です。

レビュアーは、はっきりとした言葉で、テストを信用するな、プランを信用するな、実装したエージェントによる自分の作業の説明を信用するな、と伝えられています。

### 指摘

すべての指摘には、深刻度、ファイル、実際に読んだ箇所の行番号、根拠、なぜそれが問題なのか、そして修正の方向が付きます。

| 深刻度 | 完了を妨げるか |
|---|---|
| `CRITICAL` | はい — 正しさ、セキュリティ、データ損失、破壊的な振る舞い |
| `MAJOR` | はい — 実在するバグ、必要な振る舞いの欠落、起こりうるリグレッション、重要なテストの欠落 |
| `MINOR` | いいえ — 直す価値のある、より小さな欠陥 |
| `SUGGESTION` | いいえ — 任意です |

指摘と併せて、レビュアーはあなたの依頼から組み立てた **要件チェックリスト** を返します。各項目には満たされている、部分的、満たされていないのいずれかが付きます。これが「このコードは良さそうか」と「頼まれたものを作ったのか」を切り分ける部分であり、間違った機能のきれいな実装を捕まえるチェックです。

判定は `PASS`、`PASS_WITH_WARNINGS`、`FAIL` のいずれかです。完了を妨げる指摘を挙げながら合格を主張する応答は **FAIL** として記録されます。決めるのは指摘であり、矛盾が見えるようにレビュアー自身の主張もその横に示されます。

### 抜け穴が塞がれている理由

- **合格を生み出せるのは、本物のレビューだけです。** 判定を設定できるキーは、どのアクションにも存在しません。レビューの状態を動かせる唯一のものは、レビュアーエージェント自身の出力を項目ごとにパースし検証したものです。「review passed」と書くモデルは文を書いているだけであり、文は状態機械を動かしません。
- **完了しなかったレビューは合格ではありません。** クラッシュした、タイムアウトした、あるいは読めないものを返したレビュアーは、タスクを `ERROR` のまま残します。これは失敗とまったく同じように最終回答をゲートします。
- **合格したレビューは、その下でコードが動くと古くなります。** レビューが通ったあとにファイルを編集すれば、次の回答には新しいレビューが必要です。通ったものは、出荷されるものではありません。
- **プランのレビューのステップを、先回りしてチェックすることはできません。** タイトルにレビューを含むステップを完了としてマークすることは、レビューが通っていない間は拒否されます。
- **レビュアーが自分の作業をレビューすることはできません。** `review` はレビュアーを含むすべてのバックグラウンドエージェントに拒否されており、この動詞はメインエージェントのプロンプトにしか記載されていません。
- **ワーカーが動いている間はレビュアーを起動できません。** ワーカーは、レビュアーが読んでいるツリーに書き込むことになり、そのレビューは一度も存在しなかった状態に対するものになってしまいます。

### いつ行われるか

レビューが必須になるのは、ランタイムがまとまった作業の **両方** の側面を観測したときです。3 ステップ以上のプランと、実際に書き込まれたファイルが少なくとも 1 つ。どちらか一方では足りません。何も変えなかった長いプランは調査であり、プランのない 1 行のパッチは手助けです。どちらも、モデルの主張ではなく TMT が観測した事実なので、作業を小さいものとして説明することでレビューを避けることはできません。

あなた自身の言葉で、どちらの方向にも上書きできます。「…そして変更をレビューして」でオンになり、「no review needed」でオフになります。何も言わなければ判断は証拠に委ねられ、これが通常のケースです。

### 上限

**1 タスクにつきレビューのサイクルは 3 回** です。3 回目でもなお完了を妨げる問題が報告される場合、回答は永久に保留されるのではなく解放されます。それ以上保留すればターンを使い切り、回答が何も出ないまま終わることになるからです。回答には、レビューが通らなかったことと未解決の指摘が何件あるかをはっきり述べる一行が付き、メインエージェントも自分の言葉で同じことを述べることを求められます。沈黙のほうが悪い失敗です。

### 画面上では

レビューはプランの下、同じ右側の列に、最大 3 行で表示されます。

```
PLAN 2/5                       PLAN 5/5
S1 + Inspect repository        S1 + Inspect repository
S2 + Implement feature         S2 + Implement feature
S3 > Add tests                 S3 + Add tests
S4 - Independent review        S4 + Independent review
S5 - Final verification        S5 + Final verification

REVIEW 1/3                     REVIEW 2/3
> Running independent review   + Review passed
```

どの状態にも色だけでなく記号が付くので、エスケープを取り除いても、色がまったくないターミナルでも列は読めます。`/review` は指摘を全文で表示し、2 列を取れないほど狭いウィンドウではこれが入口になります。

## プロジェクトコンテキスト: `TMT_Context/`

かつてセッションは、何もないところから始まっていました。プロジェクトについて分かったこと — エントリポイントの場所、テストを実行するコマンド、先週実装したもの、中途半端に残されたもの — は、起動のたびにゼロから組み立て直されるか、プロセスの終了とともに失われていました。

いまや TMT は、作業対象のプロジェクトに 2 つの markdown ファイルを保持します。

```text
my-project/
├── src/
├── tests/
├── package.json
└── TMT_Context/
    ├── notes.md      how this project works
    └── progress.md   what has been done, what is being done, what remains
```

これらはごく普通のファイルです。開いて、読んで、編集して、コミットしてください。

### いつ作られるか

プロジェクトでの **最初の実際のタスク** のときです。TMT を起動したときでも、スラッシュコマンドを入力したときでもありません。起動して気が変わっただけなら、何も残りません。

```text
tmtcode
   ↓
"Add a dark mode to this application."
   ↓
no TMT_Context → create it, inspect the project, record what was found
   ↓
start working
```

`TMT_Context/` がすでにあれば、作り直され **ません**。どちらかのファイルがすでにあれば、上書きされ **ません**。マージもされず、再生成もされず、まったく触られません。

### `notes.md` — このプロジェクトの仕組み

最初にリポジトリの実地調査から書かれ、その後 TMT が学ぶにつれて修正され、追記されていきます。あなたも TMT も物事を見つけられるよう、見出しは固定です。

```text
# TMT Project Notes
## Project Overview      ## Dependencies
## Architecture          ## Constraints
## Important Files       ## Known Issues
## Build                 ## TMT Notes
## Testing
## Configuration
```

最初の調査は意図的に浅いものです。マニフェスト、マーカー、パッケージのスクリプト、Makefile のターゲット、`[tool.X]` セクション、CI の設定、README の最初の段落、トップレベルのディレクトリ、そしてマニフェストが *宣言している* エントリポイントだけを見ます。ファイルを読むだけで何も実行しないので、大きなリポジトリを歩き回るのではなく一瞬で済みます。

**そこに書かれることが捏造されることはありません。** 事実を確定できなかった場合、ファイルはそう述べます。

```text
## Build

Build command has not yet been confirmed. Nothing in this repository
names one that TMT recognised.
```

規則はそれだけです。推測されたビルドコマンドは、空のセクションより悪いものです。失敗するコマンドと、他のすべての行への信頼を、あなたから奪うからです。

### `progress.md` — 何が起きたか

```text
# TMT Project Progress
## Current Status        ## Verification
## Completed             ## Important Decisions
## Currently Working On  ## Known Issues
## Remaining             ## Next Steps
## Tests
```

**タスクが完了として記録されるのは、その証拠があるときだけです。** すべてのステップが終わったプラン、または実際に書き込まれたファイルです。何もせずに終わったタスクは、未完了の項目として *Currently Working On* に残ります。何かを実装するという TMT の意図が、チェックマークになることはありません。

**テスト結果は、常に本物だけです。** Tests セクションは終了コードから組み立てられた検証結果をもとに書かれるので、`39 passed, 3 failed` と書かれていればそれが実際に起きたことであり、何も実行されなかった場合には何も書かれません。

### どう使われるか

コンテキストはワークスペースのスナップショットの **前** にモデルのプロンプトへ入ります。したがって TMT が最初に読むのはすでに分かっていることであり、次に読むのがリポジトリそのものです。それこそが狙いです。プロジェクトの 2 つめのタスクは、レイアウトを再発見しなくてよい分、1 つめより速くあるべきなのです。

```text
"Now add keyboard shortcuts."
   ↓
load TMT_Context → already knows the architecture, the test command,
                   what dark mode did, what is outstanding
   ↓
search only where it still needs to
```

丸ごと貼り付けるのではなく、予算が割り当てられます。小さいファイルはそのまま入り、大きいものは最も重要なセクションを残したうえで **どれが省かれたかを明示します**。見えないセクションは存在しない、とモデルが教え込まれることは決してありません。

### コンテキストがコードより上位に立つことはない

`TMT_Context/` は記憶であって、真実ではありません。`notes.md` が認証は `auth.py` にあると言っていて、リポジトリではそれが `authentication/service.py` へ移動しているなら、**正しいのはリポジトリです**。

TMT はノートが名指しするパスを、実在するパスと突き合わせ、その結果をノート本体と並べてプロンプトに入れます。

```text
STALE: these paths are named in the notes but are not in the workspace now:
src/main.py. Do not act on them without checking.
```

ノートをあなたの代わりに書き換えることはしません。ファイルがないのは、ノートが古いからかもしれませんし、あなたがリファクタリングの途中だからかもしれず、その 2 つを見分けられるのはコードを読むことだけだからです。TMT がするのは、そのノートを鵜呑みにさせないこと、そしてより正確に分かった時点で直すことです。

### あなたの編集は守られます

どちらのファイルも、いつでも手で書き直して構いません。TMT は **一度に 1 つのセクションだけ** を変更し、それ以外のバイトは読んだときのまま正確に書き戻します。TMT が知らない見出しも、あなたの文章も、あなたの空け方もそのままです。ファイルを丸ごと渡す操作は存在しませんし、それを求める手段もありません。

TMT の作業中にファイルを編集した場合でも、あなたの編集は残ります。変更の瞬間にファイルが読み直されるのであって、先に読んだ写しが使われるわけではないからです。

### 秘密が書かれることはありません

キーも、トークンも、パスワードも、`.env` の値も書かれません。TMT が記録するのは要件であって、値ではありません。

```text
## Configuration

Environment variables this project declares (names only -- values are
never recorded here), from `.env.example`:

- `API_KEY`
- `DATABASE_URL`
```

本物の `.env` が開かれることはありません。存在は stat から把握されるだけで、内容は読まれません。どちらのファイルに書かれるものも、`remember` が使うのと同じ認証情報フィルタを通り、認証情報らしき形のものは伏せられたうえで報告されます。

### `/plan`、`/review`、`/verify` との関係

コンテキストはこれらの仕組みを重複させるものではなく、それらが到達した結論を覚えておくものです。

| | 書かれる先 |
|---|---|
| プランのステップと、その実際の状態 | `progress.md` の *Currently Working On* |
| 検証が実際に何を実行し、その数値がどうだったか | `progress.md` の *Tests* と *Verification* |
| 未解決のまま残っている、完了を妨げるレビュー指摘 | `progress.md` の *Known Issues* |

最終状態が永続化されるのは、完了ゲートが合意した **あと**、回答が出ていく前です。したがって順序は次のままです。

```text
work → verify → review → persist → end
```

永続化が、プランや検証やレビューが押し止めていた回答を解放することは決してありません。3 つすべてがすでに合意するまで、永続化は求められないからです。また `send_message` が何かを確定させることもありません。「機能を実装しました」と言うのは文であって、証拠ではありません。

### 常にプロジェクトごと

コンテキストのパスは、求められるたびにアクティブなワークスペースから算出されます。したがって 2 つのプロジェクトが 1 つのコンテキストを共有することはあり得ず、一方の情報が他方に現れることもあり得ません。

### オフにする

Settings → **Project Context** → Enter。既定は **ON** です。

オフにすると、TMT は `TMT_Context` を作成も読み取りも更新もしません。**すでに書かれたファイルはそのまま残されます。** それらはプロジェクトのもの、そして書いた人のものであり、設定は誰かのノートを削除してよいという同意ではないからです。

このスイッチは、TMT の他のインストール単位の設定と並んで `.tmt_context` に保存されます。したがってこれは TMT 自身の状態であり、ワークスペースには追随しません。コンテキストの *ファイル* は、TMT が意図的にあなたのプロジェクトへ書き込む唯一のものです。

### 作成できない場合

読み取り専用のチェックアウト、権限エラー、ディスクの空き不足など。TMT は一度その旨を伝え、あなたのタスクを続けます。

```text
Persistent project context could not be created (PermissionError: ...).
Continuing without TMT_Context.
```

この機能のために、タスクを失敗させる価値のあるものは 1 つもありません。

### コミットすべきか

それはあなたの判断です。TMT があなたの `.gitignore` に手を出すことはありません。既定では、この 2 つのファイルは通常のプロジェクトドキュメントとして扱われます。読めて、差分が取れて、リポジトリで作業する全員にとって有用なものなので、コミットすれば TMT が学んだことをチームの他のメンバーと共有できます。ローカルに留めておきたければ、無視してください。

## バックグラウンドエージェント

TMT は委譲できます。メインエージェントがバックグラウンドのワーカーを起動し、それらは TMT 自身が使うのと同じアクションと同じモデルで実際に作業を行い、メインエージェントはそれらを待って何をしたかを報告します。

```
Task> spawn three agents to write multiply.py, divide.py and power.py, then wait for them
```

| | 実行場所 | 編集可 | プッシュ可 | あなたと話す | 終了手段 |
|---|---|---|---|---|---|
| メインエージェント | セッションループ | はい | はい | はい | `end_conversation` |
| ワーカー | バックグラウンドスレッド | はい | **いいえ** | いいえ | `internal_response` |
| ノートエージェント | バックグラウンドスレッド | **いいえ** | いいえ | 回答のみ | `internal_response` |

**同時に 10 ワーカーまで。** メインエージェントはこの数に数えられず、ノートエージェントも数えられません。11 番目のリクエストは無視されるのではなく、その旨を述べる一文とともに拒否されます。

`/agents` は各エージェントが何をしているかを表示します。実際のターミナルでは、空行の末尾で右矢印キーを押すと同じものがライブパネルとして開き、左矢印で閉じます。

### 委譲の契約

委譲は願いごとではなく契約です。`spawn_agent` は任意の `constraints` オブジェクトを取り、そのエージェントが何をしてよいか、どれだけ動いてよいか、何を報告しなければならないかを指定します。そして **TMT はその 3 つすべてを自ら強制します。** エージェントには自分の契約が伝えられ、さらにディスパッチャでも拒否されるので、別のツールを選ぶことでどれかを回避することはできません。

```json
{"action": "spawn_agent",
 "task": "Investigate how authentication is put together in this repository.",
 "constraints": {
     "read_only": true,
     "timeout_seconds": 600,
     "report": {"file_list": true, "diff": true, "summary": true}
 }}
```

どの部分も任意であり、**`constraints` のない `spawn_agent` はこれまでとまったく同じように振る舞います。** プロンプトはバイト単位で同一、権限も同じ、レポートも同じです。既存の委譲について変わったことは何もありません。

制約は **委譲ごと** です。ワーカー #1 は読み取り専用で 5 分、ワーカー #2 は自由に書き込めて 15 分、ということができますし、どちらも相手の契約を見ることも影響を与えることもできません。契約は 1 つのレコードにぶら下がる 1 つの不変オブジェクトであり、その経路のどこにもグローバルな状態がないからです。

#### `read_only`

`read_only: true` は、そのエージェントがこのワークスペースを調べてよく、変更してはならないことを意味します。読み取り系の動詞 — `read_file`、`read_lines`、`list_files`、`glob`、`grep`、`find_symbol`、`tree`、`code_map`、`related_tests`、`recall`、`git_status`、`git_diff`、`git_identity` — はすべて残り、それ以外はすべて拒否されます。

**プロンプトでのお願いではなく、実行時に強制されます。** 拒否はアクションが実行される前に、2 か所で行われます。`agent_worker` は単一アクションの経路でもバッチの経路でも、ディスパッチ前にすべてのアクションを検査し、`agent_actions.execute_action` がディスパッチャでもう一度検査します。どちらも同じ関数に問い合わせるので、規則は 1 つ、それを強制する場所が 2 つという形になります。

**これは禁止動詞のリストではなく、ホワイトリストです。** これが書かれたあとに TMT へ追加されたアクションは、すべて既定で拒否されます。禁止動詞のリストであれば、誰かが次に登録する変更系の動詞を黙って通してしまいますし、それを追加する人はこのリストを書いた人ではありません。

これにより、明らかなファイル書き込みではない経路も押さえられます。

| 拒否されるもの | 理由 |
|---|---|
| `write_file`、`append_file`、`write_files`、`patch_file`、`replace_lines`、`replace_across`、`copy_file`、`rename_file`、`create_folder`、`delete_file`、`delete_folder` | ファイルを変更するため |
| `run_file` / `run_python` | プログラムは何でも書き込めるので、実行することは変更経路であるため |
| `git_commit` | コミットはリポジトリを変更するため |
| `open_app` | ワークスペースの外のアプリケーションを起動するため |
| `remember` | TMT 自身のメモリストアに書き込むため |
| `git_push`、`plan`、`review`、`verify`、`project_context` | 契約の有無にかかわらず、すべてのバックグラウンドエージェントですでに拒否されているため |

**TMT には汎用のシェル動詞がありません。** だからこそ、ここには「安全な」コマンドの許可リストがどこにも存在しません。ワーカーが任意のコードを実行できる唯一の方法は `run_file` であり、読み取り専用の委譲にはそれが端的に拒否されます。コマンド文字列のパースも、`sed -i` が書き込むかどうかの推測も要りません。これがこの保証の誠実な形です。実行経路が 1 つしかなく、それが閉じられていることに立脚しているのであって、TMT が変更を伴うコマンドと無害なコマンドを見分けられることに立脚しているのではありません。

**主張していないこと。** 読み取り専用の委譲は、TMT が提供するどの動詞を通しても永続的な変更を行えません。ただしこれはサンドボックスではありません。TMT はオペレーティングシステムのレベルで書き込みを防いでいるわけではなく、将来のアクションが書き込み経路を開いた場合、読み取り専用のワーカーがそれに届く前に、意図的にホワイトリストへ追加される必要があります。

拒否された試みは **隠されず、報告されます**。ワーカーには何がなぜブロックされたかが伝えられるので、調整して続けることができます。ブロックされた書き込みが自動的に委譲の失敗になるわけではありません。そして試みは記録され、結果としてメインエージェントに届きます。

```
Constraint violations: 1 write operation blocked (write_file src/auth.py)
```

#### `timeout_seconds`

1 から 3600 までの整数です。これは 1 アクションではなく **委譲全体** の最大実行時間であり、アクションが終わったりモデルが応答したりしてもリセットされません。

計測はワーカーが実際に開始した時点から始まります。登録された時点ではありません。したがって、他の何かが遅かったせいで委譲が持ち時間の一部を失うことはありません。

**ランタイムによって強制されます。** 期限はキャンセルと同じ 3 つの境界で確認されます。各ステップの先頭、ストリーミング応答のチャンクの間、そしてアクションがディスパッチされる直前の行です。期限を過ぎると、

- それ以降のアクションは実行されません。
- エージェントのステータスは `timed_out` になります。これは `failed` でも `killed` でも **ありません**。
- ワーカーの枠はただちに解放されるので、空きを待っていた委譲が開始できます。
- そこまでに行われたことは保持され、負っていたレポートも引き続き収集されます。

保証は `kill` が持つものとまったく同じで、それ以上ではありません。**期限を過ぎたあと、それ以上のツール呼び出しはディスパッチされません。** すでに送信中のリクエストは最後まで届きます。Python のスレッドは強制終了できず、ストリーミング応答には中断の手段がないからです。即時終了を主張することは、嘘のコストが最も高い場所での嘘になります。

タイマースレッドはありません。期限はレコード上の算術であり、答えが問題になりうるあらゆるタイミングで掃き取られます。空きの確認のたび、再描画のたび、そしてすべての待機の中で、待機は最も近い期限を越えてブロックすることはありません。これは 5 秒間のカード保持と同じ設計であり、理由も同じです。キャンセルするものがなく、漏れるものがなく、テストは 10 分待つ代わりに数値を進めるだけで駆動できます。

不正なタイムアウトは、何かが始まる前に拒否されます。負の値、ゼロ、文字列、`true`、1 秒未満の端数、1 時間の上限を超える値などです。**拒否された契約はワーカーを 1 つも起動しません。** 契約の半分だけで動いている委譲は、誰にも推論できない唯一の結末だからです。

#### `report`

`file_list`、`diff`、`summary` を、それぞれ独立に指定します。これらは **権限ではなく**、エージェントが何をしてよいかに影響することはありません。

- **`file_list`** — そのエージェント自身のアクションが実際に読み書きしたファイル。そのアクションが伴っていたリクエストから取られます。エージェントが何を読んだと述べたかから組み立てられることは決してありません。
- **`diff`** — このエージェントが書いたファイルについて git が述べること。意図的にそれらのファイルに限定されています。ワーカーが動いている間もメインエージェントは作業を続け、複数のワーカーが同時に動きうるので、ツリー全体の差分は 1 つの委譲の作業では断じてないからです。読み取り専用の委譲の diff は `No changes permitted by delegation.` と表示されます。書き込み可能でありながら何も変更しなかった場合は `No workspace changes.` です。
- **`summary`** — エージェント自身による作業の説明。`internal_response` の `response` であり、レポートの中で唯一モデルの言葉である部分です。

レポートは、成功時だけでなく **あらゆる終了時** に収集されます。タイムアウトした委譲やキャンセルされた委譲にも、本物のファイル一覧、本物の差分、本物の所要時間があり、通常どおり終わらなかったからといってそれを捨てるのは、そのエージェントが成し遂げたことの唯一の記録を捨てることになります。

メインエージェントに返るものは構造化された簡潔なものです。ツール呼び出しの記録も、生ログもありません。

```
Background agent #4
STATUS: TIMED OUT
Contract: READ ONLY  TIMEOUT 10:00  FILES  SUMMARY
Runtime: 10:00 of 10:00
Progress: 17 actions taken, 11 files inspected, 0 files changed

SUMMARY
  Found the authentication entry point in AuthService; three test modules cover it.

FILES
  Inspected (11):
    src/auth/service.py
    src/auth/token.py
    ...
  Changed: none
```

#### 画面上では

プロンプトの横のカウンタは `4/10 agents`、パネルのヘッダーは `AGENTS 4/10` と表示され、制約付きのエージェントのカードはその契約をコンパクトに示します。

```
██░░░░░░ #3  RO  8:32/10:00  +0 -0  ~4k out  1m28s  running
```

`RO` は読み取り専用、対になった数値は上限に対する残り時間 — 実際に作業を止めることになるのと同じ算術による、本物のカウントダウン — であり、カード上の `F D S` はレポートの要求を示します。`/agents` は、読むだけの幅があるところでそれらすべてを詳しく伝えます。タイムアウトしたエージェントは `timeout` と表示され、失敗ではなく停止として着色されます。実際にそうだからです。

#### 入れ子の委譲

バックグラウンドエージェントは自前のエージェントを起動できません。そのアクションコンテキストにはレジスタがまったく含まれていないので、読み取り専用の委譲が書き込み可能な委譲に到達する手段はありません。これは契約が存在する前からそうであり、いまも変わりません。起こり得ないことのために、入れ子ワーカーの規則をここで発明したりはしません。

### 動いている様子を見る

エージェントが動いている間、それぞれがメインの進捗バーのすぐ下に自分の行を持ちます。

```
██████████  60% Working                      <- the main agent, in colour
██░░░░░░ #1  +45 -3  4k out  47s  running    <- one row per agent, in grey
██████░░ #2  +0 -0  ~900 out  1m34s  running
████████ #3  +7 -120  ~15k out  2m21s  done
```

各行には、そのエージェントの番号、追加および削除した行数、生成したトークン数、稼働時間、そして状態が載ります。行の上のものはすべて推定ではなく実測です。ただし `~` の付いた数値は例外で、これはプロバイダが報告しなかったためテキストから TMT が算出したことを意味し、そうなった場所には必ず印が付きます。

**エージェントのバーは灰色でメインのバーは色付きであり、その違いこそが要点です。** 色のグラデーションは「メインエージェントが作業中で、進み具合はこれくらい」を意味します。色付きのバーが 5 本あれば、一目では 1 つのプロセスが 5 回報告されているように読めてしまいます。エージェントには固有の色ではなく、色がないことが与えられています。

**エージェントのバーが示すのは、消費したステップ予算の割合であって、完了までの近さではありません。** 後者は誰にも分かりません。それを示唆するバーは、誰も持っていない唯一の数値を捏造することになります。終了したエージェントのバーが満杯なのは、それが終わったからです。完了が実際に分かる唯一の瞬間です。

終了したエージェントの行とカードは 5 秒間残ってから消えます。その結果は消えません。メインエージェントはずっとあとでもそれを要求できます。

入力ボックスの上のカウンタは、エージェントの作業をセッション自身の合計に算入します。

```
+55 lines, -5 lines, ~12k context, 433 out, agents ~22k tokens
```

行数にはエージェントが書いたものがすべて含まれます。ワーカーが書いた行はセッションが書いた行であり、5 つのワーカーがプロジェクトを書き直している最中に `+0` と表示するカウンタは、1 つのスレッドについては真実を、セッションについては嘘を語っていることになります。エージェントのトークン消費は `context` とは分けて報告されます。そちらは送信中のリクエストのウィンドウがどれだけ埋まっているかであり、そこに 5 つのワーカーを足せば、存在しないコンテキストを説明することになるからです。

### `/note` — 何も乱さずにワークスペースについて尋ねる

```
Task> /note which module owns the prompt box?
```

読み取り専用のエージェントが、他のすべてが進行したままワークスペースから答えます。検索、読み取り、構造の調査はできますが、作成、編集、削除、プッシュはできません。これは丁寧に頼むのではなく、あらゆるアクションの前に検査されるホワイトリストによって強制されています。

質問は同じ行に書きます。この形はパイプ経由の実行を含め、どこでも機能します。パイプ経由のリーダーは 1 行につき 1 タスクを取るので、2 段階のプロンプトはパイプからはそもそも到達できません。実際のターミナルでは、`/note` だけを入力すると質問を別途尋ねられます。

### バックグラウンドエージェントが意図的にできないこと

これらは設計上の制限であって、やり残しではありません。

- **ワーカーはプッシュできません。** `git status`、`diff`、`log`、`branch` を読むことはでき、コミットもできます。リモートに到達することはメインエージェントの担当であり、そのメインエージェントもタスクにあなた自身の言葉が必要です。
- **ワーカーはファイルやフォルダを削除できません。** どちらもターミナルで人間の確認を待つものであり、バックグラウンドスレッドには尋ねられるターミナルがありません。ワーカーは代わりにパスを報告し、メインエージェントが実行します。
- **ワーカーはテストスイートを実行できません。** `run_file` は 10 秒で諦めるのに対し、実際のスイートはそれより長くかかるので、テストの検証を頼まれたワーカーは、できなかったことと代わりに何をしたかを述べます。見ていない結果を報告することはありません。
- **「kill」は協調的であって即座ではなく、タイムアウトも同様です。** Python はスレッドを強制停止できません。保証され、かつテストされているのは、**エージェントが kill されたか期限を過ぎたあと、それ以上のツール呼び出しが実行されない** ことです。キャンセルは次のチャンク、または次のアクションの境界で効きます。停止した接続で固まったエージェントは killed とマークされて放置されます。そのスレッドはデーモンなので、TMT を開いたままにすることは決してできません。
- **キューはありません。** 10 ワーカーは固い上限であり、11 番目のリクエストは待たされるのではなく、一文とともに拒否されます。TMT には統合すべきスケジューラがなく、このために 1 つ作るのは上限が必要としているものよりはるかに大きな話です。拒否は上限を名指しし、どうすればよいかを述べます。メインエージェントはそれをもとに動きます。
- **待機はメインエージェントをブロックします。** これはサスペンドではなく通常のアクションです。ライブ領域が自分のスレッドで再描画するのでインターフェースは待機中も生きており、Ctrl-C でプロンプトに戻れます。
- **ワーカーは書き込みを調整しません。** 単一の書き込みはアトミックであり、2 つのワーカーが同じファイルに触れた場合はメインエージェントにどれかが伝えられます。それ以上のロックはないので、同時に動かすワーカーには別々のファイルを割り当ててください。
- **ワーカー自身のアクションが見えることはありません。** インターフェースはそれぞれについてバーと短いラベルを表示するだけで、行っている読み取りや編集は表示しません。何をしたかはメインエージェントの要約として返ってきます。だからこそメインエージェントは、何を委譲したかを述べるよう指示されています。
- **カードには経過時間が表示されず、進捗バーの下の行には表示されます。** パネルは内容が変わったときにしか再描画されないので、そこに描かれた経過時間は古くなるか、あるいは毎ティックの再描画を強いることになります。後者はかつてカーソルをちらつかせていたものです。

### エージェントのコスト

API はステートレスなので、どのワーカーもリクエストごとに自分のシステムプロンプトを運びます。そのプロンプトはメインエージェントの 19k に対しておよそ 14k 推定トークンです。メインのプロンプトがインライン展開するファイルの内容ではなく、プロジェクトの `tree` を運ぶので、リクエストあたりおよそ 1,500 トークンを節約できます。10 のワーカーはそれぞれ写しを運ぶので、委譲は無料ではありません。トークンと引き換えに並列性を買うものであり、上限を 5 から 10 に上げたことで、1 つのセッションが一度に買える量が倍になりました。本当に切り分けられる作業を委譲してください。自分で 2 ステップでできる作業ではなく。

契約は、それを運ぶワーカーに数百トークンを追加しますが、運ばないワーカーには何も追加しません。制約のない委譲のプロンプトは、契約が存在する前のものとバイト単位で同一です。

## インターフェース

タスクの実行中は、最初の出力までは THINKING のアニメーション、そのあとは進捗バー、経過時間、リアルタイムのトークン数が表示されます。モデルのテキストはストリーミングされるにつれて 1 文字ずつ現れます。最終回答は枠で囲まれます。動作中のエージェントがあるときは、その数がメーターの横に表示されます。

**エージェントパネルは画面下部の列であって、全高のサイドバーではありません。** パネルは返信やプロンプトボックスとライブ領域を共有し、その上の会話は全幅のまま、再描画されることはありません。これはやり残しではなく意図的な制限です。スクロールバックはセッションについての TMT の唯一の永続記録であり、プログラムがウィンドウ全体を占有できるようにする 2 つのエスケープ — スクロール領域を狭めること、そして代替スクリーンバッファ — はどちらもそれを破壊します。狭められた領域から流れ出た行は保持されずに破棄されるので、上へスクロールしてもセッション自身の履歴には届かなくなってしまいます。テストがモジュールを grep して、どちらも復活しないようにしています。

45 桁未満のターミナルでは、パネルはライブ領域の全幅を占め、開いている間プロンプトボックスは描画されません。30 桁未満では開くことを拒否し、その理由を述べます。カードはトークンの行より先にアクティビティの行を落とし、折り返さずに切り詰めます。

### 作業中に入力する

プロンプトボックスはターンの間ずっと生きています。エージェントが前の質問に取り組んでいる最中でも、編集キーも含めてそのまま次の質問を書けます。

**Enter は割り込みではなく、行をキューに入れます。** その行は現在のタスクが終わり次第答えられ、入力した順に処理されます。したがってフォローアップを 3 つ積んでおいて席を外すこともできます。ボックスは何件待機しているかを表示します。

`/note` もそこに入力できます。それがこのコマンドの狙いです。進行中の作業を乱すことなく、ワークスペースから答えます。

Ctrl-C はこれまでどおり、実行中のタスクを停止します。

これには実際のターミナルが必要です。パイプやリダイレクト経由の実行は 1 行 1 タスクとして読み、ボックスは動作しません。スクリプトによる実行とテストスイートが受け取るのはこの形です。

ストリーミングを無効にするには `TMT_STREAM=0` を設定します。ストリーミングには `requests` も必要で、それがない場合 TMT はストリーミングなしで動作します。

## スラッシュコマンド

プロンプトで、**それだけしかない** `/` コマンドの行は TMT 自身が答え、モデルへ送られることはありません。名前は大文字小文字を区別しません。それ以外はすべてタスクであり、これまでどおりそのままモデルへ渡されます。`/usr/bin/python is broken` のように、単にパスで始まるだけの行も同様です。

`/plan`、`/review`、`/verify` の 3 つは、両方の読み方をされます。行に単独で書けば下記の読み取り専用レポートになり、そのあとにタスクが続けば — `/plan Build the login page` のように — その行はそのタスクであり、そのタスクに対してケイパビリティがオンになります。[ケイパビリティ](#ケイパビリティ-planreviewverify) を参照してください。

| コマンド | 内容 |
|---|---|
| `/context` | ここまでの会話: モデル、プロバイダ、ワークスペース、次のリクエストへ持ち越されるターン数、入出力の推定トークン数、追加および削除した行数、そして直近のいくつかの質問 |
| `/config` | リクエストが動作する設定: モデル、プロバイダ、エフォート、ストリーミング、JSON モード、ワークスペース、そして API キーが設定されているかどうか |
| `/clear` | 会話を忘れて仕切り直します。モデル、エフォート、ワークスペースをはじめすべての設定は保たれ、ファイルには一切触れません |
| `/effort` | 現在のエフォートレベルを表示します |
| `/effort low\|medium\|high` | 設定します |
| `/model` | 現在のモデルと、このプロバイダが提供するモデルを表示します |
| `/model <name>` | id、または Settings に表示される名前で切り替えます |
| `/note <question>` | ワークスペースについての質問に 1 つ答えます。何も変更しません |
| `/notes` | セッションをまたいで TMT がこのプロジェクトについて覚えていること: `TMT_Context/` の場所、各ファイルの内容、そしてもう存在しないパスを名指ししているノート |
| `/agents` | バックグラウンドエージェントが何をしているか |
| `/back` | セッションを保ったまま起動メニューへ抜けます。下記参照 |
| `/plan` | このタスクで TMT が進めているステップと、残っているもの |
| `/verify` | このタスクの作業を確認するために実際に実行されたもの: すべてのチェック、そのコマンド、終了コード、そして失敗したものの出力 |
| `/review` | 独立したレビューが見つけたもの: 判定、すべての指摘、そしてこのタスクのレビュー履歴 |

### `/back` — セッションを失わずにメニューへ

`/back` は、まだ動いているセッションの上に起動メニューを再表示します。何も終了されず、消去されず、キャンセルされず、待たれません。会話は会話のまま、プランはプランのまま、バックグラウンドエージェントはその裏で作業を続けます。これができるまで、Settings と Help には終了しないと到達できませんでした。

開くメニューは起動メニューと 3 点だけ異なります。

```
> Resume    Go back to the session, which is still here
  Settings  Provider, API key and the model TMT runs on
  Help      What TMT does, and how to drive it
  Exit      Close TMT and end the session
```

- **Start は Resume と表示されます。** そのラベルはカーソルが他の場所にあるときでもグラデーションの中を動き続けます。それが、あなたのセッションがまだそこにあると画面が語っている姿です。
- **Exit はセッションを終了すると述べます。** 語は起動時と同じですが、結果は同じではありません。
- **何かが動いている間、Settings は提示されません。** その行はグレーアウトでも無効化でもなく、消えます。そしてリストの上の行が、何が動いていてどうすればよいかを述べます。

```
Settings are not offered while work is running: 2 agents. Wait for it to
finish, then /back again.
```

プロバイダ、キー、モデルはいずれもリクエストの実行中に読まれるので、動いているエージェントの下でそれらを変えれば、すでに始まっているリクエストの途中に誰も頼んでいない変更が持ち込まれます。作業が終われば、メニューを閉じることなく次のフレームでその行が戻ってきます。

Resume を選ぶと画面がクリアされ、ヘッダーが再描画され、すべてを残したままプロンプトへ戻ります。

**エフォート** は、1 つのタスクに TMT がどれだけの労力を費やすかです。変えるのは 2 つのことだけで、どちらもすべてのプロバイダで実在するものです。応答の長さをどれだけ要求するか、そして 1 つの質問にエージェントループを何巡使ってよいかです。

| レベル | 要求する応答の長さ | タスクあたりの巡回数 |
|---|---|---|
| `low` | 4096 トークン | 12 |
| `medium`（既定） | 4096 トークン | 35 |
| `high` | 8192 トークン | 60 |

応答の長さは、どのレベルでも 4096 を下回りません。応答はすべて 1 つの JSON オブジェクトであり、重要なものはその中にファイルを丸ごと抱えています。したがって上限を小さくしてもモデルが簡潔になるわけではなく、オブジェクトが文字列の途中で切れて書き込みが行われなくなるだけです。この設定はモデルの選択と同じく、インストール先の `.tmt_effort` に保存され、再起動しても残ります。

**補完。** 実際のターミナルでは、`/` を入力すると入力中の行の下に 10 個のコマンドが一覧表示され、入力するにつれて絞り込まれます。`/mo` なら `/model` だけが残ります。Tab は候補が一致するところまで補完します。`/mo` は `/model ` になり、`/co` は `/con` になります。`/context` と `/config` の両方がまだ該当するからです。パイプやリダイレクト経由の実行は行全体を読み、一覧は描画しません。コマンド自体はそこでも機能します。

**秘密。** `/context` も `/config` も、キー、トークン、パスワードを表示することは決してありません。`/config` はキーが設定されているかどうかだけを述べ、それ以外には何も述べません。値も、そのマスクされた形も表示しません。

## 設定

| 変数 | 既定値 |
|---|---|
| `OPENROUTER_API_KEY` | `.tmt_key` から |
| `OPENROUTER_MODEL` | `minimax/minimax-m3:free` |
| `TMT_STREAM` | `1` |
| エフォート | `medium`、`.tmt_effort` から。`/effort` で設定します |
| プロジェクトコンテキスト | オン、`.tmt_context` から。Settings で設定します。[プロジェクトコンテキスト](#プロジェクトコンテキスト-tmt_context) を参照 |

| `TMT_GIT_EMAIL` | なし — TMT がコミットする前に必須です |
| `TMT_GIT_ROOT` | プロジェクトディレクトリを含むリポジトリ |
| `PATH` 引数、または `--dir` | カレントディレクトリ |

## `tmtcode` が見つからない場合

コマンドはインストールされていますが、pip がそれを置いたディレクトリが PATH 上にありません。そのディレクトリは次のようにして分かります。

```bash
python -c "import sysconfig; print(sysconfig.get_path('scripts'))"
```

Windows では `Scripts`、macOS と Linux では `bin` で、インストール先の Python または仮想環境の下にあります。それを PATH に追加するか、次のいずれかの代替手段を使ってください。どちらも同じ引数を取り、同じ方法でプロジェクトディレクトリを選びます。

```bash
python -m TMT                     # インストール済みなら、どこからでも
python /path/to/TMT/TMT.py        # クローンから直接、どこからでも
```

仮想環境にインストールした場合、`tmtcode` はその環境が有効な間だけ存在します。

`tmtcode --help` は引数を表示します。

## テスト

```bash
python run_tests.py
```

スイートは `testing/` にあり、`testing/unit/` と `testing/integration/` に分かれています。ランナーはルートに置かれたまま両方を検出します。どちらに何が属するかは [testing/README.md](../testing/README.md) を参照してください。

1581 個のテストがあります。そのうち 8 個は `.tmt_key` から API キーを読むので、キーが未設定の新しいクローンではその 8 個が失敗し、残りは成功します。

所要時間はかつての 2 分ではなく、およそ 15 分です。そのほとんどは `test_agent_review.py` の 1 つのテストで、3 つの本物のレビュアーエージェントを起動し、それぞれについて実際の API 往復を待ちます。このテストはまた、ここで唯一決定的でないテストでもあります。失敗するレビューを確定させたうえで偽のオブジェクトを送り、そのどれもそれを合格に変えられないことを示すのですが、`review` を実行するということはレビューが実行されるということなので、あなたのワーキングツリーを気に入った実際のレビュアーが正当な経路でそれを通してしまい、アサーションが発火します。信じる前に、もう一度実行してください。
