## "Too Many Tools" —— 一个命令行编码智能体。它在沙箱化的工作区中编辑文件，运行十余种语言的代码，并在任意仓库上自动提交和推送。

>**需要 Python 3.8+。**

## 命令是 `tmtcode`

安装会在你的 PATH 上放入一条命令：

```bash
tmtcode
```

可以在系统上的任意目录中运行它。**你运行它时所在的目录，就是 TMT 要处理的项目。**

```bash
cd ~/Projects/MyWebsite && tmtcode      # TMT 处理 ~/Projects/MyWebsite
cd ~/Documents/MyProject && tmtcode     # TMT 处理 ~/Documents/MyProject
```

TMT 只需安装一次，放在哪里都行。你永远不需要把它复制进某个项目，项目里也永远不需要有 TMT 的文件。

## 安装

```bash
git clone https://github.com/lllons/TMT.git
cd TMT
pip install -e .                 # 把 `tmtcode` 放到 PATH 上
pip install -e ".[live]"         # 可选：加入 requests 和 rich，用于流式输出和彩色显示
```

智能体本身只需要标准库；`requests` 和 `rich` 仅增加实时流式输出和颜色，没有它们 TMT 也会自动降级运行。

安装之后，把克隆下来的目录留在原地，然后在你实际工作的地方运行 `tmtcode`。那份克隆是 TMT 的家，不是你的项目。

不安装也可以，克隆下来的代码可以直接运行，而且可以从任何地方运行：

```bash
python /path/to/TMT/TMT.py                    # 当前目录就是项目
python /path/to/TMT/TMT.py ~/Projects/MyWebsite
```

Windows：`py`。macOS/Linux：`python3`。

## 两个目录

TMT 严格区分它自己的安装目录和你的项目目录。它们是两样不同的东西，而且理应保持分离。

| | 那里存放什么 | 它在哪里 |
|---|---|---|
| **安装目录** | TMT 自己的源码、你保存的 API key、TMT 的 git 共同作者身份、它的日志 | 你克隆到的任何地方 —— `~/tools/TMT`、`C:\Coding\TMT` —— 设定一次，之后再不移动 |
| **项目目录**（工作区） | TMT 读取、编辑、运行和提交的文件 | 你运行 `tmtcode` 的地方 |

只有项目目录会被修改。无论你站在哪个项目里，TMT 自己的文件都留在安装目录中，所以它在任何地方都是同一个智能体 —— 同一把 key，同一个共同作者地址。

再直白地说一遍：**你不需要把 TMT 复制进某个项目才能在那个项目上使用它。** 一次克隆、一次安装，然后 `cd` 到任意项目并输入 `tmtcode`。

## 选择项目目录

| 命令 | 项目目录 |
|---|---|
| `tmtcode` | 当前目录 |
| `tmtcode ../other-repo` | 相对当前目录解析，然后转为绝对路径 |
| `tmtcode /abs/path/to/project` | 该路径 |
| `tmtcode --dir PATH` | 与位置参数 `PATH` 完全相同，保留是为了兼容既有用法 |

相对路径会相对于你运行命令时所在的目录解析，然后转为绝对路径。同时给出位置参数 `PATH` 和一个指向不同目录的 `--dir` 是错误，TMT 会直接退出而不启动。

TMT 严格使用它收到的那个目录。它不会向上查找项目根目录：在 `MyWebsite/src` 中运行它，工作区就是 `MyWebsite/src`。

解析后的路径会在启动时打印出来，因此在错误位置启动会一目了然：

```
Workspace: C:\Projects\my-repo
```

该目录之外的一切都不可触碰 —— 任何爬出工作区的路径都会被拒绝，而不是被跟随。

## 权限与限制

- TMT 可以在项目目录内的任何位置创建、覆盖和删除文件，而且除非该目录是一个 git 仓库，否则它在那里所做的一切都不可恢复。它需要对该目录拥有普通的读写权限。
- 安装目录必须可写：`.tmt_key` 和 `logs/` 会写在那里。`.tmt_git` 和 `.tmt_git.local` 只从那里读取。
- 目录是被选定的，而不是被创建的。TMT 会拒绝不存在的路径、文件、文件系统根目录以及你的主目录。
- 如果目录中已经有文件，且不在某个 git 工作树内，TMT 会描述它即将指向的对象，并在开始前询问你。git 仓库自带撤销能力，所以它会直接开始而不询问。
- TMT 从不运行 shell 命令。它只通过 `run_file` 运行代码，并且只启动下文列出的两个应用程序。
- 推送使用你已有的 git 凭据。TMT 不存储任何凭据，也没有实现任何登录。

## 启动画面

每次运行 `tmtcode` 都会打开同一个画面：填满终端的 TMT 字标，下面是

```
                              Press Enter to Continue
```

这一行在等待时会脉动 —— 在彩色终端上渐变会沿着它扫过，在没有颜色的终端上是缓慢的字重脉动，而在无法使用转义序列的地方则什么都没有，因为在这里颜色同样从来不是信息本身。Enter 是唯一能继续的键；Ctrl-C 关闭 TMT。其他一切都会被忽略，所以在画面稳定之前输入的第一条任务不会误触发任何东西。

**启动画面始终出现。** 它不是一项设置，也没有什么可以关掉。**属于**设置的，是按下 Enter 之后发生的事。

### 按下 Enter 之后：更新检查

当 `Auto Update on Launch` **开启**（默认）时，TMT 会查看它自己的 git 检出，判断是否存在更新版本，并在同一画面上说明：

```
                              Searching for updates...
```

然后是以下之一

```
                                    Up to date.            nothing was pulled, nothing restarted
                          Update complete. Restarting...   a fast-forward was applied
                            Continuing without updating.   an update could not be taken safely
                Update check failed. Continuing without update.
```

当该设置**关闭**时，上述过程都不会发生，而且 TMT 不会假装发生过 —— 对于从未进行过的搜索，不会显示任何 "searching" 行。它会直接继续。

在那之后，TMT 会完全照旧继续：如果本次安装尚未配置，则进入 API key 设置流程，否则进入普通的启动画面。

### TMT 何时会、何时不会自我更新

只有在更新明确安全时它才更新，而且它从不触碰你的工作成果。

| 它发现了什么 | 它会做什么 |
|---|---|
| 已经是最新 | 什么都不做。不拉取，不重启 |
| 远端领先、工作树干净、可以快进 | 快进，然后重启 |
| **有未提交的本地改动** | 拒绝，并说明原因。你的改动不受影响 |
| **分支已分叉** —— 本地和远端都有新提交 | 拒绝。本地提交永远不会被丢弃 |
| 未配置上游，或处于分离 HEAD 状态 | 说明它无法判断，然后继续 |
| 根本不是 git 检出 | 继续 |
| 没有网络、没有 git、远端有问题、合并失败 | 报告失败并继续 |

它在你已经检出的分支上工作，从不创建、切换或强制某个分支。它只使用 `git fetch` 和 `git merge --ff-only`，别无其他：**它从不运行 `git reset --hard`、`git clean`、强制检出或普通的 `git pull`** —— pull 可能触发合并，而启动期间的合并正是绝不能发生的事。有一个测试会读取更新器自身的源码，并断言这些命令不出现在其中。

TMT 在没有网络的情况下依然可用。一次失败的更新检查只是启动画面上的一行字，仅此而已。

### 重启

一次成功的更新会用一个全新的进程替换当前进程，这样新代码才真正生效，而不是旧模块继续留在内存里。你的命令行会被保留 —— `tmtcode --dir ~/project` 会以 `tmtcode --dir ~/project` 的形式回来。

随后你会再次看到启动画面，这是预期之中的：启动画面是每次启动的一部分。重启后的进程会发现自己已是最新，然后继续。**它不会循环** —— 每次启动最多发生一次自动重启，而且第二个进程知道自己是第二个。

### 关闭它

Settings → `Auto Update on Launch`，按 Enter 切换：

```
  AI Provider            Which service answers a request
  API Key                The credential that service is given
  Model                  Which model TMT runs on
> Auto Update on Launch  Check for a newer TMT after the launch screen  ON
  Back                   Return to the menu
```

它保存在安装目录中的 `.tmt_autoupdate` 里，与模型和 effort 设置放在一起，因此它属于这次安装而不属于某个项目，并且能在重启后保留。文件缺失表示开启；无法读取的文件，或被改成无意义内容的文件，同样表示开启，而不是在启动时报错。

**关闭它并不会关闭启动画面。** 无论如何都会显示启动画面。

## 首次启动

首次启动会索取一个 [OpenRouter key](https://openrouter.ai/keys) 并把它保存到安装目录中的 `.tmt_key`（已被 git 忽略）。设置 `OPENROUTER_API_KEY` 可以跳过这一步。它是按安装索取一次，而不是按项目索取一次。

在 `Task>` 提示符处输入任务。`quit` 或 `exit` 退出。Ctrl-C 取消当前任务而不关闭 TMT。

小于 8 KB 的文件会自动展示给模型，直到达到固定的文件数量和总大小上限；列表在提前停止时会说明这一点。更大的文件按需读取。

## 你可以要求什么

用平实的自然语言。TMT 会自己挑选动作。

```
Task> write a python script that fetches a URL and prints the status code
Task> what does report.py do?
Task> find every TODO in src and list them
Task> change the timeout in net.py from 5 to 30 seconds
Task> run hello.py
Task> open notes.txt in notepad
Task> commit the changes and push to main
```

## 与你对话：`send_message` 和 `end_conversation`

TMT 只有两种把文字放到你屏幕上的方式，而它们之间的全部区别在于任务之后是否继续。

| 动作 | 向你展示文字 | 结束任务 |
|---|---|---|
| `send_message` | 是 | **否** —— 控制权每次都会回到智能体手中 |
| `end_conversation` | 是 | **是** —— 而且它是唯一能结束任务的动作 |

**`send_message` 用来在过程中说话。**"我先读一下解析器"、"测试通过了，接下来是文档"、"这个文件比我预想的大"。它会被打印到会话里，你可以往回滚动查看，然后 TMT 从原本的位置继续。在一次任务中它可以被使用任意多次，只要用得值得；没有上限，而且它没有任何一点是终局性的。

**`end_conversation` 就是结尾。** 它的消息是你最后看到的那份总结，这也是为什么智能体被告知：没有写在那里的工作，等于没有发生过。没有第二种停下来的方式：没有单独的 `done`，也没有什么标志能悄悄把一条消息变成最后一条。TMT 要么用这个动作结束一次任务，要么就没有结束它。

**想要结束，和被允许结束，是两回事。** `end_conversation` 正是完成关卡所拦住的对象，你为该提示词开启的任何能力都可以拒绝它：还有步骤未完成的计划、尚未通过的评审、尚未运行或发现了失败检查的验证。拒绝不是错误，也不会结束本轮 —— TMT 会收到原因，回去继续工作，而答案仍然没有说出口。参见 [能力](#能力planreviewverify)。

后台智能体在任何有意义的层面上都没有这两条通道：没有人在读它们，所以一条消息会消耗一步却传达不到任何人，而它们的结尾是给主智能体的一份报告。参见 [后台智能体](#后台智能体)。

## 能力：`/plan`、`/review`、`/verify`

TMT 能做的事情里，有三件不属于普通的工具工作。写下一份计划并被它约束、让第二个智能体审计 diff、运行这个仓库自己的检查，每一件都要额外花掉一整次模型运行，都会在屏幕上占一列，而且都可以拒绝 TMT 自己的最终答案。它们是你的花销，所以除非你提出要求，否则它们都是关闭的，而提出要求的方式就是在提示词里写下对应命令。

| 命令 | 启用 |
|---|---|
| `/plan` | 计划工作流 —— TMT 写下步骤，并且在它们完成之前无法结束 |
| `/review` | 独立代码评审 —— 一个单独的只读智能体审计这份工作 |
| `/verify` | 智能验证 —— 真正运行这个仓库实际拥有的检查 |

```
Task> build me an authentication system
        nothing gated. Ordinary tools, ordinary answer.

Task> build me an authentication system /plan
        plans the work and is held to the plan. No review, no verification.

Task> fix this implementation /review
        an independent reviewer audits it before the answer goes out.

Task> add the endpoint /plan /verify /review
        the whole pipeline: plan, implement, verify, review, fix, answer.
```

**斜杠就是全部的分界线，光有 `verify` 这个词是不够的。**"verify this code"、"please verify this"、"verified" 和 "verification" 都是人们在要求普通工作时会说的话，它们没有一个会打开这套引擎。只有 `/verify` 会。`plan` 和 `review` 也一样："review my code please" 是在征求意见，`/review` 则是在要求那个受关卡约束、有轮次上限的独立评审者。

以某个命令开头的更长单词同样不算。`/planning`、`/planner`、`/plan123`、`/reviewing` 和 `/verification` 都是普通文本，路径中的命令也是 —— `src/review` 和 `abc/verify` 是路径，不是命令。

其余规则都是你能猜到的那些：

- **在提示词的任何位置。** 开头、中间、结尾，或者粘贴块里单独成行都可以。`/plan Build it`、`Build it /plan` 和 `Build the /plan feature` 是同一个请求。
- **可以出现任意多次。** `/plan ... /plan` 只启用一次计划。世界上没有两份计划这回事。
- **大小写随意。** `/PLAN` 有效，而且在你的屏幕上仍然显示为 `/PLAN` —— TMT 只为你的文本添加样式，从不改写它。
- **彼此独立。** `/plan` 不会打开评审或验证，那两个也都不会打开其他任何一个。工作流由你选择。
- **一次只对一个提示词生效。** 一项能力只对提出它的那次请求授权。下一个问题从零开始，除非它也提出要求。

**只有你能打开它们。** TMT 不能，后台智能体不能，评审者不能，它读到的某个文件也不能。如果一个模型认为任务大到该做计划，于是把 `/plan` 写进自己的推理里并调用该动作，它会被运行时拒绝 —— 授权只从你输入的那一行读取，别无来源。这一点被强制执行了两次：未授权的动作词完全不会出现在提示词里，而如果仍有人试图使用，调度器会再次拒绝它。

**它们会在你输入时被高亮。** 输入框中一条有效命令上会带有红 → 橙 → 绿的渐变，这样你在按下 Enter 之前就能看到自己打开了什么，也能在打错时看到它消失。只有完全匹配的命令会被着色：`verify` 保持普通样式，`/verification` 也保持普通样式。在没有颜色的终端上，命令会改用粗体和下划线突出显示；而在管道运行中完全没有样式 —— 那一行仍然读作 `/plan`，也就是命令本身被完整写了出来。

在本轮运行期间，你所授权的内容会列在右侧列的顶部：

```
                                                        CAPABILITIES 2
                                                        ● /plan
                                                        ● /verify

                                                        PLAN 2/5
```

**`/plan`、`/review` 和 `/verify` 单独出现时，仍然是它们一直以来的那些报告** —— 参见 [斜杠命令](#斜杠命令)。一行里只有命令，展示的是 TMT 正在做什么；一行里带着任务，则是为那个任务授权对应能力。

### 文件

| 动作 | 用途 |
|---|---|
| `write_file` / `write_files` | 创建一个文件，或一次创建多个 |
| `patch_file` | 查找并替换 —— 编辑时的默认方式 |
| `replace_lines` | 替换一个精确的行区间 |
| `append_file` | 追加到文件末尾 |
| `read_file` / `read_lines` | 读取整个文件，或一个行区间 |
| `search_files` | 普通或正则搜索，可选限定到某个文件夹 |
| `copy_file` / `rename_file` / `delete_file` | 移动、重命名、删除 |
| `create_folder` / `delete_folder` | 文件夹（递归删除需显式选择） |
| `list_files` | 列出工作区 |

路径按相对于项目目录来解释，任何解析后落在其外的路径都会被拒绝。只有那个目录会被列出、读取或写入。

编辑已有文件用的是 `patch_file` 而不是整体重写，因此未被触及的行保持原样。Python 文件在写入前会做语法检查；有问题的编辑会被拒绝而不是保存下来。

### 计划

**在你的提示词里用 `/plan` 提出要求。** 没有这条命令，TMT 不会写计划，这里的任何内容也不会拦住答案。参见 [能力](#能力planreviewverify)。

有了 `/plan`，对于任何实质性的工作 —— 添加一项功能、修复一个跨仓库的 bug、重构一个子系统、更新整个项目的文档 —— TMT 会在动手之前写下计划，并当着你的面逐步推进。它在工作期间显示为实时区域右侧的一列，并在完成后留在那里，与下一个提示符并排。

```
                                                        PLAN 2/5
                                                        ─────────────────────────
                                                        S1 ✓ Inspect repository
 09:14 · OpenRouter · MiniMax M3                        S2 ✓ Find and…erminology
 ───────────────────────────────────────────────────    S3 ● Update documentation
 > Describe your next task                              S4 ○ Run tests and verify
 ───────────────────────────────────────────────────    S5 ○ Explain changes
```

| 标记 | 状态 | 颜色 | 含义 |
|---|---|---|---|
| `✓` | completed | 绿色 | 该步骤的工作确实已经完成 |
| `●` | in progress | 橙色 | 当前正在进行的那一个步骤 |
| `○` | pending | 红色 | 尚未开始 |
| `!` | blocked | 琥珀色 | 它无法推进，而且仍然算作未完成 |

同一时间恰好只有一个步骤在进行中。完成一个步骤会自动把下一个提升上来。颜色是确认，从来不是信息本身：每种状态都同时带有一个标记，而且在无法绘制其余字符的终端上，整列会降级为 `+ > - !` 和 ASCII 分隔线。

**计划是一份契约，不是进度条。** 在还有步骤未完成时，TMT 不被允许结束一次任务。带着遗留工作发出的最终答案根本不会展示给你 —— 运行时会拒绝它，把仍然欠着的步骤列表交回给模型，本轮继续。这一点由程序强制执行，而不是在提示词里请求，所以一个模型自认为完成了，并不等于它真的完成了：

```
Task> add the feature
 · Planning the work in two steps.
 ◆ Plan created with 2 steps.
 ▲ Plan not finished - 2 steps outstanding, next is S1 Implement the feature. Continuing.
 · The feature is in; running the tests next.
 ◆ S1 (Implement the feature) in_progress -> completed.
 · Suite is green.
 ◆ S2 (Run the tests) in_progress -> completed.
 ┌──────────────────────────────────────────────────────────────┐
 │ Added the feature and the suite is green: 12 tests, 0 failures.│
 └──────────────────────────────────────────────────────────────┘
```

当工作实际情况与预期不同时，计划随时可以修改 —— 步骤可以重命名、增加、删除，整份计划也可以替换。有两件事不会发生。已完成的步骤永远不会被重新打开：完成了就是完成了，而形状不对的计划会被整体替换，而不是逐步回退。以及，已经有工作记在名下的计划不能被丢弃 —— 那曾是绕过关卡的唯一路径，所以一旦有任何步骤被标为完成，清空就会被拒绝。完成它和重塑它都在屏幕上可见；悄悄丢弃它则不会。

**并不是所有事情都需要计划。**"这个函数是做什么的？"只需要一个答案，为它写计划只会在屏幕上制造噪音，并给 TMT 自己的回复加上一道关卡。计划是给有阶段的工作用的。

**计划属于任务，不属于会话。** 你提出下一个问题的那一刻它就被退役了，所以一份未完成的计划永远不会拦住一个不相关问题的答案。什么都不会写入磁盘。后台智能体既看不到也无法修改它 —— 它是主智能体与你之间的契约，而一个工作者去完成某个步骤，会让 TMT 基于它仅仅声称过的工作而收尾。

**在窄于 45 列的终端上**这一列不会绘制 —— 输入框更需要那点空间 —— 而 `/plan` 在任何宽度下都会以普通文本打印同样的内容。

### 理解一个仓库

八个动作，用来在不通读全部代码的情况下摸清一个代码库。每一个回答一个问题，而 TMT 被要求选择其中范围最窄且合适的那一个。

| 动作 | 用途 | 什么时候用它 |
|---|---|---|
| `tree` | 目录、文件、大小、层级。不读取任何内容 | 你需要项目的整体形状 |
| `find_text` | 一次性跨每个文件的精确、区分大小写的搜索。查询串可以跨多行 | 你确切知道自己要找的字符 |
| `find_symbol` | 某个函数、类、方法、常量或类型在哪里被*定义* | 你要的是定义，不是提及 |
| `code_map` | 什么定义了它、什么导入了它、它导入了什么、它在哪里被引用 | 你需要知道一处改动会影响什么 |
| `replace_across` | 在多个文件中做完全相同的编辑 | 重命名整个项目都在用的东西 |
| `related_tests` | 读取 git diff，指出值得运行的测试 | 你只改了一处，又不想全量跑测试 |
| `remember` / `recall` | 关于这个项目的持久笔记，跨会话保留 | 某件事花了你不少时间才弄明白 |

```
Task> show me the project structure
Task> find every place that calls self.workspace_root
Task> where is calculate_total defined?
Task> what imports agent_file_ops?
Task> rename old_function_name to new_function_name across src
Task> which tests should I run for what I just changed?
```

`find_text` 是精确且区分大小写的；`search_files` 则是宽松、不区分大小写的那个。两者并存，是因为它们回答的是不同的问题。

**`replace_across` 默认只做预览。** 它会报告它*将会*改动多少个文件和多少处出现，并且什么都不写。再次发送同一动作并带上 `"apply": true` 才会真正执行。行尾和编码会被保留，二进制文件会被跳过，而会让某个 Python 文件无法解析的替换会被拒绝而不是写入。

**事实和猜测被区别标注。** Python 符号是通过解析文件找到的，所以那些答案是精确的；其他语言按词法匹配，并且会说明这一点。`related_tests` 会把 diff 所能证明的和它只是在猜的分开。没有任何东西会把启发式结果当作测量结果来呈现。

**项目记忆**存放在 TMT 自己的设置旁边，按项目建立索引，永远不在你的仓库里 —— 与 TMT 其他所有状态遵循同一条规则。笔记在写入前会被扫描，任何形似 key、token 或密码的内容都会被拒绝。

### 运行代码

`run_file` 执行代码并返回输出。支持 Python、JavaScript、TypeScript、Ruby、PHP、Lua、Perl、R、Go、C、C++、Java。10 秒超时。工具链必须在你的 PATH 上。代码以项目目录作为工作目录运行。

### 应用程序

`open_app` 启动记事本，或启动资源管理器并选中某个文件。仅此而已 —— TMT 从不运行 shell 命令。

## Git

TMT 在包含项目目录的那个仓库中提交 —— 而不是在 TMT 自己的仓库中。它所做的每一次提交，你都仍然是作者和提交者；TMT 通过一个 `Co-authored-by` 尾注与你并列署名。

```
Task> commit this                        commits, does not push
Task> commit these changes and push       commits and pushes
Task> push this to main                   targets main
Task> fix the bug                         edits only, no commit, no push
```

提交和推送是分开的。只有当你自己的话语要求推送时，TMT 才会推送 —— "fix the bug" 从不触发推送，完成一次编辑同样不会。

动作：`git_status`、`git_diff`、`git_identity`、`git_commit`、`git_push`。

它只暂存自己改动过的文件，所以你无关的工作仍然保持未提交状态。它从不创建分支，从不臆造远端，也从不强制推送。如果推送失败，提交留在本地，而你会拿到真实的错误信息。

### TMT 共同署名

TMT 不以你的身份提交，也不代替你提交。仓库自身的 git 身份才是作者和提交者。TMT 只往消息里加一条尾注，别无其他。一次提交，你们两个都被记上。

一次由 TMT 完成的提交，git 报告出来是这样的：

```
$ git log -1 --format=fuller
commit f1977e70a471011bf9b5ab643aecdf5e18a8e8fa
Author:     Liam <liam@example.com>
AuthorDate: Sat Aug 29 13:10:01 2026 +1200
Commit:     Liam <liam@example.com>
CommitDate: Sat Aug 29 13:10:01 2026 +1200

    Add a greeting file

    Co-authored-by: TMT code <TMT.tmt.code@gmail.com>
```

它是一条 git 尾注，而不是一行碰巧带冒号的散文，因此 git 自己就能把它取回来：

```
$ git log -1 --format=%(trailers:key=Co-authored-by)
Co-authored-by: TMT code <TMT.tmt.code@gmail.com>
```

这在实践中意味着：

- 作者和提交者就是仓库的 git 配置所声明的那个人。TMT 从不把自己放进这两个字段中的任何一个，也从不写入你的 git config，无论是全局的还是单个仓库的。
- 如果你没有设置 git 身份，git 会拒绝这次提交。TMT 会报告这一点，告诉你自己去设置 `user.name` 和 `user.email`，而不会顶替上去当作者。什么都不会被提交。
- TMT 只给它自己创建的提交加尾注。你自己运行的 `git commit` 不受影响。
- 已经署名了 TMT 地址的消息只会得到一条尾注，而不是两条。匹配基于地址，所以同一个地址换个显示名，仍然算作已经署名。
- 已有的尾注会被保留。别人的 `Co-authored-by:` 会被保留，TMT 会加在它旁边；`Signed-off-by:` 块会被并入其中，而不是被推到新的段落里。
- 历史永远不会被重写。如果最终的提交出于某种原因缺少那条尾注，TMT 会报告，并把提交原样留下，而不是去修补它。
- 如果没有配置 TMT 地址，或者随附的占位地址仍然原样保留，TMT 会拒绝提交并且不暂存任何东西。

GitHub 上的署名归属是另一个问题，而且 TMT 无法决定答案：

- TMT 决定提交的元数据 —— 那条尾注，也仅仅是那条尾注。
- GitHub 决定是否为共同作者署名。它会把尾注中的地址与某个账户上已验证的地址进行匹配。没有在任何账户上验证过的地址不会被记到任何人头上，而只有显示名是不起作用的。
- 即便地址确实匹配，GitHub 的贡献者和个人资料数据也可能滞后。一次推送不一定会立刻改变贡献图。
- 获得署名和被允许推送不是一回事。身份认证是独立的，而且仍然归你。

### 共同作者身份

```
TMT_GIT_NAME=TMT code
TMT_GIT_EMAIL=someone@example.com
```

TMT 被署名时所用的地址。它绝不会作为作者被写进提交里。读取顺序为：`TMT_GIT_*` 环境变量，然后是 `.tmt_git.local`（被 git 忽略，按机器区分），然后是 `.tmt_git`（被跟踪，随项目分发）。名字默认为 `TMT code`。邮箱没有默认值，而且绝不会取自你的 git config —— 你的 git config 提供的是作者，不是共同作者。

这两个文件都位于安装目录中，所以无论你把 TMT 指向哪个项目，它都以同一个地址被署名。

`.tmt_git` 被跟踪是有意为之：提交邮箱是公开的元数据，不是凭据，因此每份克隆都能在无需任何配置的情况下得到同一个 TMT 共同作者。它只包含一个名字和一个地址，别无其他。不要在它里面、也不要在 `.tmt_git.local` 里放任何 token、密码或 key。

运行 `git_identity` 可以查看是哪个来源胜出、查询了哪些文件，以及该地址是否可用。

### 设置 GitHub 署名归属

被跟踪的 `.tmt_git` 中写的是代表 TMT 的那个 GitHub 账户上已验证的地址，因此全新克隆无需任何设置就能正确署名。如果那个邮箱是占位值，TMT 会拒绝提交，而不是署上一个谁也对应不上的共同作者。若要改为署名你自己的账户：

1. 为 TMT 创建一个 GitHub 账户。
2. 在上面添加并验证一个地址。
3. 把那个地址写进 `.tmt_git.local`，或者写进 `.tmt_git` 并提交一次。

四件互不相同的事，其中只有一件由 TMT 决定：

- **作者身份** —— 写进提交里的作者和提交者。是你。TMT 只会读回来用于报告，从不设置或修改它，你的 `user.name` 和 `user.email` 也不会被改动，无论全局还是单个仓库。
- **共同作者署名** —— 那条 `Co-authored-by` 尾注。这是提交中唯一由 TMT 决定的部分。
- **GitHub 署名归属** —— GitHub 把那条尾注中的地址与某个已验证账户相匹配。这不在 TMT 掌控之内，而且只有显示名是不起作用的。
- **身份认证** —— 谁可以推送。仍然归你：你的 SSH key、凭据管理器或 `gh` 登录。TMT 不存储任何凭据，也没有实现任何登录。

## 验证

**在你的提示词里用 `/verify` 提出要求。** 没有这条命令，这里的一切都不会发生，也没有任何东西会拦住答案；只写 `verify` 这个词是不够的。参见 [能力](#能力planreviewverify)。

有了 `/verify`，在 TMT 被允许宣称某项工作已经完成之前，它会运行这个仓库实际拥有的检查，而且在这些检查通过之前运行时不会让它作答。

关键在于证据与观点之间的区别：

> "This should work" 不是验证。`43 passed, 0 failed` 才是。

TMT 不会去问模型代码是否可用。它读取仓库，弄清楚这个项目自己是用什么来测试、检查和构建的，读取 diff 以了解改动了什么，为*那次*改动挑选值得运行的检查，运行它们，然后报告退出码。模型写下的任何内容都无法改变那个结果 —— 任何动作上都没有能设置状态的字段，而一项检查只有在进程以零退出时才算通过，除此之外任何时候都不算。

### 它决定运行什么

**它优先使用你的命令，而不是它自己的猜测。** 顺序如下：

1. 这个仓库按名字定义的命令 —— 一个 `package.json` 脚本、一个 `Makefile` 目标、根目录下的一个 `run_tests.py`
2. 这个仓库配置过的工具 —— `[tool.ruff]`、`[tool.mypy]`、`tsconfig.json`
3. 项目的包管理器 —— `npm`、`pnpm`、`yarn`、`bun`、`uv`、`poetry`
4. 该生态的标准命令 —— `cargo test`、`go vet`、`pytest`
5. 一个猜测，并且被标注为猜测

如果你的 `package.json` 里写着 `"test": "vitest run"`，TMT 就运行 `npm run test`。它不会自作主张地认为 node 项目都用 jest。如果你的仓库里有 `run_tests.py`，那就是测试命令 —— 即便 `pytest` 也能跑，因为运行一个与你实际所用不同的东西，然后把它称作你的验证，即使通过了也仍然是错的。

CI 配置只被当作你真正在用哪些工具的*证据*来阅读，而绝不作为命令的来源。TMT 运行的任何东西都不是从项目文件里取出来的字符串：被取出的是一个名字，命令则由围绕它的一张固定表格构建而成。这条路径上任何地方都没有 shell。

**它先跑便宜的检查，再跑昂贵的**，并在第一个失败处停下：

| 层级 | 内容 |
|---|---|
| 1 | 改动部分的语法和格式 |
| 2 | lint、类型检查、编译器检查 |
| 3 | 指名涉及你改动内容的测试 |
| 4 | 它们周边的测试 |
| 5 | 项目的构建 |
| 6 | 整个测试套件 |

一旦类型检查已经失败，集成测试套件要花的那十分钟，就是花在测量一棵已知有问题的代码树上的十分钟。失败之后的一切都会被报告为已跳过，并以此作为原因 —— 这样*没有*被检查的东西是可见的，而不是靠推断。

**当改动风险更高时，它会挖得更深。** 身份认证、数据迁移、数据库 schema、API 契约、并发、文件系统边界、shell 执行、依赖或构建配置 —— 或者干脆就是一次改了很多文件 —— 都会走完整测试套件。只改文档的变更只做静态检查，不跑测试。

### 四种结果，彼此分明

| | 含义 |
|---|---|
| **PASSED** | 命令运行了并以 0 退出。这是唯一一种证据 |
| **FAILED** | 命令运行了并以非零退出。有问题，而输出说明了是什么问题 |
| **SKIPPED** | 它没有被运行 —— 工具没安装，或者之前某项检查已经失败 |
| **ERROR** | 它无法运行或没有跑完。什么都不知道，而且这*不是*你代码的失败 |

它们绝不会被压缩成一个布尔值。超时不是失败；缺少 linter 不是通过了 lint。TMT 不会为了补上其中某个缺口而安装任何东西 —— 缺失的依赖会被报告，绝不会被悄悄修好。

### 它看起来是什么样

```
VERIFY 1/3
✓ Syntax          passed
✓ Lint            passed
✗ Targeted tests  2 failed, 41 passed
– Full suite      not run: Targeted tests did not pass
```

`/verify` 会打印整次运行，包括任何失败项的输出。

### 它挑选哪些测试

对于测试命令可以接受路径的项目，TMT 会算出改动波及了哪些测试，并优先运行它们。当一个测试文件有证据支撑时它算作**targeted** —— 它指名了某个被改动的模块、导入了某个被改动的符号，或者位于项目自身命名约定所指定的位置 —— 而当它只是可达性猜测时算作**related**。两者被分开对待、分层对待，因为把猜测当作测量来呈现，比完全不做筛选还要糟糕。

当项目的测试命令*无法*被收窄到路径时 —— 比如 `npm test`，或者一个跑全部内容的 `run_tests.py` —— TMT 会说明这一点，并把整个套件作为测试证据来运行。它不会跑全部然后把它标成 targeted。

### 它什么时候发生

当运行时看到实质性工作的**两半**时，验证是必需的：一份三步或更多的计划，以及至少一个确实被写入的文件 —— 与决定是否评审所依据的是同样两个事实，都是观察到的而不是声称的。一个问题、一次读取，或者一次没有计划的小补丁，完全不会被拦。

你可以用自己的话在两个方向上覆盖它。"…and run the tests" 会打开它；"no verification needed" 会关掉它。什么都不说，就交给证据来决定。

它在计划中也有一席之地。当验证尚未完成时，一个以验证命名的计划步骤不能被标记为已完成 —— 这条拒绝写在代码里，而不在提示词里。而最终答案需要三者齐备：**计划完成、验证通过、评审通过。** 它们谁也不能替谁开脱。

### 循环及其上限

一次失败的检查是反馈，不是任务的终点：TMT 读取输出，修复它报告的问题，然后再次验证。最多三轮 —— 之后答案会被放行而不是被永远扣住，并附上一行说明验证始终没有通过。沉默才是更糟的失败。

**代码在通过之后发生变动的那一刻，这次通过就过期了。** 在验证通过之后编辑任何东西，都意味着通过的那份东西已经不是将要交付的那份，于是下一个答案会被扣住，直到重新验证过为止。这正是让"修复—验证"循环真正闭合、而不只是一句建议的原因。

如果一个仓库里根本没有任何可运行的东西 —— 没有测试命令、没有 linter、什么都没装 —— 验证会说明这一点，答案会被放行，而 TMT 必须明白地告诉你这项工作未经验证。"我无法验证这个"是有用的；在什么都没跑的情况下说"已验证"则不是。

## 独立评审

**在你的提示词里用 `/review` 提出要求。** 没有这条命令就不会启动任何评审者，这里的一切也不会拦住答案。参见 [能力](#能力planreviewverify)。

验证和评审回答的是不同的问题，而一次实质性的改动两者都需要。验证问的是*这能不能通过可执行的检查*；评审问的是*这是不是正确的改动，以及它是否安全*。测试全绿说明代码做到了测试所说的事 —— 它并不说明这些测试是正确的测试，它也注意不到你造了错的功能。

TMT 在被允许宣称完成之前会评审自己的工作 —— 而且不是通过自问自答。一个**独立的智能体**会去读仓库、diff 和你最初的请求，它没有写过其中任何一行代码，然后报告它的发现。主智能体必须处理那些阻断性的发现，而在评审真正通过之前，运行时不会让它作答。

关键在于绿色测试套件抓不住的那类失败：

> 你要的是带刷新令牌支持的身份认证。测试通过了。评审者读了 diff，发现刷新令牌的过期时间从未被检查，而且 `/health` 已经悄悄被移到了认证之后。两者都没有测试覆盖，因为代码和测试是同一个智能体写的。

### 循环

```
      your request
           |
      plan --> implement --> tests
           |
      independent review
           |
   +-------+--------+
   |                |
 PASS            FINDINGS
   |                |
   |          main agent fixes
   |                |
   |            tests again
   |                |
   +-------<---- review again
           |
     plan complete
           |
      final answer
```

### 评审者能看到什么，看不到什么

它拿到的是**用户最初的请求** —— 被当作真相来源 —— 实施智能体写的计划、计划的完成状态、`git status`、`git diff`、`git diff --stat`、当前的提交、实际被写入的路径，以及一份关于本次会话中实际执行了什么的记录。除此之外的一切都由它自己去取：被改动的文件、调用它们的代码、测试、项目自身的约定。diff 排在最前面，其余内容只在 diff 无法回答问题的地方才展开。

它是**只读**的，而且这一点由代码强制执行，而不是在提示词里请求：每一个写入类动作在被调度之前就会被拒绝。它只做报告；每一处改动都由主智能体来做。它也不能运行任何东西，因此它无法评审自己运行的结果 —— 本次会话执行了什么，是作为一个观察到的事实陈述给它的，而判断那能证明什么则是它的工作。

它被明明白白地告知：不要相信测试，不要相信计划，也不要相信实施智能体对自身工作的描述。

### 发现项

每一条发现都带有一个严重级别、一个文件、一个确实读到过的行号、证据是什么、为什么重要，以及修复的方向。

| 严重级别 | 阻断完成 |
|---|---|
| `CRITICAL` | 是 —— 正确性、安全性、数据丢失、破坏性行为 |
| `MAJOR` | 是 —— 真实的 bug、缺失的必需行为、很可能的回归、重要测试的缺失 |
| `MINOR` | 否 —— 值得修复的较小缺陷 |
| `SUGGESTION` | 否 —— 可选 |

除了这些发现之外，评审者还会返回一份根据你的请求构建的**需求清单**，每一项标记为已满足、部分满足或未满足。正是这一部分把"这段代码看起来好不好"和"我们造的是不是要求的东西"区分开来，也正是这项检查能抓住一个把错误功能实现得干干净净的情况。

结论是 `PASS`、`PASS_WITH_WARNINGS` 或 `FAIL`。一份既声称通过又列出了阻断性发现的回复会被记录为 **FAIL** —— 由发现项决定，而评审者自己的声称会被并排展示出来，好让矛盾可见。

### 是什么让它无法被钻空子

- **只有一次真实的评审才能产生通过。** 任何动作上都没有能设置结论的字段。唯一能改变评审状态的，是评审智能体自己的输出，并且要逐字段解析和校验。一个模型写下 "review passed"，写下的只是一个句子，而句子推不动状态机。
- **没有跑完的评审不是通过。** 一个崩溃了、超时了或者返回了无法解读内容的评审者，会让任务停留在 `ERROR` 状态，而它与失败一样会阻断最终答案。
- **代码在通过之后发生变动时，这次通过就过期了。** 在评审通过之后编辑某个文件，下一个答案就需要一次新的评审 —— 通过的那份东西已经不是将要交付的那份。
- **计划里的评审步骤不能被提前勾掉。** 在评审尚未通过时，把一个标题里含有评审字样的步骤标为完成会被拒绝。
- **评审者不能评审自己的工作。** `review` 对每一个后台智能体（包括评审者自己）都是被拒绝的，而这个动作只在主智能体的提示词中有说明。
- **在有工作者运行时无法启动评审者。** 它们会往评审者正在读的那棵代码树上写东西，那样评审的将是一个从未存在过的状态。

### 它什么时候发生

当运行时看到实质性工作的**两半**时，评审是必需的：一份三步或更多的计划，以及至少一个确实被写入的文件。两者缺一不可 —— 一份改动了零个文件的长计划属于调研，而一次没有计划的单行补丁属于顺手帮忙。这两个都是 TMT 观察到的事实，而不是模型做出的声称，所以模型无法通过把自己的工作描述得很小来躲开评审。

你可以用自己的话在两个方向上覆盖它。"…and review the changes" 会打开它；"no review needed" 会关掉它。什么都不说，就把决定权交给证据，而这是通常的情况。

### 上限

**每个任务有三轮评审。** 如果第三轮仍然报告阻断性问题，答案会被放行，而不是被永远扣住 —— 继续扣住只会耗尽本轮，最后什么答案都没有。它发出时会附上一行，明白地说明评审没有通过以及还有多少条发现未解决，而主智能体也被要求用自己的话说同样的事。沉默才是更糟的失败。

### 屏幕上

评审位于同一右侧列中计划的下方，最多三行：

```
PLAN 2/5                       PLAN 5/5
S1 + Inspect repository        S1 + Inspect repository
S2 + Implement feature         S2 + Implement feature
S3 > Add tests                 S3 + Add tests
S4 - Independent review        S4 + Independent review
S5 - Final verification        S5 + Final verification

REVIEW 1/3                     REVIEW 2/3
> Running independent review   + Review passed
```

每种状态除了颜色之外都带有一个标记，因此这一列在剥掉转义序列后仍然可读，在完全没有颜色的终端上也一样。`/review` 会完整打印这些发现，而且在窄到放不下两列的窗口上，它就是进入这些信息的入口。

## 项目上下文：`TMT_Context/`

会话过去总是从零开始。关于一个项目所弄明白的一切 —— 入口点在哪、哪条命令跑测试、上周实现了什么、什么半途而废 —— 在每次启动时都要重新推导一遍，或者随着进程结束而丢失。

现在 TMT 会在它正在处理的项目里保留两个 markdown 文件：

```text
my-project/
├── src/
├── tests/
├── package.json
└── TMT_Context/
    ├── notes.md      how this project works
    └── progress.md   what has been done, what is being done, what remains
```

它们就是普通文件。打开它们、读它们、编辑它们、提交它们都可以。

### 它什么时候被创建

在一个项目中的**第一个真正的任务**上 —— 不是在你启动 TMT 时，也不是在你输入斜杠命令时。启动之后又改变主意，不会留下任何东西。

```text
tmtcode
   ↓
"Add a dark mode to this application."
   ↓
no TMT_Context → create it, inspect the project, record what was found
   ↓
start working
```

如果 `TMT_Context/` 已经存在，它**不会**被重新创建。如果其中任一文件已经存在，它**不会**被覆盖 —— 不合并、不重新生成，根本不去碰它。

### `notes.md` —— 这个项目是如何运作的

它先根据对仓库的一次真实检查写成，然后随着 TMT 了解更多而被修正和补充。它有固定的标题，方便你和 TMT 都能找到东西：

```text
# TMT Project Notes
## Project Overview      ## Dependencies
## Architecture          ## Constraints
## Important Files       ## Known Issues
## Build                 ## TMT Notes
## Testing
## Configuration
```

初次检查刻意保持浅层 —— 清单文件、标记文件、包脚本、Makefile 目标、`[tool.X]` 段落、CI 配置、README 的第一段、顶层目录，以及任何由清单文件*声明*的入口点。它只读文件、不运行任何东西，因此代价只是一小会儿，而不是遍历一个大仓库。

**其中没有任何内容是编造的。** 在某个事实无法确立的地方，文件会直接说明：

```text
## Build

Build command has not yet been confirmed. Nothing in this repository
names one that TMT recognised.
```

这就是全部规则。一条猜出来的构建命令比一个空章节更糟，因为它会让你付出一次失败的命令，外加你对其余每一行的信任。

### `progress.md` —— 发生过什么

```text
# TMT Project Progress
## Current Status        ## Verification
## Completed             ## Important Decisions
## Currently Working On  ## Known Issues
## Remaining             ## Next Steps
## Tests
```

**只有在有证据的情况下，一项任务才会被记录为已完成** —— 每一步都完成了的计划，或者确实被写入的文件。一个什么都没做就结束的任务，会作为未完成项留在 *Currently Working On* 下面。TMT 打算实现某样东西，永远不会变成一个勾。

**测试结果只会是真实的结果。** Tests 章节是根据由退出码构建出来的验证结果写成的，所以当实际发生的是 `39 passed, 3 failed` 时它就这么写，而当什么都没跑时它什么也不写。

### 它是怎么被使用的

上下文会被放进模型的提示词里，位置在工作区快照**之前**，所以 TMT 读到的第一样东西是它已经弄明白的内容，第二样才是仓库本身。这正是全部要点：一个项目中的第二个任务应该比第一个更快，因为布局不必被重新发现一遍。

```text
"Now add keyboard shortcuts."
   ↓
load TMT_Context → already knows the architecture, the test command,
                   what dark mode did, what is outstanding
   ↓
search only where it still needs to
```

它是按预算装入的，而不是整篇粘贴。小文件会被完整放入；大文件会保留最重要的章节，并且**说明哪些被略去了**，这样模型永远不会被教成"看不见的章节就不存在"。

### 上下文永远不高于代码

`TMT_Context/` 是记忆，不是真相。如果 `notes.md` 说身份认证在 `auth.py` 里，而仓库已经把它挪到了 `authentication/service.py`，那么**仓库是对的**。

TMT 会把笔记中提到的路径与实际存在的路径核对，并把核对结果与笔记本身一起放进提示词：

```text
STALE: these paths are named in the notes but are not in the workspace now:
src/main.py. Do not act on them without checking.
```

它不会替你修改那条笔记 —— 一个文件缺失，可能是因为笔记过时了，也可能是因为你正在重构中途，而只有读代码才能分辨这两者。它所做的，是阻止那条笔记被轻信，并在自己弄清楚之后再去纠正它。

### 你的编辑受到保护

你随时可以手工重写这两个文件中的任何一个。TMT **一次只改一个章节**，并把其余每一个字节原封不动地写回去 —— 包括它从未听说过的标题、你的行文和你的空白格式。没有任何操作会整体交出一个文件，也没有办法要求这么做。

如果你在 TMT 工作期间编辑了文件，你的编辑会保住：改动发生的那一刻文件会被重新读取，而不是取自更早读入的一份副本。

### 机密永远不会被写入

没有 key，没有 token，没有密码，也没有任何来自 `.env` 的值。TMT 记录的是需求而不是值：

```text
## Configuration

Environment variables this project declares (names only -- values are
never recorded here), from `.env.example`:

- `API_KEY`
- `DATABASE_URL`
```

真正的 `.env` 从来不会被打开 —— 它的存在只通过一次 stat 记录下来，内容不会被读取。写入这两个文件的一切内容还会经过 `remember` 所用的同一套凭据过滤器，任何形似凭据的东西都会被涂抹并报告。

### 与 `/plan`、`/review` 和 `/verify` 配合

上下文不重复那几套系统；它记住的是它们得出的结论。

| | 写入 |
|---|---|
| 计划步骤及其真实状态 | `progress.md`，*Currently Working On* |
| 验证实际运行了什么，以及它的数字 | `progress.md`，*Tests* 和 *Verification* |
| 仍未解决的阻断性评审发现 | `progress.md`，*Known Issues* |

最终状态是在完成关卡都同意**之后**、答案发出之前被持久化的，所以顺序始终是：

```text
work → verify → review → persist → end
```

持久化永远不可能放行一个被计划、验证或评审扣住的答案 —— 在那三者都已同意之前根本不会问到它。而 `send_message` 从不敲定任何事：说"我已经实现了这个功能"是一个句子，不是证据。

### 按项目区分，始终如此

上下文路径每次被请求时都从当前活动的工作区推算出来，因此两个项目永远不可能共用一份，一个项目的信息也永远不可能出现在另一个项目里。

### 关闭它

Settings → **Project Context** → Enter。默认是**开启**。

关闭后，TMT 既不创建、也不读取、也不更新任何 `TMT_Context`。**已经写好的文件会被原封不动地留下** —— 它们属于这个项目和写下它们的人，而一项设置并不等于删除别人笔记的同意。

这个开关存放在 `.tmt_context` 中，与 TMT 其他按安装区分的设置放在一起，因此它是 TMT 自己的状态，不会跟着工作区走。上下文*文件*则是 TMT 有意写进你项目里的唯一东西。

### 如果它无法被创建

只读检出、权限失败、磁盘写满：TMT 会说明一次，然后继续你的任务。

```text
Persistent project context could not be created (PermissionError: ...).
Continuing without TMT_Context.
```

这项功能里没有任何东西值得让一个任务失败。

### 应该提交它们吗？

那是你的决定。TMT 不会碰你的 `.gitignore`。默认把这两个文件当作普通的项目文档 —— 它们可读、可 diff，对参与这个仓库的每个人都有用 —— 所以提交它们就是把 TMT 学到的东西分享给团队其他成员。如果你更希望它们只留在本地，就忽略它们。

## 后台智能体

TMT 可以委派工作。主智能体派出后台工作者，它们通过与主智能体相同的动作、相同的模型做真正的工作，主智能体等待它们并报告它们做了什么。

```
Task> spawn three agents to write multiply.py, divide.py and power.py, then wait for them
```

| | 运行于 | 可以编辑 | 可以推送 | 与你对话 | 结束于 |
|---|---|---|---|---|---|
| 主智能体 | 会话循环 | 可以 | 可以 | 可以 | `end_conversation` |
| 工作者 | 一个后台线程 | 可以 | **不可以** | 不可以 | `internal_response` |
| 笔记智能体 | 一个后台线程 | **不可以** | 不可以 | 只回答 | `internal_response` |

**同时十个工作者。** 主智能体不计入其中，笔记智能体也不计入。第十一个请求会被拒绝并附上一句说明，而不是被忽略。

`/agents` 会打印它们正在做什么。在真实终端里，在空行末尾按右方向键会把同样的内容作为实时面板打开，按左方向键关闭。

### 委派契约

一次委派是一份契约，不是一个愿望。`spawn_agent` 接受一个可选的 `constraints` 对象，说明那个智能体可以做什么、可以运行多久、必须报告什么 —— 而且 **TMT 自己强制执行这三点。** 智能体会被告知它的契约，同时它在调度器处也会被拒绝，因此它无法通过换一个工具来绕过其中任何一条。

```json
{"action": "spawn_agent",
 "task": "Investigate how authentication is put together in this repository.",
 "constraints": {
     "read_only": true,
     "timeout_seconds": 600,
     "report": {"file_list": true, "diff": true, "summary": true}
 }}
```

其中每一部分都是可选的，而且**一个不带 `constraints` 的 `spawn_agent` 行为与它一直以来完全一致** —— 逐字节相同的提示词、相同的权限、相同的报告。现有委派的任何方面都没有改变。

约束是**按委派区分**的。工作者 #1 可以是只读且限时五分钟，同时工作者 #2 可以自由写入并限时十五分钟；两者既看不到也影响不到对方的契约，因为一份契约是挂在一条记录上的一个不可变对象，而这条路径上任何地方都没有全局状态。

#### `read_only`

`read_only: true` 表示该智能体可以检视这个工作区，但不可以改动它。它保留每一个读取类动作 —— `read_file`、`read_lines`、`list_files`、`search_files`、`find_text`、`find_symbol`、`tree`、`code_map`、`related_tests`、`recall`、`git_status`、`git_diff`、`git_identity` —— 其余一律被拒绝。

**在执行时强制执行，而不是在提示词里请求。** 拒绝发生在动作运行之前，在两个地方：`agent_worker` 在每个动作被调度前都会检查它，单动作路径和批处理路径都一样，而 `agent_actions.execute_action` 会在调度器处再检查一次。两者调用的是同一个函数，所以只有一条规则，却有两处执行它。

**它是一份白名单，而不是一份被禁动作的清单。** 在这段代码写成之后加入 TMT 的每一个动作，默认都会被拒绝。一份被禁动作的清单会悄无声息地放行下一个有人注册的变更类动作，而添加它的人并不是写那份清单的人。

这也覆盖了那些并非明显属于文件写入的路径：

| 被拒绝 | 原因 |
|---|---|
| `write_file`、`append_file`、`write_files`、`patch_file`、`replace_lines`、`replace_across`、`copy_file`、`rename_file`、`create_folder`、`delete_file`、`delete_folder` | 它们会改动文件 |
| `run_file` / `run_python` | 一个程序可以写任何东西，所以运行它就是一条变更路径 |
| `git_commit` | 提交会改动仓库 |
| `open_app` | 它会启动工作区之外的应用程序 |
| `remember` | 它会写入 TMT 自己的记忆存储 |
| `git_push`、`plan`、`review`、`verify`、`project_context` | 无论有没有契约，它们本来就对每一个后台智能体都是被拒绝的 |

**TMT 没有通用的 shell 动作**，这就是为什么这里任何地方都没有一份"安全"命令的允许清单。工作者能执行任意代码的唯一途径是 `run_file`，而只读委派会被直接拒绝使用它 —— 不需要解析命令字符串，也不需要猜测 `sed -i` 会不会写入。这是这份保证的诚实版本：它建立在只有一条执行路径、而且那条路径是封闭的基础上，而不是建立在 TMT 能分辨变更类命令与无害命令的基础上。

**它不宣称什么。** 一次只读委派无法通过 TMT 提供给它的任何动作做出持久化改动。它不是一个沙箱：TMT 并没有在操作系统层面阻止写入，而如果将来某个动作打开了一条写入途径，那么在只读工作者能够触及它之前，它必须被有意地加入白名单。

一次被拒绝的尝试会被**报告，而不是隐藏**。工作者会被告知什么被拦下了以及为什么，这样它可以调整并继续 —— 一次被拦下的写入并不会自动变成一次失败的委派 —— 而这次尝试会被记录下来，并随结果传达给主智能体：

```
Constraint violations: 1 write operation blocked (write_file src/auth.py)
```

#### `timeout_seconds`

一个 1 到 3600 之间的整数。它是**整次委派**的最长运行时间，而不是某一个动作的，而且不会因为一个动作完成或模型回复而重置。

计时从工作者真正开始运行时起算，而不是从它被注册时起算，因此一次委派不会因为别的什么慢了而损失掉自己的一部分时间。

**由运行时强制执行。** 截止时间会在与取消相同的三个边界上被检查：每一步的开头、流式响应的各个数据块之间，以及每个动作被调度前紧邻的那一行。当它过期时：

- 不会再有动作运行；
- 该智能体的状态变成 `timed_out` —— 它**不是** `failed`，也不是 `killed`；
- 它的工作者名额会立刻释放，因此一次正在等待容量的委派可以开始；
- 它已经做过的一切都会被保留，而它欠下的报告仍然会被收集。

这份保证与 `kill` 所携带的完全一致，不多一分：**在截止时间之后，不会再有工具调用被调度。** 一个已经在途的请求仍然会完整到达，因为 Python 线程无法被终止，而流式响应没有中止原语。宣称瞬时终止会是在一个代价高昂的地方撒谎。

这里没有计时器线程。截止时间是记录上的算术，只在答案可能重要时才被扫描 —— 在每次容量检查之前、在每次重绘时，以及在每次等待内部，而等待永远不会阻塞超过最近的那个截止时间。这与五秒卡片保留期用的是同一套设计，理由也相同：没有东西需要取消，没有东西会泄漏，而且测试可以靠推进一个数字来驱动它，而不用真的等十分钟。

无效的超时值在任何东西启动之前就会被拒绝：负数、零、字符串、`true`、不足一秒的分数，或者任何超过一小时上限的值。**一份被拒绝的契约不会启动任何工作者** —— 一次在半份契约下运行的委派，是唯一一种谁也无法推理的结果。

#### `report`

`file_list`、`diff` 和 `summary`，各自独立。它们**不是权限**，也绝不影响该智能体可以做什么。

- **`file_list`** —— 该智能体自身的动作实际读取和写入的文件，取自那些动作所携带的请求。绝不会由该智能体自述读过什么拼凑而成。
- **`diff`** —— git 对这个智能体所写文件的说法。刻意限定在那些文件上：主智能体在工作者运行期间会继续工作，而且可以同时有多个工作者在跑，所以整棵代码树的 diff 显然不是某一次委派的成果。一次只读委派的 diff 是 `No changes permitted by delegation.`。一次有写权限却什么都没改的委派是 `No workspace changes.`。
- **`summary`** —— 该智能体自己对工作的陈述，也就是它 `internal_response` 中的 `response`，是整份报告里唯一属于模型自身措辞的部分。

报告在**每一种**结束情形下都会被收集，而不只是成功时：一次超时或被取消的委派仍然有真实的文件列表、真实的 diff 和真实的耗时，而因为它没有正常结束就把这些丢掉，等于丢掉了它究竟完成了什么的唯一记录。

回到主智能体那里的内容是结构化且精炼的 —— 没有工具调用记录，没有原始日志：

```
Background agent #4
STATUS: TIMED OUT
Contract: READ ONLY  TIMEOUT 10:00  FILES  SUMMARY
Runtime: 10:00 of 10:00
Progress: 17 actions taken, 11 files inspected, 0 files changed

SUMMARY
  Found the authentication entry point in AuthService; three test modules cover it.

FILES
  Inspected (11):
    src/auth/service.py
    src/auth/token.py
    ...
  Changed: none
```

#### 在屏幕上

提示符旁边的计数器读作 `4/10 agents`，面板标题读作 `AGENTS 4/10`，而一个受约束的智能体的卡片会紧凑地带上它的契约：

```
██░░░░░░ #3  RO  8:32/10:00  +0 -0  ~4k out  1m28s  running
```

`RO` 表示只读，那一对数字是剩余时间对限额 —— 一个真正的倒计时，用的正是那套最终会停下这项工作的算术 —— 而卡片上的 `F D S` 标记的是报告要求。在有足够宽度可读的地方，`/agents` 会把这一切完整说出来。一个超时的智能体显示为 `timeout`，配色是"停止"而不是"失败"，因为它本来就是停止。

#### 嵌套委派

后台智能体不能派出属于自己的智能体 —— 它们的动作上下文里根本没有登记簿 —— 所以一次只读委派无法触及一次可写的委派。这在契约出现之前就已成立，而且没有改变；这里不会为一件不可能发生的事臆造嵌套工作者规则。

### 观察它们工作

在智能体运行期间，每一个都会在主进度条正下方获得属于自己的一行：

```
██████████  60% Working                      <- the main agent, in colour
██░░░░░░ #1  +45 -3  4k out  47s  running    <- one row per agent, in grey
██████░░ #2  +0 -0  ~900 out  1m34s  running
████████ #3  +7 -120  ~15k out  2m21s  done
```

每一行都带着该智能体的编号、它增加和删除的行数、它生成的 token 数、它工作了多久，以及它的状态。上面的一切都是测量出来的而非估算的，除了标有 `~` 的数字 —— 那表示提供方没有报告它，是 TMT 从文本推算出来的，而且凡是出现这种情况的地方都会标注。

**智能体的进度条是灰色的，主进度条是彩色的，而这正是这一区别的全部意义。** 颜色渐变的含义是"主智能体正在工作，而这是它的进度"。五条彩色进度条一眼看去会像是同一个进程被报告了五次。智能体得到的是没有颜色，而不是一种属于自己的颜色。

**一个智能体的进度条显示的是它已花掉的步数预算占比，而不是它离完成有多近。** 没有任何东西能知道后者 —— 一条暗示它的进度条，等于在编造那个谁也拿不到的数字。已完成智能体的进度条是满的，因为它已经结束，而那正是完成度真正可知的唯一时刻。

一个已完成智能体的行和卡片会保留五秒然后消失。它的结果不会：主智能体在很久之后仍然可以索取它。

输入框上方的计数器会把智能体的工作计入会话自身的总计中：

```
+55 lines, -5 lines, ~12k context, 433 out, agents ~22k tokens
```

行数包含智能体写的一切 —— 一个工作者写的一行就是这次会话写的一行，而在五个工作者重写了整个项目时还显示 `+0` 的计数器，是在对一个线程说真话、对整个会话说假话。智能体的 token 花销与 `context` 分开报告，因为后者是在途请求的窗口填满程度，把五个工作者加进去会描述出一个并不存在的上下文。

### `/note` —— 在不打扰任何东西的情况下询问工作区

```
Task> /note which module owns the prompt box?
```

一个只读智能体会在其他一切照常进行的同时从工作区给出答案。它可以搜索、读取和查看结构；它不能创建、编辑、删除或推送，而这一点是由一份在每个动作之前检查的白名单强制执行的，而不是靠好言相劝。

问题写在同一行上。这种形式在任何地方都有效，包括管道运行 —— 管道读取器每行接收一个任务，所以两阶段的提示在管道里根本无法完成。在真实终端里，单独的 `/note` 会另行询问问题。

### 后台智能体刻意做不到的事

这些是设计上的限制，而不是没做完的东西：

- **工作者不能推送。** 它可以读取 `git status`、`diff`、`log` 和 `branch`，也可以提交；触及远端仍然属于主智能体，而主智能体在任务中需要你自己的话语才能这么做。
- **工作者不能删除文件或文件夹。** 两者都要等一个人在终端上确认，而后台线程没有可供询问的终端。工作者会改为报告路径，由主智能体来执行。
- **工作者不能运行测试套件。** `run_file` 在 10 秒后就放弃，而真实的套件耗时更久，所以一个被要求验证测试的工作者会说它做不到，以及它改做了什么。它不会报告一个自己从未看见的结果。
- **"Kill" 是协作式的，不是即时的，超时也一样。** Python 无法强行停止一个线程。被保证并且被测试过的是：**一旦某个智能体被杀掉或已越过截止时间，就不会再有工具调用运行** —— 取消在下一个数据块或下一个动作边界处生效。一个卡在停滞连接上的智能体会被标记为已杀掉并被弃置；它的线程是守护线程，永远无法让 TMT 保持不退出。
- **没有队列。** 十个工作者是硬上限，第十一个请求会被一句话拒绝，而不是排队等待。TMT 没有可以对接的调度器，而为此造一个会远远超出这个上限所需的规模；那句拒绝会指明上限并说明该怎么办，而主智能体据此行动。
- **等待会阻塞主智能体。** 它是一个普通动作，不是挂起。等待期间界面仍然是活的，因为实时区域在它自己的线程上重绘，而 Ctrl-C 会把你带回提示符。
- **工作者之间不协调各自的写入。** 任何单次写入都是原子的，如果两个工作者动了同一个文件，主智能体会被告知是哪些。除此之外没有加锁，所以请给并发的工作者分配互不相同的文件。
- **你永远看不到某个工作者自己的动作。** 界面只为每一个显示一条进度条和一个简短标签，而不是它正在做的读取和编辑。它做了什么会回到主智能体的总结里，这也是为什么主智能体被要求说明它委派了什么。
- **卡片不显示耗时；进度条下面那一行显示。** 面板只在内容变化时重绘，而画在那里的时长要么会变陈旧，要么会强制每个时钟周期重绘一次，而后者正是当初让光标闪烁的原因。

### 智能体的成本

每个工作者在每次请求上都携带它自己的系统提示词，因为 API 是无状态的。那份提示词估计约 14k tokens，而主智能体的约为 19k：它携带的是项目的一个 `tree`，而不是主提示词内联的文件内容，这样每次请求大约省下 1,500 tokens。十个工作者各带一份，所以委派并不免费 —— 它是用 token 换取并行度，而把上限从五提到十，让一次会话能同时买到的量翻了一倍。请委派那些真正可分离的工作，而不是你自己两步就能做完的工作。

一份契约会给携带它的工作者增加几百个 token，而对不携带契约的工作者则毫无增加：一次无约束委派的提示词，与契约出现之前的那份逐字节相同。

## 界面

任务运行期间：在第一段输出之前是一个 THINKING 动画，然后是进度条、耗时和实时的 token 计数。模型文本随流式返回逐字符显现。最终答案会被框起来。只要有智能体在运行，仪表旁边就会出现正在运行的智能体数量。

**智能体面板是屏幕底部的一列，不是一条通栏的侧边栏。** 它与回复和输入框共享实时区域；它上方的对话保持完整宽度，并且永远不会被重绘。这是一条有意的限制，而不是一件没做完的事：滚动回放缓冲区是 TMT 对一次会话唯一的永久记录，而两种能让程序独占整个窗口的转义序列 —— 收窄滚动区域，以及备用屏幕缓冲区 —— 都会摧毁它。从被收窄的区域中滚出去的行会被丢弃而不是保留，于是向上滚动就再也够不到会话自身的历史了。有一个测试会 grep 各个模块，防止它们中的任何一个卷土重来。

在窄于 45 列的终端上，面板会占据实时区域的整个宽度，而它打开期间输入框不会被绘制；窄于 30 列时它会拒绝打开并说明原因。卡片会先舍弃活动行、再舍弃 token 行，而且是截断而不是换行。

### 在它工作时打字

输入框在整轮任务期间都保持可用。你可以在智能体还在处理上一个问题时写下一个问题，编辑键也都能用。

**Enter 是把这一行排入队列，而不是打断。** 它会在当前任务结束后立刻被回答，而且各行按你输入的顺序被回答 —— 所以你可以堆上三个后续问题然后走开。输入框会说明有多少个在等待。

`/note` 也可以在那里输入，而这正是它的意义所在：它在不打扰进行中的工作的情况下从工作区给出答案。

Ctrl-C 仍然会停止正在运行的任务，与以前完全一样。

这需要一个真实的终端。管道或重定向的运行方式是每行读取一个任务，输入框是静止的，而这正是每次脚本化运行和测试套件所面对的情形。

设置 `TMT_STREAM=0` 可以关闭流式输出。流式输出还需要 `requests`；没有它 TMT 会以非流式方式运行。

## 斜杠命令

在提示符处，一行**只有**一个 `/` 命令时会由 TMT 自己回答，永远不会被发送给模型。名称不区分大小写。其他一切都是任务，并且与以前完全一样原样发送给模型 —— 包括仅仅以路径开头的行，比如 `/usr/bin/python is broken`。

`/plan`、`/review` 和 `/verify` 是三个有两种读法的命令。各自单独成行时是下面的只读报告；后面跟着任务时 —— 比如 `/plan Build the login page` —— 这一行就是那个任务，并为它打开对应能力。参见 [能力](#能力planreviewverify)。

| 命令 | 它做什么 |
|---|---|
| `/context` | 到目前为止的对话：模型、提供方、工作区、有多少轮会被带入下一次请求、估算的输入和输出 token、增加和删除的行数，以及最近的几个问题 |
| `/config` | 一次请求所依据的设置：模型、提供方、effort、流式输出、JSON 模式、工作区，以及是否设置了 API key |
| `/clear` | 忘掉对话并重新开始。模型、effort、工作区以及其他每一项设置都会保留，而且不会碰任何文件 |
| `/effort` | 显示当前的 effort 级别 |
| `/effort low\|medium\|high` | 设置它 |
| `/model` | 显示当前模型以及这个提供方提供的模型 |
| `/model <name>` | 切换到其中之一，可用 id 或 Settings 中显示的名称 |
| `/note <question>` | 回答一个关于工作区的问题，什么都不改动 |
| `/notes` | TMT 跨会话记住的关于这个项目的内容：`TMT_Context/` 在哪里、每个文件里有什么，以及哪些笔记提到了不再存在的路径 |
| `/agents` | 后台智能体正在做什么 |
| `/back` | 退到启动菜单，同时保留会话。见下文 |
| `/plan` | TMT 为这个任务正在推进的步骤，以及还剩下什么 |
| `/verify` | 为检查这个任务的工作实际运行了什么：每一项检查、它的命令、它的退出码，以及任何失败项的输出 |
| `/review` | 独立评审发现了什么：结论、每一条发现，以及这个任务历次评审的记录 |

### `/back` —— 回到菜单，而不丢掉会话

`/back` 会把启动菜单重新放到一个仍在运行的会话之上。什么都不会被结束、清空、取消或等待：对话还是那个对话，计划还是那份计划，任何后台智能体都在它后面继续工作。在此之前，Settings 和 Help 只能通过退出才能到达。

它打开的菜单就是启动菜单，只有三处不同：

```
> Resume    Go back to the session, which is still here
  Settings  Provider, API key and the model TMT runs on
  Help      What TMT does, and how to drive it
  Exit      Close TMT and end the session
```

- **Start 读作 Resume**，而且即使光标在别处，它的标签也仍然在渐变中移动 —— 那是屏幕在说你的会话还在那里。
- **Exit 会说明它结束会话。** 用词与启动时相同；后果不同。
- **只要还有任何东西在运行，就不会提供 Settings。** 那一行会消失 —— 不是变灰，不是禁用 —— 而列表上方会有一行说明什么在运行以及该怎么办：

```
Settings are not offered while work is running: 2 agents. Wait for it to
finish, then /back again.
```

提供方、key 和模型在请求进行中都会被读取，所以在一个正在运行的智能体底下改动其中之一，等于把一个没人要求的变更塞进一个已经开始的请求中间。当工作结束时，那一行会在下一帧回来，而不需要关闭菜单。

选择 Resume 会清屏、重新绘制头部，并把你带回提示符，一切如你离开时那样。

**Effort** 是 TMT 会在一个任务上花多少功夫。它改变两件事，而且都是在每个提供方上都真实存在的事：请求多长的回复，以及一个问题可以占用多少轮智能体循环。

| 级别 | 请求的回复长度 | 每任务轮数 |
|---|---|---|
| `low` | 4096 tokens | 12 |
| `medium`（默认） | 4096 tokens | 35 |
| `high` | 8192 tokens | 60 |

回复长度在任何级别上都不会低于 4096。每条回复都是一个 JSON 对象，而其中重要的那些会把一整个文件装在里面，所以更小的上限并不会让模型更简洁 —— 它会把对象从字符串中间截断，于是写入根本不会发生。这项设置存放在安装目录旁的 `.tmt_effort` 中，并能在重启后保留，就像模型选择一样。

**补全。** 在真实终端里，输入 `/` 会在你正输入的那一行下面列出十条命令，并随着你继续输入而收窄：`/mo` 只剩 `/model`。Tab 会补全到候选项一致的位置为止 —— `/mo` 变成 `/model `，`/co` 变成 `/con`，因为 `/context` 和 `/config` 都仍然适用。管道或重定向的运行方式是读取整行且不绘制列表；那些命令本身在那里仍然有效。

**机密。** `/context` 和 `/config` 都绝不会打印 key、token 或密码。`/config` 只说明是否设置了 key，除此之外关于它什么都不说 —— 不说值，也不说值的掩码形式。

## 无法识别 `tmtcode`

命令已经安装了，但 pip 放置它的那个目录不在你的 PATH 上。找到那个目录：

```bash
python -c "import sysconfig; print(sysconfig.get_path('scripts'))"
```

在 Windows 上它是 `Scripts`，在 macOS 和 Linux 上是 `bin`，位于你安装到的那个 Python 或虚拟环境之下。把它加到 PATH 上，或者使用两种备选方式之一 —— 它们接受相同的参数，并以相同的方式挑选项目目录：

```bash
python -m TMT                     # 安装之后，在任何地方
python /path/to/TMT/TMT.py        # 在任何地方，直接从一份克隆运行
```

如果你安装到的是虚拟环境，那么 `tmtcode` 只在那个环境处于激活状态时才存在。

`tmtcode --help` 会打印参数说明。

1581 个测试。其中八个会从 `.tmt_key` 读取 API key，因此在一份没有配置 key 的全新克隆上，那八个会失败，其余通过。

它现在大约需要十五分钟，而不是过去的两分钟，而且其中绝大部分来自 `test_agent_review.py` 里的一个测试，它会启动三个真实的评审智能体，并为每一个等完一次真实的 API 往返。那一个也是这里唯一一个非确定性的测试：它先让一次评审处于失败状态，然后发送一些伪造对象，以证明它们没有一个能把结果变成通过 —— 但运行 `review` 就是运行一次评审，于是一个喜欢你工作树的实时评审者会通过合法途径让它通过，断言就失败了。在相信它之前，请重新运行一次。
