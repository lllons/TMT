## «Too Many Tools» — консольный агент для программирования. Он редактирует файлы в изолированном рабочем каталоге, запускает код на десятке языков, а также автоматически делает коммиты и пуши в любом репозитории.

>**Требуется Python 3.8+.**

## Команда — `tmtcode`

Установка добавляет в PATH одну команду:

```bash
tmtcode
```

Запускайте её из любого каталога системы. **Каталог, в котором вы её запустили,
становится проектом, над которым работает TMT.**

```bash
cd ~/Projects/MyWebsite && tmtcode      # TMT работает над ~/Projects/MyWebsite
cd ~/Documents/MyProject && tmtcode     # TMT работает над ~/Documents/MyProject
```

TMT устанавливается один раз и где угодно. Копировать его в проект не нужно никогда,
и проекту никогда не требуются файлы TMT внутри себя.

## Установка

```bash
git clone https://github.com/lllons/TMT.git
cd TMT
pip install -e .                 # добавляет `tmtcode` в PATH
pip install -e ".[live]"         # опционально: ставит requests и rich для потоковой выдачи и цвета
```

Самому агенту не нужно ничего, кроме стандартной библиотеки; `requests` и `rich` лишь
добавляют потоковую выдачу и цвет, а без них TMT переходит на упрощённый режим.

После установки оставьте клон там, где он лежит, и запускайте `tmtcode` там, где
находится ваша работа. Клон — это дом TMT, а не ваш проект.

Без установки клон тоже запускается напрямую и откуда угодно:

```bash
python /path/to/TMT/TMT.py                    # проектом становится текущий каталог
python /path/to/TMT/TMT.py ~/Projects/MyWebsite
```

Windows: `py`. macOS/Linux: `python3`.

## Два каталога

TMT строго разделяет собственную установку и ваш проект. Это разные вещи, и они
должны такими и оставаться.

| | Что там лежит | Где он находится |
|---|---|---|
| **Каталог установки** | собственный исходный код TMT, сохранённый API-ключ, git-идентичность TMT как соавтора, его журналы | там, куда вы его клонировали — `~/tools/TMT`, `C:\Coding\TMT` — задаётся один раз и больше не меняется |
| **Каталог проекта** (рабочий каталог) | файлы, которые TMT читает, редактирует, запускает и коммитит | там, где вы запустили `tmtcode` |

Изменяется только каталог проекта. Собственные файлы TMT остаются в каталоге установки,
в каком бы проекте вы ни находились, — так что это один и тот же агент с тем же ключом
и тем же адресом соавтора везде.

Скажем это прямо ещё раз: **чтобы работать с проектом, TMT в этот проект копировать не
надо.** Один клон, одна установка, затем `cd` в любой проект и команда `tmtcode`.

## Выбор каталога проекта

| Команда | Каталог проекта |
|---|---|
| `tmtcode` | текущий каталог |
| `tmtcode ../other-repo` | разрешается относительно текущего каталога, затем приводится к абсолютному виду |
| `tmtcode /abs/path/to/project` | этот путь |
| `tmtcode --dir PATH` | то же самое, что позиционный `PATH`; сохранено для существующих сценариев |

Относительный путь разрешается относительно каталога, в котором вы выполнили команду, а
затем приводится к абсолютному виду. Указать одновременно позиционный `PATH` и `--dir`,
которые называют разные каталоги, — ошибка, и TMT завершается, не запускаясь.

TMT использует ровно тот каталог, который ему передали. Он не поднимается вверх в
поисках корня проекта: запустите его в `MyWebsite/src` — и рабочим каталогом будет
`MyWebsite/src`.

Разрешённый путь печатается при запуске, поэтому запуск не из того места сразу заметен:

```
Workspace: C:\Projects\my-repo
```

Всё за пределами этого каталога недоступно: путь, выводящий за пределы рабочего
каталога, отклоняется, а не отрабатывается.

## Права и ограничения

- TMT может создавать, перезаписывать и удалять файлы в любом месте внутри каталога
  проекта, и ничто из сделанного там не восстановимо, если каталог не является
  git-репозиторием. Ему нужны обычные права на чтение и запись в нём.
- Каталог установки должен быть доступен для записи: туда пишутся `.tmt_key` и `logs/`.
  `.tmt_git` и `.tmt_git.local` оттуда только читаются.
- Каталог выбирается, а не создаётся. TMT отклоняет несуществующий путь, файл, корень
  файловой системы и ваш домашний каталог.
- Если в каталоге уже есть файлы и он не находится внутри рабочего дерева git, TMT
  описывает, на что его собираются направить, и спрашивает перед стартом. Git-репозиторий
  сам себе откат, поэтому в нём запуск происходит без вопросов.
- TMT никогда не выполняет команды оболочки. Код он запускает только через `run_file`, а
  из приложений открывает только два перечисленных ниже.
- Для отправки изменений используются те git-учётные данные, которые у вас уже есть. TMT
  ничего не хранит и не реализует никакой авторизации.

## Экран запуска

Каждый запуск `tmtcode` начинается с одного и того же экрана: логотип TMT во весь
терминал, а под ним

```
                              Press Enter to Continue
```

Строка пульсирует, пока идёт ожидание: на цветном терминале по ней проходит градиент,
на терминале без цвета — медленная пульсация насыщенности, а там, где escape-последовательности
недоступны, — ничего, потому что и здесь цвет никогда не является сообщением. Продолжить
можно только клавишей Enter; Ctrl-C закрывает TMT. Всё остальное игнорируется, поэтому
первая задача, набранная до того, как экран устоялся, ничего запустить не может.

**Экран запуска показывается всегда.** Это не настройка, и отключить его нельзя. Настройкой
является то, что происходит *после* Enter.

### После Enter: проверка обновлений

Когда `Auto Update on Launch` **включено** (по умолчанию), TMT смотрит на собственный
git-клон, чтобы понять, существует ли более новая версия, и сообщает об этом на том же
экране:

```
                              Searching for updates...
```

а затем одно из:

```
                                    Up to date.            nothing was pulled, nothing restarted
                          Update complete. Restarting...   a fast-forward was applied
                            Continuing without updating.   an update could not be taken safely
                Update check failed. Continuing without update.
```

Когда настройка **выключена**, ничего этого не происходит, и TMT не делает вид, что
происходило: строка о поиске не показывается для поиска, которого не было. Он сразу идёт
дальше.

После этого TMT продолжает ровно так же, как всегда: настройка API-ключа, если эта
установка ещё не сконфигурирована, а в остальных случаях — обычный стартовый экран.

### Когда TMT обновит себя, а когда нет

Он обновляется, только если обновление однозначно безопасно, и никогда не трогает вашу
работу.

| Что он обнаружил | Что он делает |
|---|---|
| уже актуальная версия | ничего. Никакого pull, никакого перезапуска |
| удалённая ветка впереди, дерево чистое, перемотка вперёд возможна | делает перемотку вперёд, затем перезапускается |
| **незакоммиченные локальные изменения** | отказывается и говорит об этом. Ваши изменения не тронуты |
| **ветка разошлась** — сдвинулись и локальная, и удалённая | отказывается. Локальные коммиты никогда не отбрасываются |
| upstream не настроен или HEAD отсоединён | сообщает, что не может определить, и продолжает |
| это вообще не git-клон | продолжает |
| нет сети, нет git, неверный remote, неудачное слияние | сообщает об ошибке и продолжает |

Он работает с той веткой, которая у вас уже выгружена, и никогда не создаёт, не
переключает и не форсирует ветку. Он использует `git fetch` и `git merge --ff-only` и
ничего больше: **он никогда не выполняет `git reset --hard`, `git clean`, принудительный
checkout или простой `git pull`** — pull может привести к слиянию, а слияние во время
запуска — именно то, чего быть не должно. Отдельный тест читает исходный код самого
обновляющего модуля и проверяет, что этих команд там нет.

TMT остаётся работоспособным без интернета. Неудачная проверка обновлений — это строка
на заставке и ничего больше.

### Перезапуск

Успешное обновление заменяет процесс новым, чтобы действительно выполнялся новый код, а
не оставались загруженными старые модули. Ваша командная строка сохраняется:
`tmtcode --dir ~/project` возвращается как `tmtcode --dir ~/project`.

После этого вы снова видите экран запуска, и это ожидаемо: экран запуска — часть каждого
старта. Перезапущенный процесс обнаруживает, что версия актуальна, и продолжает.
**Зациклиться это не может** — за один запуск происходит не более одного автоматического
перезапуска, и второй процесс знает, что он второй.

### Как это выключить

Settings → `Auto Update on Launch`, Enter для переключения:

```
  AI Provider            Which service answers a request
  API Key                The credential that service is given
  Model                  Which model TMT runs on
> Auto Update on Launch  Check for a newer TMT after the launch screen  ON
  Back                   Return to the menu
```

Настройка хранится в `.tmt_autoupdate` в каталоге установки, рядом с настройками модели
и уровня усилий, поэтому она принадлежит установке, а не одному проекту, и переживает
перезапуски. Отсутствующий файл означает «включено»; файл, который никто не может
прочитать, или файл, отредактированный до бессмыслицы, — тоже «включено», а не ошибка
при старте.

**Выключение этой настройки не выключает экран запуска.** Заставка показывается в любом
случае.

## Первый запуск

При первом запуске запрашивается [ключ OpenRouter](https://openrouter.ai/keys) и
сохраняется в `.tmt_key` в каталоге установки (игнорируется git). Задайте
`OPENROUTER_API_KEY`, чтобы пропустить этот шаг. Ключ запрашивается один раз на
установку, а не один раз на проект.

Наберите задачу в приглашении `Task>`. `quit` или `exit` — выход. Ctrl-C отменяет
текущую задачу, не закрывая TMT.

Файлы меньше 8 КБ показываются модели автоматически — до определённого количества и
суммарного объёма; когда перечисление обрывается раньше, об этом говорится. Файлы
большего размера читаются по запросу.

## О чём можно просить

Обычным языком. Действия TMT выбирает сам.

```
Task> write a python script that fetches a URL and prints the status code
Task> what does report.py do?
Task> find every TODO in src and list them
Task> change the timeout in net.py from 5 to 30 seconds
Task> run hello.py
Task> open notes.txt in notepad
Task> commit the changes and push to main
```

## Разговор с вами: `send_message` и `end_conversation`

У TMT есть ровно два способа вывести слова на ваш экран, и вся разница между ними в
том, продолжается ли задача после этого.

| Действие | Показывает вам текст | Завершает задачу |
|---|---|---|
| `send_message` | да | **нет** — управление каждый раз возвращается агенту |
| `end_conversation` | да | **да** — и это единственное действие, которое завершает задачу |

**`send_message` — чтобы говорить по ходу дела.** «Сначала прочитаю парсер», «тесты
зелёные, дальше документация», «этот файл оказался больше, чем я ожидал». Сообщение
печатается в сессию, где вы можете вернуться к нему прокруткой, после чего TMT
продолжает ровно с того места, где был. Использовать его в одной задаче можно столько
раз, сколько это оправдано; ограничения нет, и ничего окончательного в нём нет.

**`end_conversation` — это завершение.** Его сообщение — та самая сводка, которая
остаётся у вас перед глазами, и именно поэтому агенту сказано: работа, не описанная в
ней, всё равно что не сделана. Второго способа остановиться не существует: нет
отдельного `done` и нет флага на сообщении, который тихо делал бы его последним. TMT
либо завершает задачу этим действием, либо не завершает её вовсе.

**Хотеть завершить и иметь на это право — не одно и то же.** `end_conversation` — это
то, что удерживают шлюзы завершения, и любая возможность, включённая вами для этого
запроса, может его отклонить: план с невыполненными шагами, не пройденное ревью,
верификация, которая не запускалась или нашла проваленную проверку. Отказ — это не
ошибка, и он не завершает ход: TMT получает причину, возвращается к работе, и ответ
по-прежнему не произнесён. См.
[Возможности](#возможности-plan-review-verify).

У фоновых агентов ни одного из этих каналов в осмысленном виде нет: их никто не читает,
поэтому сообщение стоит одного шага и не доходит ни до кого, а завершение — это отчёт
главному агенту. См. [Фоновые агенты](#фоновые-агенты).

## Возможности: `/plan`, `/review`, `/verify`

Три вещи, которые умеет TMT, не являются обычной работой с инструментами. Написать план
и быть им связанным, дать второму агенту проверить дифф и запустить собственные проверки
репозитория — каждая из них стоит целого дополнительного прогона модели, занимает колонку
на экране и может отклонить итоговый ответ самого TMT. Это ваш ресурс, поэтому они
выключены, пока вы их не попросите, а просите вы, написав команду в своём запросе.

| Команда | Что включает |
|---|---|
| `/plan` | процесс планирования — TMT пишет шаги и не может закончить, пока они не выполнены |
| `/review` | независимое ревью кода — отдельный агент только для чтения проверяет работу |
| `/verify` | умную верификацию — реальный запуск тех проверок, которые в этом репозитории действительно есть |

```
Task> build me an authentication system
        nothing gated. Ordinary tools, ordinary answer.

Task> build me an authentication system /plan
        plans the work and is held to the plan. No review, no verification.

Task> fix this implementation /review
        an independent reviewer audits it before the answer goes out.

Task> add the endpoint /plan /verify /review
        the whole pipeline: plan, implement, verify, review, fix, answer.
```

**Вся разница — в слэше, и одного слова `verify` недостаточно.** «verify this code»,
«please verify this», «verified» и «verification» — это то, что люди говорят, прося
обычную работу, и ни одно из них движок не включает. Включает только `/verify`. То же
самое касается `plan` и `review`: «review my code please» — это просьба высказать мнение,
а `/review` — просьба о том самом независимом ревьюере с шлюзом и ограничением по циклам.

Не включает и более длинное слово, начинающееся с команды. `/planning`, `/planner`,
`/plan123`, `/reviewing` и `/verification` — обычный текст, как и команда внутри пути:
`src/review` и `abc/verify` — это пути, а не команды.

Остальные правила ровно те, о которых вы бы и догадались:

- **В любом месте запроса.** В начале, в середине, в конце или отдельной строкой во
  вставленном блоке. `/plan Build it`, `Build it /plan` и `Build the /plan feature` —
  это один и тот же запрос.
- **Сколько угодно раз.** `/plan ... /plan` включает планирование один раз. Двух планов
  не бывает.
- **В любом регистре.** `/PLAN` работает и остаётся на экране как `/PLAN` — TMT
  оформляет ваш текст, но никогда его не переписывает.
- **Независимо друг от друга.** `/plan` не включает ни ревью, ни верификацию, и ни одна
  из них не включает другие. Процесс выбираете вы.
- **По одному запросу за раз.** Возможность разрешена для того запроса, который её
  попросил. Следующий вопрос начинается с нуля, если не попросит тоже.

**Включить их можете только вы.** Не TMT, не фоновый агент, не ревьюер и не файл,
который он прочитал. Модель, решившая, что задача достаточно велика для плана,
написавшая `/plan` в собственных рассуждениях и вызвавшая действие, получит отказ от
среды выполнения: разрешение читается из набранной вами строки и больше ниоткуда. Это
обеспечивается дважды: неразрешённые глаголы вообще не включаются в промпт, а
диспетчер отказывает в них ещё раз, если до одного из них всё же попытались дотянуться.

**Они подсвечиваются по мере набора.** Корректная команда в поле ввода несёт по себе
градиент красный → оранжевый → зелёный, так что вы видите, что именно включили, ещё до
нажатия Enter, и видите, как подсветка исчезает при опечатке. Раскрашивается только
точная команда: `verify` остаётся обычным текстом, и `/verification` тоже. На терминале
без цвета команда выделяется жирным и подчёркиванием, а в конвейерном запуске оформления
нет вовсе — строка всё равно читается как `/plan`, то есть как записанная команда.

Пока идёт ход, всё, что вы разрешили, перечисляется вверху правой колонки:

```
                                                        CAPABILITIES 2
                                                        ● /plan
                                                        ● /verify

                                                        PLAN 2/5
```

**`/plan`, `/review` и `/verify` сами по себе по-прежнему остаются теми же отчётами**,
какими были всегда, — см. [Слэш-команды](#слэш-команды). Строка, в которой нет ничего,
кроме команды, показывает, что делает TMT; строка, в которой есть задача, разрешает
возможность для этой задачи.

### Файлы

| Действие | Назначение |
|---|---|
| `write_file` / `write_files` | Создать файл или сразу несколько |
| `patch_file` | Поиск и замена — вариант по умолчанию для правок |
| `replace_lines` | Заменить точный диапазон строк |
| `append_file` | Дописать в конец файла |
| `read_file` / `read_lines` | Прочитать файл целиком или диапазон строк |
| `glob` | Найти файлы и каталоги по шаблону пути |
| `grep` | Искать по содержимому файлов и сообщать путь, номер строки и саму строку |
| `copy_file` / `rename_file` / `delete_file` | Переместить, переименовать, удалить |
| `create_folder` / `delete_folder` | Папки (рекурсивное удаление — только по явному указанию) |
| `list_files` | Показать содержимое рабочего каталога |

Пути трактуются относительно каталога проекта, и всё, что разрешается за его пределы,
отклоняется. Перечисляется, читается и записывается только этот каталог.

Правка существующего файла выполняется через `patch_file`, а не переписыванием, поэтому
нетронутые строки остаются нетронутыми. Файлы Python проверяются на синтаксис перед
записью; сломанная правка отклоняется, а не сохраняется.

### План

**Попросите его командой `/plan` в запросе.** Без этой команды TMT плана не пишет, и
ничто здесь ответ не блокирует. См.
[Возможности](#возможности-plan-review-verify).

С `/plan` для чего-то существенного — добавить функциональность, исправить ошибку по
всему репозиторию, отрефакторить подсистему, обновить документацию по всему проекту —
TMT пишет план до начала работы и проходит его у вас на глазах. Он появляется колонкой
справа от живой области во время работы и остаётся там, уже завершённый, рядом со
следующим приглашением.

```
                                                        PLAN 2/5
                                                        ─────────────────────────
                                                        S1 ✓ Inspect repository
 09:14 · OpenRouter · MiniMax M3                        S2 ✓ Find and…erminology
 ───────────────────────────────────────────────────    S3 ● Update documentation
 > Describe your next task                              S4 ○ Run tests and verify
 ───────────────────────────────────────────────────    S5 ○ Explain changes
```

| Значок | Статус | Цвет | Означает |
|---|---|---|---|
| `✓` | completed | зелёный | работа по этому шагу действительно сделана |
| `●` | in progress | оранжевый | тот единственный шаг, над которым идёт работа сейчас |
| `○` | pending | красный | ещё предстоит |
| `!` | blocked | янтарный | продвинуться нельзя, и шаг по-прежнему считается незавершённым |

В работе одновременно находится ровно один шаг. Завершение одного само переводит
следующий в работу. Цвет — подтверждение, а не сообщение: у каждого статуса есть ещё и
значок, а вся колонка деградирует до `+ > - !` и ASCII-линеек на терминале, который не
может нарисовать остальное.

**План — это обязательство, а не индикатор прогресса.** TMT не имеет права завершить
задачу, пока остаётся невыполненный шаг. Итоговый ответ, отправленный при незакрытой
работе, вам вообще не показывается: среда выполнения его отклоняет, возвращает модели
список шагов, которые та ещё должна, и ход продолжается. Это обеспечивается программой,
а не просьбой в промпте, поэтому решение модели, что она закончила, не делает работу
законченной:

```
Task> add the feature
 · Planning the work in two steps.
 ◆ Plan created with 2 steps.
 ▲ Plan not finished - 2 steps outstanding, next is S1 Implement the feature. Continuing.
 · The feature is in; running the tests next.
 ◆ S1 (Implement the feature) in_progress -> completed.
 · Suite is green.
 ◆ S2 (Run the tests) in_progress -> completed.
 ┌──────────────────────────────────────────────────────────────┐
 │ Added the feature and the suite is green: 12 tests, 0 failures.│
 └──────────────────────────────────────────────────────────────┘
```

План можно пересматривать всякий раз, когда работа оказывается не такой, как ожидалось:
шаги переименовываются, добавляются, удаляются, а весь план может быть заменён. Двух
вещей произойти не может. Завершённый шаг никогда не открывается заново: законченный
шаг остаётся законченным, а план, форма которого оказалась неверной, заменяется целиком,
а не откатывается. И план, по которому уже проделана работа, нельзя просто выбросить —
это был единственный обходной путь мимо шлюза, поэтому очистка отклоняется, как только
хотя бы один шаг завершён. И доведение плана до конца, и его переработка видны на
экране; тихое исчезновение — нет.

**План получает не всё.** «Что делает эта функция?» — это один ответ, и план для него
был бы шумом на экране и шлюзом на собственном ответе TMT. Планы нужны для работы,
состоящей из этапов.

**План принадлежит задаче, а не сессии.** Он снимается в тот момент, когда вы задаёте
следующий вопрос, поэтому незавершённый план никогда не может задержать ответ на что-то
не связанное. На диск ничего не пишется. Фоновые агенты не могут его ни видеть, ни
менять: это обязательство главного агента перед вами, а завершение шага рабочим агентом
позволило бы TMT закончить работу, которую он лишь заявил.

**На терминале уже 45 колонок** колонка не рисуется — поле ввода нуждается в месте
больше, — а `/plan` печатает то же самое обычным текстом при любой ширине.

### Как разобраться в репозитории

Девять действий, чтобы ориентироваться в кодовой базе, не читая её целиком. Каждое
отвечает на один вопрос, и TMT велено выбирать самое узкое из подходящих.

| Действие | Назначение | Когда за ним обращаться |
|---|---|---|
| `tree` | Каталоги, файлы, размеры, вложенность. Содержимое не читает | Нужна форма проекта |
| `glob` | Файлы и каталоги, подходящие под шаблон пути. `*` останавливается на `/`, `**/` означает любую глубину, а шаблон без `/` совпадает с именем где угодно | Нужно узнать, какие файлы есть или где лежит нужный |
| `grep` | Искать внутри файлов, сообщая путь, номер строки и саму строку. По умолчанию точно и с учётом регистра; запрос может занимать несколько строк | Вы знаете текст, который ищете |
| `find_symbol` | Где *определены* функция, класс, метод, константа или тип | Нужно определение, а не упоминание |
| `code_map` | Что это определяет, что это импортирует, что импортирует его, где на него ссылаются | Нужно понять, на что повлияет изменение |
| `replace_across` | Одна и та же точная правка во многих файлах | Переименование того, что используется во всём проекте |
| `related_tests` | Читает git-дифф и называет тесты, которые стоит прогнать | Вы изменили одно и не хотите гонять всё |
| `remember` / `recall` | Долговременные заметки об этом проекте, сохраняемые между сессиями | Что-то стоило вам времени, чтобы выяснить |

```
Task> show me the project structure
Task> find every place that calls self.workspace_root
Task> where is calculate_total defined?
Task> what imports agent_file_ops?
Task> rename old_function_name to new_function_name across src
Task> which tests should I run for what I just changed?
```

**`glob` находит файлы по пути или имени; `grep` находит текст внутри файлов.** В этом
и вся разница, и её стоит усвоить как следует: работающий порядок — `glob`, чтобы найти
файлы-кандидаты, `grep`, чтобы найти в них строки, `read_lines`, чтобы прочитать нужный
участок, затем правка, затем тесты — а не чтение целого репозитория ради одной строки.

```json
{"action": "glob", "pattern": "agent_*.py"}
{"action": "glob", "pattern": "testing/**/*.py"}
{"action": "grep", "query": "end_conversation"}
{"action": "grep", "query": "def run_file", "glob": "agent_*.py"}
{"action": "grep", "query": "timeout", "path": "src", "ignore_case": true}
```

`grep` по умолчанию точный и чувствительный к регистру — как и инструмент, чьё имя он
носит. `"ignore_case": true` делает его нестрогим, `"regex": true` читает запрос как
регулярное выражение, `"context"` добавляет строки по обе стороны от каждого совпадения,
а `"path"` или `"glob"` ограничивают то, какие файлы вообще будут прочитаны. Он никогда
не возвращает файл целиком: вы получаете путь, номер строки и саму строку, а остальное
достаёт `read_lines`.

**`replace_across` по умолчанию только показывает предварительный результат.** Он
сообщает, сколько файлов и вхождений *было бы* изменено, и ничего не пишет. Отправка
того же действия ещё раз с `"apply": true` выполняет замену. Переводы строк и кодировка
сохраняются, бинарные файлы пропускаются, а замена, после которой файл Python перестал
бы разбираться, отклоняется, а не записывается.

**Факты и догадки помечаются по-разному.** Символы Python находятся разбором файла,
поэтому такие ответы точны; в других языках сопоставление лексическое, и об этом
говорится. `related_tests` отделяет то, что доказывает дифф, от того, о чём он лишь
догадывается. Ничто не выдаёт эвристику за измерение.

**Память проекта** хранится рядом с собственными настройками TMT, с ключом по проекту, и
никогда не внутри вашего репозитория — то же правило, что и для любого другого состояния
TMT. Заметки просматриваются перед записью, и всё, что похоже на ключ, токен или пароль,
отклоняется.

### Запуск кода

`run_file` выполняет код и возвращает вывод. Python, JavaScript, TypeScript, Ruby, PHP,
Lua, Perl, R, Go, C, C++, Java. Таймаут 10 секунд. Инструментарий должен быть в вашем
PATH. Код выполняется с каталогом проекта в качестве рабочего каталога.

### Приложения

`open_app` запускает Notepad или Explorer с выделенным файлом. И ничего больше — TMT
никогда не выполняет команды оболочки.

## Git

TMT делает коммиты в том репозитории, который содержит каталог проекта, — а не в
собственном репозитории TMT. Автором и коммиттером каждого сделанного им коммита
остаётесь вы; TMT указывается рядом с вами трейлером `Co-authored-by`.

```
Task> commit this                        commits, does not push
Task> commit these changes and push       commits and pushes
Task> push this to main                   targets main
Task> fix the bug                         edits only, no commit, no push
```

Коммит и отправка разделены. TMT отправляет изменения, только если об этом попросили
вашими собственными словами: «fix the bug» никогда не приводит к push, как и завершение
правки.

Действия: `git_status`, `git_diff`, `git_identity`, `git_commit`, `git_push`.

Он индексирует только те файлы, которые изменил сам, поэтому ваша посторонняя работа
остаётся незакоммиченной. Он никогда не создаёт ветку, никогда не выдумывает remote и
никогда не делает принудительную отправку. Если push не удался, коммит остаётся
локальным, а вы получаете настоящую ошибку.

### Соавторство TMT

TMT не коммитит от вашего имени и не коммитит вместо вас. Автором и коммиттером
выступает собственная git-идентичность репозитория. TMT добавляет к сообщению один
трейлер и ничего больше. Один коммит, и в нём отмечены вы оба.

Коммит, сделанный TMT, каким его показывает git:

```
$ git log -1 --format=fuller
commit f1977e70a471011bf9b5ab643aecdf5e18a8e8fa
Author:     Liam <liam@example.com>
AuthorDate: Sat Aug 29 13:10:01 2026 +1200
Commit:     Liam <liam@example.com>
CommitDate: Sat Aug 29 13:10:01 2026 +1200

    Add a greeting file

    Co-authored-by: TMT code <TMT.tmt.code@gmail.com>
```

Это именно git-трейлер, а не строка прозы, в которой случайно оказалось двоеточие,
поэтому сам git вернёт его обратно:

```
$ git log -1 --format=%(trailers:key=Co-authored-by)
Co-authored-by: TMT code <TMT.tmt.code@gmail.com>
```

Что это означает на практике:

- Автор и коммиттер — те, кого называет git-конфигурация репозитория. TMT никогда не
  вписывает себя ни в одно из этих полей и никогда не пишет в вашу git-конфигурацию —
  ни глобальную, ни на уровне репозитория.
- Если git-идентичность у вас не задана, git отклоняет коммит. TMT сообщает об этом,
  говорит вам самостоятельно задать `user.name` и `user.email` и не подставляет себя в
  качестве автора. Ничего не коммитится.
- TMT добавляет трейлер только к тем коммитам, которые создаёт сам. Коммит, сделанный
  вами через `git commit`, не трогается.
- Сообщение, в котором адрес TMT уже указан, получает один трейлер, а не два.
  Сопоставление идёт по адресу, поэтому тот же адрес под другим отображаемым именем
  тоже считается уже указанным.
- Существующие трейлеры сохраняются. `Co-authored-by:` для кого-то другого остаётся, и
  TMT добавляется рядом; блок `Signed-off-by:` дополняется, а не выносится в новый
  абзац.
- История никогда не переписывается. Если в готовом коммите трейлера почему-то не
  оказалось, TMT сообщает об этом и оставляет коммит в покое, а не правит его через
  amend.
- Если адрес TMT не настроен или на месте остаётся поставляемая заглушка, TMT
  отказывается коммитить и ничего не индексирует.

Признание на GitHub — отдельный вопрос, и ответ на него TMT не контролирует:

- TMT решает, каковы метаданные коммита, — трейлер, и только трейлер.
- GitHub решает, засчитывать ли соавторство. Он сопоставляет адрес из трейлера с
  адресами, подтверждёнными в учётной записи. Адрес, не подтверждённый ни в одной
  учётной записи, не засчитывается никому, а одно только отображаемое имя не даёт
  ничего.
- Даже когда адрес совпадает, данные GitHub об участниках и профиле могут обновляться с
  задержкой. Push не обязательно сразу меняет граф участников.
- Получить признание и иметь право на push — не одно и то же. Аутентификация — отдельная
  вещь и остаётся вашей.

### Идентичность соавтора

```
TMT_GIT_NAME=TMT code
TMT_GIT_EMAIL=someone@example.com
```

Адрес, под которым указывается TMT. В коммит как автор он не вписывается никогда.
Читается в таком порядке: переменные окружения `TMT_GIT_*`, затем `.tmt_git.local`
(игнорируется git, для конкретной машины), затем `.tmt_git` (отслеживается, поставляется
с проектом). Имя по умолчанию — `TMT code`. У адреса значения по умолчанию нет, и он
никогда не берётся из вашей git-конфигурации: ваша git-конфигурация даёт автора, а не
соавтора.

Оба файла лежат в каталоге установки, поэтому TMT указывается под одним и тем же
адресом в каждом проекте, на который вы его направляете.

`.tmt_git` отслеживается намеренно: адрес для коммитов — публичные метаданные, а не
учётные данные, поэтому каждый клон получает того же соавтора TMT без настройки. В нём
есть имя и адрес — и ничего больше. Не кладите туда токены, пароли и ключи, как и в
`.tmt_git.local`.

Выполните `git_identity`, чтобы увидеть, какой источник победил, какие файлы были
просмотрены и пригоден ли адрес.

### Настройка признания на GitHub

Отслеживаемый `.tmt_git` называет адрес, подтверждённый в учётной записи GitHub,
представляющей TMT, поэтому свежий клон засчитывает соавторство правильно без всякой
настройки. Если этот адрес когда-либо окажется заглушкой, TMT откажется коммитить, а не
укажет соавтора, за которым никого нет. Чтобы указывать вместо этого вашу собственную
учётную запись:

1. Создайте учётную запись GitHub для TMT.
2. Добавьте и подтвердите на ней адрес.
3. Пропишите этот адрес в `.tmt_git.local` или в `.tmt_git` и закоммитьте его один раз.

Четыре разные вещи, и лишь одну из них решает TMT:

- **Авторство** — автор и коммиттер, вписанные в коммит. Ваши. TMT читает их, чтобы
  сообщить, и никогда не задаёт и не меняет, а ваши `user.name` и `user.email` не
  модифицируются ни глобально, ни для репозитория.
- **Признание соавторства** — трейлер `Co-authored-by`. Единственная часть коммита, о
  которой решает TMT.
- **Признание на GitHub** — сопоставление GitHub'ом адреса из трейлера с подтверждённой
  учётной записью. Вне власти TMT, и одно только отображаемое имя не даёт ничего.
- **Аутентификация** — кто имеет право на push. Остаётся вашей: ваш SSH-ключ, менеджер
  учётных данных или вход через `gh`. TMT не хранит учётных данных и не реализует
  авторизации.

## Верификация

**Попросите её командой `/verify` в запросе.** Без этой команды ничего из описанного не
происходит, и ничто здесь ответ не блокирует; одного слова `verify` недостаточно.
См. [Возможности](#возможности-plan-review-verify).

С `/verify`, прежде чем TMT будет позволено сказать, что работа сделана, он запускает
те проверки, которые в этом репозитории действительно есть, и среда выполнения не даст
ему ответить, пока они не пройдут.

Суть — в различии между доказательством и мнением:

> «Это должно работать» — не верификация. `43 passed, 0 failed` — верификация.

TMT не спрашивает модель, работает ли код. Он читает репозиторий, выясняет, чем этот
проект сам себя тестирует, линтует и собирает, читает дифф, чтобы понять, что
изменилось, выбирает проверки, которые имеет смысл выполнить именно для *этого*
изменения, запускает их и сообщает коды возврата. Ничто из написанного моделью не может
сдвинуть этот результат: нет ни одного ключа ни у одного действия, который задавал бы
статус, а проверка считается пройденной, когда процесс завершился с нулём, и ни в какой
другой момент.

### Что он решает запускать

**Он предпочитает ваши команды собственным догадкам.** По порядку:

1. команда, которую этот репозиторий определяет по имени, — скрипт в `package.json`,
   цель `Makefile`, `run_tests.py` в корне
2. инструменты, которые этот репозиторий настраивает, — `[tool.ruff]`, `[tool.mypy]`,
   `tsconfig.json`
3. пакетный менеджер проекта — `npm`, `pnpm`, `yarn`, `bun`, `uv`, `poetry`
4. стандартная команда для экосистемы — `cargo test`, `go vet`, `pytest`
5. догадка, помеченная как догадка

Если в вашем `package.json` написано `"test": "vitest run"`, TMT запускает `npm run
test`. Он не решает, что в node-проектах используется jest. Если в вашем репозитории
есть `run_tests.py`, то это и есть команда тестов — даже там, где сработал бы и
`pytest`, потому что запускать не то, что запускаете вы, и называть это вашей
верификацией было бы неправильно, даже если бы она прошла.

Конфигурация CI читается как *свидетельство* того, какими инструментами вы реально
пользуетесь, и никогда как источник команд. Ничто из запускаемого TMT не является
строкой, взятой из файла проекта: берётся имя, а команда строится вокруг него по
фиксированной таблице. Никакой оболочки на этом пути нет.

**Он запускает дешёвые проверки раньше дорогих** и останавливается на первой
провалившейся:

| Уровень | Что |
|---|---|
| 1 | синтаксис и форматирование того, что изменилось |
| 2 | линт, проверка типов, проверки компилятора |
| 3 | тесты, которые называют то, что вы изменили |
| 4 | тесты вокруг них |
| 5 | сборка проекта |
| 6 | весь набор тестов |

Когда проверка типов уже провалилась, десять минут, которые заняли бы интеграционные
тесты, — это десять минут измерения дерева, о котором уже известно, что оно неверно.
Всё, что идёт после провала, сообщается как пропущенное с этим в качестве причины, —
так что *непроверенное* видно, а не подразумевается.

**Он идёт глубже, когда изменение рискованнее.** Аутентификация, миграции, схема базы
данных, контракты API, конкурентность, границы файловой системы, выполнение команд
оболочки, конфигурация зависимостей или сборки — или просто много файлов сразу —
получают полный набор тестов. Изменение только документации получает статические
проверки и никакого прогона тестов.

### Четыре исхода, которые не смешиваются

| | Означает |
|---|---|
| **PASSED** | команда выполнилась и завершилась с кодом 0. Единственный существующий вид доказательства |
| **FAILED** | команда выполнилась и завершилась с ненулевым кодом. Что-то не так, и вывод говорит, что именно |
| **SKIPPED** | она не запускалась — инструмент не установлен, либо более ранняя проверка уже провалилась |
| **ERROR** | она не смогла запуститься или не завершилась. Ничего не известно, и это *не* провал вашего кода |

Они никогда не сводятся к булеву значению. Таймаут — не провал; отсутствующий линтер —
не пройденный линт. TMT ничего не станет устанавливать, чтобы закрыть такую дыру:
отсутствующая зависимость сообщается, а не чинится втихую.

### Как это выглядит

```
VERIFY 1/3
✓ Syntax          passed
✓ Lint            passed
✗ Targeted tests  2 failed, 41 passed
– Full suite      not run: Targeted tests did not pass
```

`/verify` печатает весь прогон, включая вывод всего, что провалилось.

### Как он выбирает тесты

Для проекта, чья команда тестов принимает пути, TMT определяет, каких тестов достигает
изменение, и запускает их первыми. Тестовый файл считается **целевым**, когда для этого
есть свидетельство: он называет изменённый модуль, импортирует изменённый символ или
находится там, где велит собственное соглашение об именовании в проекте, — и
**связанным**, когда это догадка о достижимости. Эти два случая держатся врозь и
разнесены по уровням, потому что догадка, поданная как измерение, хуже, чем отсутствие
выборки вообще.

Там, где команду тестов проекта *нельзя* сузить до путей — `npm test` или `run_tests.py`,
запускающий всё, — TMT говорит об этом и запускает весь набор в качестве тестового
свидетельства. Он не запускает всё, называя это целевым прогоном.

### Когда это происходит

Верификация обязательна, когда среда выполнения увидела **обе** половины существенной
работы: план из трёх и более шагов и хотя бы один действительно записанный файл — те же
два факта, по которым решается вопрос о ревью, наблюдаемые, а не заявленные. Вопрос,
чтение или небольшая правка без плана не блокируются вовсе.

Вы переопределяете это в любую сторону своими словами. «…and run the tests» включает
верификацию; «no verification needed» выключает. Молчание оставляет решение за
свидетельствами.

Ей есть место и в плане. Шаг плана, названный по верификации, не может быть отмечен
завершённым, пока верификация не сделана, — этот отказ реализован в коде, а не в
промпте. А итоговому ответу нужны все три условия: **план завершён, верификация пройдена
и ревью пройдено.** Ни одно из них не отменяет другого.

### Цикл и его пределы

Провалившаяся проверка — это обратная связь, а не конец задачи: TMT читает вывод,
исправляет то, о чём тот сообщает, и верифицирует снова. Не более трёх кругов; после
этого ответ выпускается, а не удерживается вечно, и несёт строку о том, что верификация
так и не прошла. Молчание было бы худшим исходом.

**Пройденная верификация устаревает в тот момент, когда код под ней сдвигается.** Правка
чего угодно после пройденной верификации означает, что прошло не то, что поедет в
релиз, и следующий ответ удерживается до повторной верификации. Именно это замыкает
цикл «исправить и проверить», а не оставляет его пожеланием.

Если в репозитории вообще нечего запускать — нет ни команды тестов, ни линтера, ничего
не установлено, — верификация говорит об этом, ответ выпускается, и TMT обязан прямо
сказать вам, что работа не верифицирована. «Я не смог это проверить» полезно;
«проверено», когда ничего не запускалось, — нет.

## Независимое ревью

**Попросите его командой `/review` в запросе.** Без этой команды никакой ревьюер не
запускается и ничто здесь ответ не блокирует. См.
[Возможности](#возможности-plan-review-verify).

Верификация и ревью отвечают на разные вопросы, и существенному изменению нужны оба.
Верификация спрашивает, *проходит ли это исполняемые проверки*; ревью спрашивает, *то
ли это изменение и безопасно ли оно*. Зелёный набор тестов говорит, что код делает то,
что говорят его тесты, — он не говорит, что тесты правильные, и не замечает, что вы
построили не ту функциональность.

TMT проверяет собственную работу, прежде чем ему будет позволено сказать, что она
сделана, — и не спрашивая самого себя. **Отдельный агент** читает репозиторий, дифф и
ваш исходный запрос, ничего из этого не написав, и сообщает, что нашёл. Главный агент
обязан отреагировать на блокирующие находки, а среда выполнения не даст ему ответить,
пока ревью действительно не пройдено.

Суть — в том провале, который зелёный набор тестов не ловит:

> Вы попросили аутентификацию с поддержкой refresh-токенов. Тесты проходят. Ревьюер
> читает дифф и обнаруживает, что срок действия refresh-токенов нигде не проверяется и
> что `/health` тихо уехал под аутентификацию. Ни то ни другое не покрыто тестами,
> потому что один и тот же агент написал и код, и тесты.

### Цикл

```
      your request
           |
      plan --> implement --> tests
           |
      independent review
           |
   +-------+--------+
   |                |
 PASS            FINDINGS
   |                |
   |          main agent fixes
   |                |
   |            tests again
   |                |
   +-------<---- review again
           |
     plan complete
           |
      final answer
```

### Что ревьюер видит, а что нет

Ему даются **исходный запрос пользователя** — как источник истины, — план, написанный
агентом-исполнителем, состояние выполнения плана, `git status`, `git diff`,
`git diff --stat`, текущий коммит, пути, которые действительно были записаны, и заметка
о том, что в сессии действительно выполнялось. Всё остальное он добывает сам:
изменённые файлы, код, который их вызывает, тесты, собственные соглашения проекта. Дифф
идёт первым, а остальное разворачивается только там, где дифф на вопрос не отвечает.

Он работает **только на чтение**, и это обеспечивается кодом, а не просьбой в его
промпте: каждый записывающий глагол отклоняется до диспетчеризации. Он сообщает; все
изменения делает главный агент. Он также не может ничего запускать, поэтому не может
рецензировать результат собственного запуска: то, что выполнила сессия, излагается ему
как наблюдаемый факт, а судить о том, что это доказывает, — его работа.

Ему прямым текстом сказано не доверять тестам, не доверять плану и не доверять рассказу
агента-исполнителя о собственной работе.

### Находки

Каждая находка несёт степень серьёзности, файл, строку, если она действительно была
прочитана, в чём состоит свидетельство, почему это важно и в каком направлении
исправлять.

| Степень | Блокирует завершение |
|---|---|
| `CRITICAL` | да — корректность, безопасность, потеря данных, разрушительное поведение |
| `MAJOR` | да — настоящая ошибка, отсутствующее обязательное поведение, вероятная регрессия, важный отсутствующий тест |
| `MINOR` | нет — менее значительный дефект, который стоит исправить |
| `SUGGESTION` | нет — необязательное |

Вместе с находками ревьюер возвращает **контрольный список требований**, построенный из
вашего запроса, где каждый пункт отмечен как выполненный, выполненный частично или
невыполненный. Именно эта часть отличает «выглядит ли этот код хорошо» от «построили ли
мы то, о чём просили», и именно она ловит чистую реализацию не той функциональности.

Вердикт — `PASS`, `PASS_WITH_WARNINGS` или `FAIL`. Ответ, заявляющий о прохождении и
при этом перечисляющий блокирующую находку, записывается как **FAIL**: решают находки,
а собственное заявление ревьюера показывается рядом, чтобы противоречие было видно.

### Что мешает это обойти

- **Пройденное ревью может дать только настоящее ревью.** Нет ни одного ключа ни у
  одного действия, который задавал бы вердикт. Состояние ревью двигает единственная
  вещь — собственный вывод агента-ревьюера, разобранный и проверенный поле за полем.
  Модель, пишущая «review passed», пишет предложение, а предложения конечный автомат не
  двигают.
- **Незавершённое ревью — не пройденное ревью.** Ревьюер, который упал, вышел по
  таймауту или вернул нечто нечитаемое, оставляет задачу в состоянии `ERROR`, а оно
  блокирует итоговый ответ ровно так же, как провал.
- **Пройденное ревью устаревает, когда код под ним сдвигается.** Отредактируйте файл
  после пройденного ревью — и следующему ответу понадобится свежее: прошло не то, что
  поедет в релиз.
- **Шаг ревью в плане нельзя отметить заранее.** Отметить завершённым шаг, в названии
  которого есть ревью, отклоняется, пока ревью не пройдено.
- **Ревьюер не может рецензировать собственную работу.** `review` запрещено любому
  фоновому агенту, включая самого ревьюера, а сам глагол документирован только в
  промпте главного агента.
- **Ревьюера нельзя запустить, пока работают рабочие агенты.** Они писали бы в то
  дерево, которое он читает, и ревью относилось бы к состоянию, которого никогда не
  существовало.

### Когда это происходит

Ревью обязательно, когда среда выполнения увидела **обе** половины существенной работы:
план из трёх и более шагов и хотя бы один действительно записанный файл. По отдельности
не считается: длинный план, ничего не изменивший, был исследованием, а однострочная
правка без плана была услугой. И то и другое — факты, которые TMT наблюдал, а не
утверждения модели, поэтому модель не может назвать свою работу мелкой, чтобы избежать
ревью.

Вы переопределяете это в любую сторону своими словами. «…and review the changes»
включает ревью; «no review needed» выключает. Молчание оставляет решение за
свидетельствами, и это обычный случай.

### Пределы

На задачу отводится **три цикла ревью**. Если и третий сообщает о блокирующих проблемах,
ответ выпускается, а не удерживается вечно: дальнейшее удержание израсходовало бы ход и
закончилось бы вообще без ответа. Ответ уходит со строкой, прямо говорящей, что ревью не
пройдено и сколько находок открыто, и главный агент обязан сказать то же самое своими
словами. Молчание было бы худшим исходом.

### На экране

Ревью располагается под планом в той же правой колонке, не более чем в трёх строках:

```
PLAN 2/5                       PLAN 5/5
S1 + Inspect repository        S1 + Inspect repository
S2 + Implement feature         S2 + Implement feature
S3 > Add tests                 S3 + Add tests
S4 - Independent review        S4 + Independent review
S5 - Final verification        S5 + Final verification

REVIEW 1/3                     REVIEW 2/3
> Running independent review   + Review passed
```

У каждого состояния есть не только цвет, но и значок, поэтому колонка читается и с
вырезанными escape-последовательностями, и на терминале вовсе без цвета. `/review`
печатает находки полностью и является входом туда, где окно слишком узко для двух
колонок.

## Контекст проекта: `TMT_Context/`

Раньше сессия начиналась с нуля. Всё, что было выяснено о проекте, — где точка входа,
какая команда запускает тесты, что было сделано на прошлой неделе и что осталось
недоделанным, — восстанавливалось заново при каждом запуске или терялось вместе с
завершением процесса.

Теперь TMT держит в проекте, над которым работает, два markdown-файла:

```text
my-project/
├── src/
├── tests/
├── package.json
└── TMT_Context/
    ├── notes.md      how this project works
    └── progress.md   what has been done, what is being done, what remains
```

Это обычные файлы. Открывайте их, читайте, редактируйте, коммитьте.

### Когда он создаётся

При **первой настоящей задаче** в проекте — не при запуске TMT и не при вводе
слэш-команды. Если вы запустили TMT и передумали, после вас ничего не останется.

```text
tmtcode
   ↓
"Add a dark mode to this application."
   ↓
no TMT_Context → create it, inspect the project, record what was found
   ↓
start working
```

Если `TMT_Context/` уже есть, он **не** создаётся заново. Если один из файлов уже есть,
он **не** перезаписывается — не сливается, не генерируется заново, не трогается вовсе.

### `notes.md` — как устроен проект

Пишется сначала по результатам реального осмотра репозитория, а затем исправляется и
дополняется по мере того, как TMT узнаёт больше. У него устойчивые заголовки, чтобы и
вы, и TMT могли что-то найти:

```text
# TMT Project Notes
## Project Overview      ## Dependencies
## Architecture          ## Constraints
## Important Files       ## Known Issues
## Build                 ## TMT Notes
## Testing
## Configuration
```

Первичный осмотр намеренно неглубок: манифесты, файлы-маркеры, скрипты пакета, цели
`Makefile`, секции `[tool.X]`, конфигурация CI, первый абзац README, каталоги верхнего
уровня и любая точка входа, которую *объявляет* манифест. Он читает файлы и ничего не
запускает, поэтому стоит мгновения, а не обхода большого репозитория.

**Ничто в нём не выдумано.** Там, где факт установить не удалось, файл так и говорит:

```text
## Build

Build command has not yet been confirmed. Nothing in this repository
names one that TMT recognised.
```

Это и есть всё правило. Угаданная команда сборки хуже пустого раздела, потому что стоит
вам одной провалившейся команды и доверия ко всем остальным строкам.

### `progress.md` — что произошло

```text
# TMT Project Progress
## Current Status        ## Verification
## Completed             ## Important Decisions
## Currently Working On  ## Known Issues
## Remaining             ## Next Steps
## Tests
```

**Задача записывается как завершённая, только если для этого есть свидетельство** — план,
у которого выполнены все шаги, или файлы, которые действительно были записаны. Задача,
завершившаяся без каких-либо действий, остаётся в *Currently Working On* как открытая.
Намерение TMT что-то реализовать никогда не превращается в галочку.

**Результаты тестов бывают только настоящими.** Раздел Tests пишется из результата
верификации, построенного на кодах возврата, поэтому там стоит `39 passed, 3 failed`,
когда именно так и было, и не стоит ничего, когда ничего не запускалось.

### Как он используется

Контекст помещается в промпт модели **перед** снимком рабочего каталога, поэтому первое,
что читает TMT, — это то, что он уже выяснил, а второе — сам репозиторий. В этом и весь
смысл: вторая задача в проекте должна идти быстрее первой, потому что структуру не
приходится открывать заново.

```text
"Now add keyboard shortcuts."
   ↓
load TMT_Context → already knows the architecture, the test command,
                   what dark mode did, what is outstanding
   ↓
search only where it still needs to
```

Он не вставляется целиком, а укладывается в бюджет. Небольшие файлы входят полностью, у
больших сохраняются самые важные разделы, и при этом **говорится, какие разделы были
опущены**, чтобы модель никогда не решила, что раздела, которого она не видит, не
существует.

### Контекст никогда не главнее кода

`TMT_Context/` — это память, а не истина. Если `notes.md` говорит, что аутентификация
живёт в `auth.py`, а репозиторий перенёс её в `authentication/service.py`, **прав
репозиторий**.

TMT сверяет пути, названные в заметках, с существующими путями и кладёт найденное в
промпт рядом с самими заметками:

```text
STALE: these paths are named in the notes but are not in the workspace now:
src/main.py. Do not act on them without checking.
```

Он не правит заметку за вас: файл может отсутствовать и потому, что заметка устарела, и
потому, что вы в середине рефакторинга, а различить это можно, только прочитав код.
Что он делает — так это мешает заметке быть принятой на веру и исправляет её, когда
узнаёт лучше.

### Ваши правки защищены

Вы можете в любой момент переписать любой из файлов вручную. TMT меняет **один раздел за
раз** и записывает каждый другой байт обратно ровно таким, каким прочитал, — включая
заголовки, о которых он никогда не слышал, вашу прозу и ваши отступы. Нет операции,
которая передавала бы файл целиком, и нет способа такую попросить.

Если вы отредактируете файл, пока TMT работает, ваша правка сохранится: файл
перечитывается в момент изменения, а не берётся из копии, прочитанной ранее.

### Секреты не записываются никогда

Ни ключей, ни токенов, ни паролей, ни значений из `.env`. TMT записывает требование, а
не значение:

```text
## Configuration

Environment variables this project declares (names only -- values are
never recorded here), from `.env.example`:

- `API_KEY`
- `DATABASE_URL`
```

Настоящий `.env` не открывается вообще: его наличие отмечается по stat, а содержимое не
читается. Всё записываемое в любой из двух файлов проходит через тот же фильтр учётных
данных, который использует `remember`, и всё, похожее на учётные данные, вымарывается и
о нём сообщается.

### Вместе с `/plan`, `/review` и `/verify`

Контекст не дублирует эти системы; он запоминает, к чему они пришли.

| | попадает в |
|---|---|
| шаги плана и их настоящий статус | `progress.md`, *Currently Working On* |
| что реально выполнила верификация и с какими цифрами | `progress.md`, *Tests* и *Verification* |
| блокирующие находки ревью, остающиеся открытыми | `progress.md`, *Known Issues* |

Итоговое состояние сохраняется **после** того, как шлюзы завершения согласились, и до
того, как уйдёт ответ, поэтому порядок остаётся таким:

```text
work → verify → review → persist → end
```

Сохранение никогда не может выпустить ответ, который удерживали план, верификация или
ревью, — его не спрашивают, пока все трое уже не согласились. А `send_message` ничего не
финализирует: фраза «я реализовал эту функциональность» — это предложение, а не
доказательство.

### Отдельно для каждого проекта, всегда

Путь к контексту вычисляется из активного рабочего каталога каждый раз, когда он
запрашивается, поэтому два проекта не могут разделять один контекст, а сведения из
одного не могут появиться в другом.

### Как это выключить

Settings → **Project Context** → Enter. По умолчанию **ON**.

Когда выключено, TMT никакой `TMT_Context` не создаёт, не читает и не обновляет.
**Уже записанные файлы остаются ровно такими, какие они есть** — они принадлежат проекту
и тому, кто их написал, а настройка не является согласием удалить чьи-то заметки.

Переключатель хранится в `.tmt_context` рядом с прочими настройками установки TMT,
поэтому это собственное состояние TMT, и за рабочим каталогом оно не следует. Файлы
контекста — единственное, что TMT намеренно записывает в ваш проект.

### Если его не удалось создать

Клон только для чтения, отказ прав, переполненный диск: TMT говорит об этом один раз и
продолжает вашу задачу.

```text
Persistent project context could not be created (PermissionError: ...).
Continuing without TMT_Context.
```

Ничто в этой возможности не стоит того, чтобы завалить из-за неё задачу.

### Стоит ли это коммитить?

Решать вам. TMT не трогает ваш `.gitignore`. По умолчанию эти два файла считаются
обычной документацией проекта — они читаемы, их видно в диффе, и они полезны всем, кто
работает над репозиторием, — поэтому, закоммитив их, вы делитесь тем, что узнал TMT, с
остальной командой. Игнорируйте их, если вам удобнее, чтобы они оставались локальными.

## Фоновые агенты

TMT умеет делегировать. Главный агент порождает фоновых рабочих агентов, они делают
настоящую работу теми же действиями и на тех же моделях, которыми пользуется он сам, а
он дожидается их и сообщает, что они сделали.

```
Task> spawn three agents to write multiply.py, divide.py and power.py, then wait for them
```

| | Где выполняется | Может редактировать | Может делать push | Говорит с вами | Завершается через |
|---|---|---|---|---|---|
| главный агент | цикл сессии | да | да | да | `end_conversation` |
| рабочий агент | фоновый поток | да | **нет** | нет | `internal_response` |
| агент-заметка | фоновый поток | **нет** | нет | только ответ | `internal_response` |

**Десять рабочих агентов одновременно.** Главный агент в это число не входит, как и
агент-заметка. Одиннадцатый запрос отклоняется фразой об этом, а не игнорируется.

`/agents` печатает, чем они заняты. В настоящем терминале стрелка вправо в конце пустой
строки открывает то же самое живой панелью, а стрелка влево закрывает её.

### Контракт делегирования

Делегирование — это контракт, а не пожелание. `spawn_agent` принимает необязательный
объект `constraints`, который говорит, что этому агенту можно делать, сколько он может
работать и о чём обязан отчитаться, — и **все три пункта TMT обеспечивает сам.** Агенту
сообщают его контракт, и ему же отказывают на диспетчере, поэтому обойти что-либо из
этого выбором другого инструмента он не может.

```json
{"action": "spawn_agent",
 "task": "Investigate how authentication is put together in this repository.",
 "constraints": {
     "read_only": true,
     "timeout_seconds": 600,
     "report": {"file_list": true, "diff": true, "summary": true}
 }}
```

Каждая часть необязательна, и **`spawn_agent` без `constraints` ведёт себя ровно так же,
как всегда** — тот же промпт байт в байт, те же права, тот же отчёт. В существующем
делегировании не изменилось ничего.

Ограничения задаются **на каждое делегирование отдельно**. Рабочий агент №1 может быть
только для чтения и с пятью минутами, пока рабочий агент №2 свободно пишет и имеет
пятнадцать; ни один не видит контракта другого и не влияет на него, потому что контракт
— это один неизменяемый объект, висящий на одной записи, и никакой глобальной переменной
на этом пути нет.

#### `read_only`

`read_only: true` означает, что агент может осматривать этот рабочий каталог и не может
его изменять. Он сохраняет все читающие глаголы — `read_file`, `read_lines`,
`list_files`, `glob`, `grep`, `find_symbol`, `tree`, `code_map`,
`related_tests`, `recall`, `git_status`, `git_diff`, `git_identity` — и получает отказ
во всём остальном.

**Обеспечивается во время выполнения, а не просьбой в промпте.** Отказ происходит до
запуска действия, в двух местах: `agent_worker` проверяет каждое действие перед
диспетчеризацией — и на пути одиночного действия, и на пакетном, — а
`agent_actions.execute_action` проверяет ещё раз на диспетчере. Оба обращаются к одной
и той же функции, поэтому правило одно, а мест, где оно применяется, два.

**Это белый список, а не перечень запрещённых глаголов.** Любое действие, добавленное в
TMT после того, как это было написано, по умолчанию отклоняется. Перечень запрещённых
глаголов тихо пропустил бы следующий изменяющий глагол, который кто-нибудь
зарегистрирует, а тот, кто его добавляет, — не тот, кто писал перечень.

Это покрывает и те пути, которые не выглядят очевидной записью в файл:

| Отклоняется | Потому что |
|---|---|
| `write_file`, `append_file`, `write_files`, `patch_file`, `replace_lines`, `replace_across`, `copy_file`, `rename_file`, `create_folder`, `delete_file`, `delete_folder` | они изменяют файлы |
| `run_file` / `run_python` | программа может записать что угодно, поэтому её запуск — путь к изменениям |
| `git_commit` | коммит изменяет репозиторий |
| `open_app` | он запускает приложение за пределами рабочего каталога |
| `remember` | он пишет в собственное хранилище памяти TMT |
| `git_push`, `plan`, `review`, `verify`, `project_context` | уже запрещены любому фоновому агенту, с контрактом или без |

**У TMT нет универсального глагола для оболочки**, и именно поэтому здесь нет никакого
списка «безопасных» команд. Единственный способ, которым рабочий агент может выполнить
произвольный код, — `run_file`, а делегированию только для чтения он запрещён напрямую:
никакого разбора командных строк, никаких догадок о том, пишет ли `sed -i`. Это честная
версия гарантии: она держится на том, что путь выполнения один и он закрыт, а не на
способности TMT отличить изменяющую команду от безобидной.

**На что она не претендует.** Делегирование только для чтения не может внести
постоянного изменения ни одним из глаголов, которые предлагает ему TMT. Это не песочница:
TMT не предотвращает запись на уровне операционной системы, и если какое-то будущее
действие откроет такой путь, его придётся сознательно добавить в белый список, прежде
чем рабочий агент только для чтения сможет до него дотянуться.

Об отклонённой попытке **сообщается, а не умалчивается**. Рабочему агенту говорят, что
именно было заблокировано и почему, чтобы он мог скорректироваться и продолжить —
заблокированная запись не означает автоматически проваленного делегирования, — а сама
попытка фиксируется и доходит до главного агента в результате:

```
Constraint violations: 1 write operation blocked (write_file src/auth.py)
```

#### `timeout_seconds`

Целое число от 1 до 3600. Это максимальное время работы **всего делегирования**, а не
одного действия, и оно не сбрасывается ни завершением действия, ни ответом модели.

Отсчёт начинается, когда рабочий агент действительно стартовал, а не когда он был
зарегистрирован, поэтому делегирование никогда не теряет часть своего времени из-за
того, что что-то другое было медленным.

**Обеспечивается средой выполнения.** Крайний срок проверяется на тех же трёх границах,
что и отмена: в начале каждого шага, между фрагментами потокового ответа и в строке
непосредственно перед диспетчеризацией каждого действия. Когда срок проходит:

- никакое дальнейшее действие не выполняется;
- статус агента становится `timed_out` — и это **не** `failed` и не `killed`;
- его рабочий слот освобождается немедленно, поэтому делегирование, ожидавшее
  свободного места, может стартовать;
- всё, что он успел сделать, сохраняется, а тот отчёт, который он был должен,
  по-прежнему собирается.

Гарантия ровно та же, что несёт `kill`, и не шире: **после крайнего срока ни один вызов
инструмента не диспетчеризуется.** Уже отправленный запрос всё же дойдёт до конца,
потому что поток Python нельзя завершить принудительно, а у потокового ответа нет
примитива прерывания. Заявлять о мгновенном прекращении было бы ложью там, где ложь
обходится дорого.

Никакого потока-таймера нет. Крайний срок — это арифметика по записи, выполняемая всякий
раз, когда ответ может иметь значение: перед каждой проверкой свободных мест, при каждой
перерисовке и внутри каждого ожидания, которое никогда не блокируется дольше ближайшего
срока. Это тот же подход, что и у пятисекундного удержания карточек, и по тем же
причинам: нечего отменять, нечему утекать, а тест управляет этим, увеличивая число,
вместо того чтобы ждать десять минут.

Некорректные таймауты отклоняются до того, как что-либо начнётся: отрицательный, ноль,
строка, `true`, доля секунды или что угодно сверх часового потолка. **Отклонённый
контракт не запускает никакого рабочего агента вовсе** — делегирование, работающее по
половине контракта, — это единственный исход, о котором никто не может рассуждать.

#### `report`

`file_list`, `diff` и `summary`, каждый независимо. Это **не права доступа**, и на то,
что агенту можно делать, они не влияют никак.

- **`file_list`** — файлы, которые собственные действия агента действительно прочитали
  и записали, взятые из запросов, которые эти действия несли. Никогда не собирается из
  того, что агент сказал о прочитанном.
- **`diff`** — то, что git говорит о файлах, которые записал этот агент. Ограничен
  именно этими файлами намеренно: главный агент продолжает работать, пока рабочий агент
  выполняется, и одновременно их может быть несколько, поэтому дифф всего дерева — это
  решительно не работа одного делегирования. Дифф делегирования только для чтения
  сообщает `No changes permitted by delegation.` Пишущее делегирование, ничего не
  изменившее, сообщает `No workspace changes.`
- **`summary`** — собственный рассказ агента о работе, то есть `response` его
  `internal_response`, и единственная часть отчёта, которая является словами модели.

Отчёты собираются при **любом** завершении, а не только при успешном: у делегирования,
вышедшего по таймауту или отменённого, всё равно есть настоящий список файлов, настоящий
дифф и настоящее время, и выбрасывать это из-за того, что оно завершилось не штатно,
означало бы уничтожить единственную запись о том, что оно успело.

Главному агенту возвращается структурированное и краткое — никаких стенограмм вызовов
инструментов, никаких сырых журналов:

```
Background agent #4
STATUS: TIMED OUT
Contract: READ ONLY  TIMEOUT 10:00  FILES  SUMMARY
Runtime: 10:00 of 10:00
Progress: 17 actions taken, 11 files inspected, 0 files changed

SUMMARY
  Found the authentication entry point in AuthService; three test modules cover it.

FILES
  Inspected (11):
    src/auth/service.py
    src/auth/token.py
    ...
  Changed: none
```

#### На экране

Счётчик рядом с приглашением показывает `4/10 agents`, заголовок панели —
`AGENTS 4/10`, а карточка агента с ограничениями компактно несёт свой контракт:

```
██░░░░░░ #3  RO  8:32/10:00  +0 -0  ~4k out  1m28s  running
```

`RO` — только чтение, пара чисел — оставшееся время против лимита (настоящий обратный
отсчёт по той же арифметике, которая действительно остановит работу), а `F D S` на
карточке отмечают требования к отчёту. `/agents` говорит всё это полностью там, где
хватает ширины, чтобы прочесть. Агент, вышедший по таймауту, показывается как `timeout`
и окрашен как остановка, а не как провал, потому что это она и есть.

#### Вложенное делегирование

Фоновые агенты не могут порождать собственных агентов — в их контексте действий вообще
нет реестра, — поэтому делегирование только для чтения никак не может дотянуться до
пишущего. Так было и до появления контрактов, и это не изменилось; никакого правила о
вложенных рабочих агентах здесь не выдумывается для того, чего не может произойти.

### Наблюдение за их работой

Пока агенты работают, у каждого есть собственная строка прямо под главным индикатором
прогресса:

```
██████████  60% Working                      <- the main agent, in colour
██░░░░░░ #1  +45 -3  4k out  47s  running    <- one row per agent, in grey
██████░░ #2  +0 -0  ~900 out  1m34s  running
████████ #3  +7 -120  ~15k out  2m21s  done
```

Каждая строка несёт номер агента, добавленные и удалённые им строки, сгенерированные
токены, время работы и состояние. Всё на ней измерено, а не оценено, кроме тех величин,
что помечены `~`: это значит, что провайдер их не сообщил и TMT вычислил их из текста, и
помечается это везде, где происходит.

**Полосы агентов серые, а главная полоса цветная, и в этом весь смысл различия.**
Цветовой градиент означает «главный агент работает, и вот насколько он продвинулся».
Пять цветных полос читались бы с первого взгляда как один процесс, показанный пять раз.
Агенты получают отсутствие цвета, а не собственный цвет.

**Полоса агента показывает израсходованную долю его бюджета шагов, а не то, насколько он
близок к завершению.** Второго не может знать никто — полоса, подразумевающая это,
выдумывала бы ту единственную величину, которой ни у кого нет. Полоса завершившегося
агента заполнена потому, что он закончил, и это единственный момент, когда завершённость
действительно известна.

Строка и карточка завершившегося агента остаются пять секунд, а затем исчезают. Его
результат — нет: главный агент может запросить его и много позже.

Счётчик над полем ввода включает работу агентов в общие итоги сессии:

```
+55 lines, -5 lines, ~12k context, 433 out, agents ~22k tokens
```

Строки включают всё, что написали агенты: строка, написанная рабочим агентом, — это
строка, написанная сессией, а счётчик, показывающий `+0`, пока пять рабочих агентов
переписывали проект, говорил бы правду об одном потоке и ложь о сессии. Расход токенов
агентами показывается отдельно от `context`, потому что последний — это то, насколько
заполнено окно выполняющегося запроса, и добавление туда пяти рабочих агентов описывало
бы контекст, которого не существует.

### `/note` — спросить о рабочем каталоге, ничего не потревожив

```
Task> /note which module owns the prompt box?
```

Агент только для чтения отвечает по рабочему каталогу, пока всё остальное продолжается.
Он может искать, читать и осматривать структуру; он не может создавать, редактировать,
удалять и делать push, и это обеспечивается белым списком, проверяемым перед каждым
действием, а не вежливой просьбой.

Вопрос идёт в той же строке. Такая форма работает везде, в том числе в конвейерном
запуске: конвейерный чтец берёт одну задачу на строку, поэтому двухшаговое приглашение
из конвейера недостижимо в принципе. В настоящем терминале одинокий `/note` спросит
вопрос отдельно.

### Чего фоновые агенты намеренно не умеют

Это ограничения замысла, а не недоделки:

- **Рабочий агент не может делать push.** Он может читать `git status`, `diff`, `log` и
  `branch` и может коммитить; обращение к удалённому репозиторию остаётся за главным
  агентом, которому для этого нужны ваши собственные слова в задаче.
- **Рабочий агент не может удалить файл или папку.** И то и другое ждёт подтверждения
  человека в терминале, а у фонового потока нет терминала, где его можно было бы
  спросить. Вместо этого рабочий агент сообщает путь, а делает это главный агент.
- **Рабочий агент не может прогнать набор тестов.** `run_file` сдаётся через 10 секунд,
  а настоящий набор идёт дольше, поэтому рабочий агент, которого попросили проверить
  тесты, скажет, что не смог, и что он сделал вместо этого. Результат, которого он не
  видел, он не сообщит.
- **«Убийство» кооперативно, а не мгновенно, и то же самое верно для таймаута.** Python
  не может принудительно остановить поток. Гарантируется — и тестируется — вот что:
  **после убийства агента или прохождения его крайнего срока не выполняется ни одного
  дальнейшего вызова инструмента**; отмена вступает в силу на ближайшем фрагменте или на
  ближайшей границе действия. Агент, застрявший на зависшем соединении, помечается
  убитым и бросается; его поток — демон и никогда не сможет удержать TMT открытым.
- **Очереди нет.** Десять рабочих агентов — жёсткий предел, и одиннадцатый запрос
  отклоняется фразой, а не паркуется. У TMT нет планировщика, с которым это можно было
  бы связать, а строить его ради этого было бы куда большим делом, чем требует сам
  предел; отказ называет предел и говорит, что с этим делать, и именно на это реагирует
  главный агент.
- **Ожидание блокирует главного агента.** Это обычное действие, а не приостановка.
  Интерфейс остаётся живым во время ожидания, потому что живая область перерисовывается
  в собственном потоке, а Ctrl-C возвращает вас к приглашению.
- **Рабочие агенты не согласовывают свои записи.** Любая отдельная запись атомарна, и
  если два рабочих агента затронули один файл, главному агенту сообщается, какие именно.
  Никаких блокировок сверх этого нет, поэтому давайте параллельным агентам разные файлы.
- **Собственных действий рабочего агента вы не видите.** Интерфейс показывает для
  каждого полосу и короткую метку, а не выполняемые им чтения и правки. Что он сделал,
  возвращается в сводке главного агента, и именно поэтому главному агенту велено
  говорить, что он делегировал.
- **На карточке нет времени работы, а в строке под индикатором прогресса — есть.**
  Панель перерисовывается только тогда, когда её содержимое меняется, а нарисованная там
  длительность либо устаревала бы, либо заставляла бы перерисовывать её на каждом тике,
  а именно из-за этого раньше мерцал курсор.

### Во что обходятся агенты

Каждый рабочий агент несёт собственный системный промпт в каждом запросе, потому что API
не хранит состояния. Этот промпт — около 14 тыс. оценочных токенов против 19 тыс. у
главного агента: он несёт `tree` проекта, а не содержимое файлов, которое встраивает
главный промпт, что экономит примерно 1500 токенов на запрос. Десять рабочих агентов
несут по копии каждый, поэтому делегирование не бесплатно: оно покупает параллелизм за
токены, а поднятие предела с пяти до десяти удвоило то, сколько его сессия может купить
за раз. Делегируйте работу, которая действительно разделима, а не ту, которую вы сами
сделали бы в два шага.

Контракт добавляет несколько сотен токенов тому рабочему агенту, который его несёт, и
ровно ничего тому, который не несёт: промпт делегирования без ограничений байт в байт
тот же, каким был до появления контрактов.

## Интерфейс

Пока идёт задача: анимация THINKING до первого вывода, затем индикатор прогресса,
прошедшее время и живой счётчик токенов. Текст модели раскрывается символ за символом по
мере поступления. Итоговый ответ обрамляется рамкой. Счётчик работающих агентов
появляется рядом с индикатором всякий раз, когда они есть.

**Панель агентов — это колонка внизу экрана, а не боковая панель во всю высоту.** Она
делит живую область с ответом и полем ввода; разговор выше сохраняет полную ширину и
никогда не перерисовывается. Это осознанное ограничение, а не недоделка: прокрутка —
единственная постоянная запись сессии, которая есть у TMT, и обе escape-возможности,
позволяющие программе занять всё окно, — сужение области прокрутки и альтернативный
экранный буфер — её уничтожают. Строки, ушедшие за пределы суженной области,
отбрасываются, а не сохраняются, поэтому прокрутка вверх переставала бы доставать до
собственной истории сессии. Отдельный тест ищет их в модулях, чтобы ни одна не вернулась.

На терминале уже 45 колонок панель занимает всю ширину живой области, и пока она открыта,
поле ввода не рисуется; уже 30 колонок она отказывается открываться и говорит почему.
Карточки отбрасывают строку активности раньше строки с токенами и обрезают текст, а не
переносят его.

### Набор текста во время работы

Поле ввода остаётся живым в течение всего хода. Вы можете писать следующий вопрос, пока
агент ещё работает над предыдущим, вместе со всеми клавишами редактирования.

**Enter ставит строку в очередь, а не прерывает работу.** Она будет обработана, как
только завершится текущая задача, и строки обрабатываются в том порядке, в каком вы их
ввели, — так что можно поставить три уточнения подряд и уйти. Поле сообщает, сколько их
ждёт.

`/note` тоже можно набрать там же, и в этом его смысл: он отвечает по рабочему каталогу,
не мешая идущей работе.

Ctrl-C по-прежнему останавливает выполняемую задачу, ровно как раньше.

Для этого нужен настоящий терминал. Конвейерный запуск или запуск с перенаправлением
читает одну задачу на строку, и поле в нём неактивно, — именно это получают всякий
сценарный запуск и набор тестов.

Задайте `TMT_STREAM=0`, чтобы отключить потоковую выдачу. Ей также нужен `requests`; без
него TMT работает без потоковой выдачи.

## Слэш-команды

В приглашении строка, в которой нет **ничего, кроме** команды с `/`, обрабатывается
самим TMT и никогда не отправляется модели. Имена нечувствительны к регистру. Всё
остальное — задача и уходит модели ровно так же, как раньше, включая строку, которая
просто начинается с пути, например `/usr/bin/python is broken`.

`/plan`, `/review` и `/verify` — те три, что читаются в обе стороны. В одиночку на
строке каждая из них — приведённый ниже отчёт только для чтения; с задачей после неё —
`/plan Build the login page` — строка является этой задачей, а возможность включена для
неё. См. [Возможности](#возможности-plan-review-verify).

| Команда | Что делает |
|---|---|
| `/context` | разговор на текущий момент: модель, провайдер, рабочий каталог, сколько ходов переносится в следующий запрос, оценка входящих и исходящих токенов, добавленные и удалённые строки и несколько последних вопросов |
| `/config` | настройки, при которых выполняется запрос: модель, провайдер, уровень усилий, потоковая выдача, режим JSON, рабочий каталог и задан ли API-ключ |
| `/clear` | забыть разговор и начать заново. Модель, уровень усилий, рабочий каталог и все прочие настройки сохраняются, и ни один файл не трогается |
| `/effort` | показать текущий уровень усилий |
| `/effort low\|medium\|high` | задать его |
| `/model` | показать текущую модель и те, что предлагает этот провайдер |
| `/model <name>` | переключиться на одну из них, по идентификатору или по имени, показанному в Settings |
| `/note <question>` | ответить на один вопрос о рабочем каталоге, ничего не меняя |
| `/notes` | что TMT помнит об этом проекте между сессиями: где находится `TMT_Context/`, что в каждом файле и какие заметки называют пути, которых больше нет |
| `/agents` | чем заняты фоновые агенты |
| `/back` | выйти в стартовое меню, сохранив сессию. См. ниже |
| `/plan` | шаги, которые TMT проходит для этой задачи, и что осталось |
| `/verify` | что реально было выполнено для проверки работы по этой задаче: каждая проверка, её команда, её код возврата и вывод всего, что провалилось |
| `/review` | что нашло независимое ревью: вердикт, каждая находка и история ревью этой задачи |

### `/back` — меню без потери сессии

`/back` возвращает стартовое меню на экран поверх сессии, которая продолжает
существовать. Ничего не завершается, не очищается, не отменяется и не ожидается:
разговор остаётся разговором, план остаётся планом, а любые фоновые агенты продолжают
работать за ним. Раньше Settings и Help были доступны только через выход.

Меню, которое он открывает, — это меню запуска с тремя отличиями:

```
> Resume    Go back to the session, which is still here
  Settings  Provider, API key and the model TMT runs on
  Help      What TMT does, and how to drive it
  Exit      Close TMT and end the session
```

- **Start читается как Resume**, и его подпись продолжает переливаться градиентом, даже
  когда курсор находится в другом месте, — это экран говорит, что ваша сессия всё ещё
  здесь.
- **Exit сообщает, что завершает сессию.** Слово то же самое, что и при запуске;
  последствие — нет.
- **Settings не предлагается, пока что-то ещё работает.** Строка исчезает — не
  становится серой и не отключается, — а строка над списком говорит, что работает и что
  делать:

```
Settings are not offered while work is running: 2 agents. Wait for it to
finish, then /back again.
```

Провайдер, ключ и модель читаются, пока запрос находится в полёте, поэтому смена одного
из них под работающим агентом вносит никем не заказанное изменение в середину уже
начатого запроса. Когда работа завершится, строка вернётся на следующем кадре, не
закрывая меню.

Выбор Resume очищает экран, снова рисует шапку и возвращает вас к приглашению — всё
ровно так, как вы оставили.

**Уровень усилий** — это то, сколько работы TMT потратит на одну задачу. Он меняет две
вещи, и только те, что реальны у любого провайдера: какой длины ответ запрашивается и
сколько кругов цикла агента может занять один вопрос.

| Уровень | Запрашиваемая длина ответа | Кругов на задачу |
|---|---|---|
| `low` | 4096 токенов | 12 |
| `medium` (по умолчанию) | 4096 токенов | 35 |
| `high` | 8192 токена | 60 |

Длина ответа ни на одном уровне не опускается ниже 4096. Каждый ответ — это один
JSON-объект, и те из них, что имеют значение, несут внутри себя целый файл, поэтому
меньший лимит не делает модель лаконичнее — он обрывает объект посреди строки, и запись
не происходит вовсе. Настройка хранится в `.tmt_effort` рядом с установкой и переживает
перезапуск, как и выбор модели.

**Автодополнение.** В настоящем терминале набор `/` показывает под набираемой строкой
десять команд, и список сужается по мере ввода: `/mo` оставляет `/model`. Tab дополняет
настолько, насколько кандидаты совпадают: `/mo` становится `/model `, а `/co` становится
`/con`, потому что и `/context`, и `/config` всё ещё подходят. Конвейерный запуск или
запуск с перенаправлением читает строку целиком и никакого списка не рисует; сами
команды там по-прежнему работают.

**Секреты.** Ни `/context`, ни `/config` никогда не печатают ключ, токен или пароль.
`/config` говорит, задан ли ключ, и ничего больше о нём — ни значения, ни даже
замаскированной формы.

## `tmtcode` не распознаётся

Команда установлена, но каталог, куда её положил pip, отсутствует в вашем PATH. Найдите
этот каталог:

```bash
python -c "import sysconfig; print(sysconfig.get_path('scripts'))"
```

Это `Scripts` в Windows и `bin` в macOS и Linux, внутри того Python или виртуального
окружения, в которое вы устанавливали. Добавьте его в PATH или используйте любой из двух
запасных вариантов — оба принимают те же аргументы и выбирают каталог проекта так же:

```bash
python -m TMT                     # откуда угодно, если установлено
python /path/to/TMT/TMT.py        # откуда угодно, прямо из клона
```

Если вы устанавливали в виртуальное окружение, `tmtcode` существует, только пока это
окружение активно.

`tmtcode --help` печатает список аргументов.

## Тесты

```bash
python run_tests.py
```

Набор тестов лежит в `testing/` и разделён на `testing/unit/` и `testing/integration/`.
Запускающий скрипт остаётся в корне и находит оба; что куда относится, см. в
[testing/README.md](../testing/README.md).

1581 тест. Восемь из них читают API-ключ из `.tmt_key`, поэтому на свежем клоне без
настроенного ключа эти восемь падают, а остальные проходят.

Прогон занимает примерно пятнадцать минут, а не две, как раньше, и почти всё это время —
один тест в `test_agent_review.py`, который запускает трёх настоящих агентов-ревьюеров и
ждёт живого обращения к API для каждого. Он же — единственный недетерминированный тест
здесь: он фиксирует проваленное ревью, а затем отправляет фиктивные объекты, чтобы
доказать, что ни один из них не может превратить его в пройденное, — но запуск `review`
запускает ревью, поэтому живой ревьюер, которому ваше рабочее дерево понравилось,
проводит его через законный путь, и проверка срабатывает. Прежде чем поверить ему,
запустите его ещё раз.
